# Collab: Live Session Sharing

`/collab` shares your running session with other omp instances in real time. Guests render the **same session natively in their own TUI** — streaming assistant text, tool-call cards, footer state (cwd, model, context %, cost), ctrl+o expansion, `/dump` — no terminal mirroring. Guests can prompt and interrupt the agent; the host machine runs the agent and all tools.

## Quick start

Host:

```
/collab
```

prints

```
Collab session started!
 • Join from another terminal: omp join "mgAYTZwEnpRQtca0CTgn-Q.gdJUbTovD94ofDaa8YvhY0-ty16w4fn8PgB6PLnoA30"
 • or any web browser: my.omp.sh/#mgAYTZwEnpRQtca0CTgn-Q.gdJUbTovD94ofDaa8YvhY0-ty16w4fn8PgB6PLnoA30
```

The browser line is click-to-join (an OSC 8 hyperlink to the full `https://` deep link): the relay serves the web guest client at `/`, and the room id + key ride in the URL fragment. From another omp (any directory, any machine), either form works:

Running `/collab` or `/collab view` starts or displays the active hosting session, rendering terminal/browser join links and a QR code for the browser URL. `/collab` requests control access: if the active room was started view-only, it replaces that room. `/collab view` reuses either access level and prints only the read-only link.

```
/join my.omp.sh/#mgAYTZwEnpRQtca0CTgn-Q.gdJU…
```

The guest's previous session is restored on `/leave` (or when the host stops).

### Commands

| Command           | Effect                                                                              |
| ----------------- | ----------------------------------------------------------------------------------- |
| `/collab`         | Start full-control sharing; reuse a control room or replace a view-only room        |
| `/collab <relay>` | Start sharing through a specific relay (`relay.example.com`, `ws://localhost:7475`) |
| `/collab view [relay]` | Start read-only sharing, or print the existing room's read-only link/QR        |
| `/collab status`  | Show link + participants                                                            |
| `/collab stop`    | Stop sharing                                                                        |
| `/collab list`    | List every active local Collab host (no links)                                      |
| `/join <link>`    | Join a shared session as a guest                                                    |
| `/leave`          | Leave (guest) or stop sharing (host)                                                |

`/collab start [relay]` is also accepted. Passing a relay while a reusable room is active does not move that room to another relay; stop it first to change the relay.


### Sharing every session automatically

Explicit `/collab stop` and `/leave` also cancel any replacement already queued by a session transition. A later, distinct session change still follows the saved auto-start policy. Guests can answer startup dialogs, but cannot prompt, interrupt, or control agents until the outer startup—including setup UI and transcript replay—has completed successfully.

Dedicated joins retain session-change observation: a failed join returns to the saved auto-start policy immediately, and `/leave` or host disconnection restores automatic hosting for the local session and its later replacements. Remote replica resynchronization never starts a local host.

An explicit `omp join <link>` launch takes precedence over auto-start: it initializes as a guest without publishing a temporary local host, and leaves the saved auto-start setting unchanged. If interactive startup fails after a host has been installed, that room is shut down and withdrawn before terminal teardown and the startup error is rethrown.

Set `collab.autoStart` to `view` or `control` and every interactive session hosts itself as it starts, through `collab.relayUrl`, without running `/collab`. The room is created before extension `session_start` hooks run — a question an extension asks at startup is retained and delivered to the first writer that joins — and the relay connection proceeds in the background, so a slow or unreachable relay never delays the prompt (a failure is shown as a dim status line). Guests can join an auto-started room and answer a startup question straight away, but — like the local composer, whose Enter is gated for the same reason — they cannot prompt, interrupt, or drive subagents until startup has finished; such a frame is refused with `… is unavailable until the host finishes starting up`. Each auto-started session publishes itself to the local host registry below; the setting's value is the highest access the registry will hand out for it (`view`: read-only links only; `control`: links that can prompt and interrupt). `/collab` still works as before: it re-prints the current room, or replaces a view-only room with a full-control one when you ask for control.

Rooms follow the session, not the process. `/new`, `/resume`, `/fork`, and branching (whoever ran them) stop the current room — guests are told goodbye and its registry entry is withdrawn — before starting a replacement under the live auto-start policy. A guest holding the old link never sees a different session; one that asked for the switch with `/new`, `/resume` or `/fork` ends up in the new session only by rejoining the replacement room (the app does this by itself through a paired computer, and drops what it had sent but the old room had not shown). During an uncommitted `/resume`, the old room instead suspends while the target session is provisionally active; rollback restores access to the original room without needing a callback. Shutdown makes the room unavailable immediately and finishes its cleanup before disposing the session. After a failed session change, `/collab` and `/join` use current-session hosting state and retire any stale owned room before proceeding; joining still refuses to replace a live host.

Explicit stop also cancels pending automatic launches without changing the saved policy. Application frames still queued or being encrypted are discarded; only the final goodbye drains. Bytes already handed to the transport cannot be recalled. A later distinct session change or manual start can host again.

A room can also end on its own: the relay closes it for good, or the host's send backlog exceeds its limit (`Collab ended: …`). Its guests must rejoin to resync, but the session keeps following the live auto-start policy: once the ended room has withdrawn, a replacement room (next generation) is hosted for the same session. An auto-started room the relay never opens — the relay is unreachable, or the connection times out — is retried the same way; no guest or registry reader ever saw it, so the retry reuses its generation and a session that recovers still publishes generation 1 first. The first replacement is immediate; if rooms keep ending, or the relay stays unavailable, within five minutes of each other, each further replacement waits twice as long (1 s, 2 s, 4 s, … up to 60 s). `/collab`, a session switch, `/collab stop`, and shutdown are not held behind that wait. With auto-start `off`, a manually started room that ends this way stays down until `/collab` is run again.

Guest ownership begins before replica activation and lasts through restoration of the previous local session. Neither joining, resynchronizing, nor a failed join may publish the replica as a local host. Leaving waits for restoration; a restoration failure is reported and keeps hosting blocked. An explicit stop during restoration suppresses its pending automatic restart without cancelling the restoration itself.

### Listing active local hosts

Suspension suppresses session data, joins, and guest actions; it does not suppress termination of an existing room-local dialog. An ended dialog carries only its request ID, so guests can dismiss it even if `/resume` later rolls back. The first authenticated answer to an existing dialog is retained while the target session is provisional and applied only if the original room resumes with the writer still authorized. Commit, stop, and local cancellation cannot apply that answer to another session. Joins during that provisional window must be retried once it settles. `/collab status` prints the room's published access level, so a view-only room never exposes its internal control link through status.

Already-admitted work is not generally undone by closing a room. In particular, subagent revival is shared with local callers and remains bound to the original agent reference and transcript; it may finish after closure, but the old guest's follow-up prompt is discarded. Closing a room does not cancel a local caller's coalesced revival.

Replacement rooms wait for the session operation to finish its hooks, transcript replacement, and any rollback before connecting. During an in-place transcript reset or tree navigation, existing guests continue receiving replication, but prompts and agent-control commands are refused until the operation settles; new joins and registry discovery are unavailable during that interval. If a previously admitted prompt is discarded before execution, its guest receives an error in a retained room. A retiring room instead sends a goodbye explaining that prompts absent from the conversation must be resubmitted after rejoining. A provisional switch must settle before deciding which notification applies.

`omp collab list` (and `/collab list` inside a TUI) enumerates every live Collab host on the local machine under the same omp configuration root — across terminals, projects, and profiles. Listing is metadata only; it never prints or transmits a link:

```
omp collab list                          # one row per host, then idle sessions; no links
omp collab list --json                   # {"version": 1, "hosts": [...], "idle": [...]}
omp collab link <instanceId|pid>         # print that host's full-control browser URL
omp collab link <instanceId|pid> --view  # print its view-only browser URL
omp collab link <instanceId> --json      # {"version": 1, "instanceId", "generation", "access", "url"}
omp collab start <instanceId|pid>        # make an idle session host (control access) and print its URL
omp collab start <instanceId|pid> --view # host with view access instead
```

Each host row carries a stable `instanceId` (random per process, kept across the rooms that process hosts), the room `generation` (increments every time the process starts a new room, e.g. on `/resume`), PID, session ID and name, working directory, model, start time, participant count, whether the relay connection is currently open, whether a host-side question is waiting for a writable guest (`inputRequired`), whether the session is running a turn (`busy`, rendered `working` or `idle`), and the highest `access` the registry will hand out (`view` or `control`). Hosts are sorted by start time, then PID, then instance ID. An empty result ("No active Collab hosts.") is a successful outcome, not an error.

`busy` is true for the whole turn — response streaming and tool execution alike — and false once the agent ends, so polling it is how a dashboard notices that a still-published session stopped working; a host that vanishes from the listing has died or become unreachable, which is a different thing. It is `null` from a host running an omp older than the field, and unknown must not be read as idle. `busy` reports a turn in flight, not scheduled work: it reads false during scheduling pauses (queued follow-ups, async-job waits, compaction) even when the session resumes on its own, so a `true`→`false` edge means the turn ended, not that the work finished.

A link is a deliberate per-host act. `omp collab link` asks the selected host for one URL, bound to the generation observed while listing: if the host has since started a new room (a session switch), the request fails with `stale_generation` instead of handing out the successor room, and you list again. A host published with `view` access refuses `control`. A PID that matches more than one live host (or none) is rejected with the candidate instance IDs; use the instance ID. The printed URL grants whatever its access says — treat a control URL like the `/collab` link itself.

Interactive sessions that are not hosting are listed too, under `idle` (`instanceId`, PID, session ID and name, cwd, model, start time, `busy`). Each interactive omp publishes an idle registry entry once startup completes and withdraws it on exit; while the process hosts, only its host row is listed, and both rows share the process's `instanceId`. `omp collab start` asks an idle session to start hosting through the same path as `/collab` and prints the link once the room is open and published. It never replaces a room: a session already hosting returns its existing link, or refuses `control` when its room is view-only. Idle entries use registry version 2, which older omp versions skip, so mixed versions keep listing hosts correctly.

How it works: each room publishes its own private IPC endpoint (a Unix domain socket on macOS/Linux, a named pipe on Windows — never a TCP port) once its relay connection succeeds; a rotation publishes under fresh artifact names, so withdrawing the old room can never disturb its successor. Full-control and view-only URLs, the room key, and the write token stay in the host process's memory; disk holds only discovery metadata (protocol version, instance ID, PID, endpoint, creation time, and a random bearer token) under `~/.omp/run/collab-hosts`. On macOS/Linux, permissions are tightened to owner-only on every publication. Windows inherits the configuration root's ACL, so that root must remain private to the user. Two authenticated operations exist over the endpoint: `snapshot` (host state, with free-form strings bounded so an unusual session title cannot make a host unlistable) and `link` (`access` + `generation` → one URL). Listing queries every live host concurrently with short independent deadlines, skips unresponsive or foreign-version entries, and prunes metadata left behind by crashed hosts; a transient socket error (`EMFILE`, `EACCES`, …) never prunes a live host. Stopped rooms disappear immediately — the registry keeps no history, lists no guests or remote hosts, and requires no relay change. Third-party dashboards and bridges can build on `omp collab list --json` plus `omp collab link` — or speak the newline-delimited JSON endpoint directly — without omp shipping a remote product of its own.

A missing registry directory means no active hosts. An unreadable or symlinked registry directory is a listing error, not a successful empty result; POSIX also rejects foreign-owned directories. Individual unreachable or malformed host entries are still omitted independently. The CLI exits nonzero for a directory error; `/collab list` displays a sanitized, bounded error and leaves the TUI usable.

## Link format

Accepted by `/join <link>` and `omp join "<link>"`:

```
<roomId>.<key>                                                    → default relay (wss://my.omp.sh)
<roomId>#<key>                                                    → legacy bare form
host[:port]/r/<roomId>.<key>                                     → custom relay, wss:// inferred
host[:port]/r/<roomId>#<key>                                     → legacy direct relay form
https://host[:port]/r/<roomId>.<key>                             → direct relay URL, normalized to wss://
wss://host[:port]/r/<roomId>.<key>                               → direct websocket relay URL
ws://localhost:7475/r/<roomId>.<key>                             → direct plain ws, localhost only
my.omp.sh/r/<roomId>.<key>?local=127.0.0.1:<port>                 → relay link plus the host computer's own loopback relay (see below)
https://host[:port]/#<link>                                      → browser deep link when web UI and relay share a host
https://web-host[:port][/<path>]/#<relay-link>                   → browser UI wrapper with relay link in the fragment
https://web.example/collab/#relay.example.com/r/<roomId>.<key>   → web UI and relay on different hosts
```

`<link>` / `<relay-link>` are parsed recursively as any accepted link above. For `http(s)` browser wrappers with a parseable fragment, the fragment wins before the HTTP host/path are treated as a relay. This lets `https://web.example/collab/#relay.example.com/r/<roomId>.<key>` open the web UI at `web.example` while joining `wss://relay.example.com/r/<roomId>`. If the fragment is not a complete collab link, parsing falls back to the legacy direct relay form, so `https://relay.example.com/r/<roomId>#<key>` still means relay `relay.example.com`.

The trailing `.<key>` or `#<key>` part is the room secret, base64url-encoded, in one of two strengths:

- **Full link** — 48 bytes: the 32-byte AES-256-GCM room key followed by a 16-byte write token. Grants prompting, interrupting, subagent control, and session controls (model, thinking level, compaction, rename).
- **View-only link** — the bare 32-byte key, no write token. Grants live read access only. Pre-token links parse as view-only.

The room secret is dot-joined in newly generated links because RFC 3986 forbids a raw `#` inside a URL fragment; parsers still accept legacy `#` forms and `%23`-mangled legacy deep links.

## End-to-end encryption

Every session payload (entries, events, state, prompts) is sealed with AES-256-GCM before it touches the socket. The relay sees only:

- room ids and connection counts,
- opaque ciphertext frames and their sizes,
- a 4-byte routing prefix (which guest a frame targets).

Possession of the link is the trust boundary: a full link reads and steers the session, a view-only link reads it. Share both like secrets.

## Guest permission model

Two trust levels, enforced by the link itself — the host verifies the 16-byte write token at join and rejects writes from peers without it (they appear as read-only in the participants list, and the join notice says so).

Guests with a full link can:

- read the entire session (including the back-transcript at join time),
- prompt the agent (rendered with their name badge on every participant's transcript; the LLM sees the prompt text verbatim — names are display-only). While a turn runs, a prompt steers it by default; `deliver: "follow-up"` instead queues it to run as its own turn once the current one ends. Writers see the queued follow-ups in `state.followUps` and can take one back with `session-cmd unqueue`. A prompt may also carry `model` (`provider/id`, one of `welcome.models`) and `thinking` (one of that model's `welcome.models[].thinkingLevels`) to run on another model for that prompt only, advertised as the `prompt-model` feature: the host refuses an unknown model or a level the model rejects with an `error` (`prompt not sent: …`), runs the run the prompt starts on the choice (a queued follow-up on its own, a steer on the running turn), and puts the session's model and thinking level back when the session settles, without a transcript entry or settings change. A `thinking` without a `model` is refused. Hosts without the feature ignore both fields.
- interrupt the agent (Esc),
- use [Agent Hub](./agent-hub.md) against the host's subagents: live table and progress, chat (steers the host's subagent), kill, revive, and transcript viewing (fetched from the host on demand).
- answer host interactive `select` and `editor` requests. The host broadcasts each pending request only to writable guests; the first submitted or cancelled response settles it and dismisses the other presentations.
- run session controls (`session-cmd`): switch the model for this session only (not saved as the default; refused while a turn runs or when the conversation exceeds the target model's context window), set the thinking level among those the current model accepts, compact with optional instructions, as the host's `/compact` does, rename the session, as the host's `/rename` does (a user-set name the automatic titler keeps), and `rewind` to just before one of the active branch's prompts, as the host's Esc Esc rewind does (refused while the agent works; the later turns stay in the session file as a branch; with `restoreFiles` it also restores the files, see [Rewinding files](#rewinding-files)). Writers receive the selectable models in `welcome.models`; hosts that predate the frame send no list, and guests hide the controls. Hosts list the newer capabilities (`follow-up`, `rewind`) in `welcome.features`; guests offer them only when listed.

Guests with a view-only link can read everything live — back-transcript, streaming text, tool cards, subagent transcripts — but the host rejects prompting, interrupting, agent control, and session controls from them.

Advisor records are not guest-visible subagents: they are excluded from roster snapshots and transcript fetches, and advisor chat/kill/revive commands are rejected.


Other session/machine commands remain host-only: `/resume`, `/branch`, bash (`!`), python (`$`), skills, etc. Typed `/model` and `/compact` stay host-only in a TUI guest; the web client's session controls are the guest route. Guests keep a small local allowlist (`/dump`, `/export`, `/copy`, `/open`, `/help`, `/hotkeys`, `/theme`, `/settings`, `/leave`, `/collab`, `/exit`, `/quit`).

When a guest joins during an assistant turn, that in-flight turn appears on the first subsequent `message_update`: the guest synthesizes the missing `message_start` from the update's full accumulating message before forwarding the delta. If the host emits no further update for that turn after the guest joins, there is no update from which to synthesize the live component. The durable entry still reaches the replica's message state, but entry frames are intentionally not rendered, so that edge case can remain absent from the live TUI.

### Rewinding files

A rewind can also put the files back. Before each prompt (the host's own, a guest's, or a queued follow-up when it starts) omp snapshots the git working tree of the session's folder into a private store under the agent dir (`<agent dir>/snapshots/<hash of the repository root>`), driven through its own git directory and index files. Your repository's `.git` is only read (`git ls-files`): HEAD, the index, refs and the stash never change. Snapshots are bound to the prompt's session entry through refs in that store, so they survive a resume; ones older than 30 days are pruned, per-session index files idle for a day are deleted, and stores of repositories that no longer exist (or unused for 30 days) are removed when another store is opened. The store keeps its own copy of the file contents rather than borrowing the repository's object database: borrowed objects could disappear if you later run `git gc --prune` or rewrite history, and a restore must not depend on that. The `rewind.snapshotFiles` setting turns it off.

A restore first snapshots the current files, then makes tracked and untracked non-ignored files match the snapshot taken before the chosen prompt: changed files are reverted, files created since are removed (only files whose creation time is after the snapshot began; one that already existed but was ignored or over the size cap then, say because a `.gitignore` rule was dropped, is left alone and counted in `skipped`; on filesystems without a creation time the change time stands in) and directories that emptied, deleted files come back, the executable bit and symlinks included. The state it replaced is kept as one undo slot: `redo-files` restores it, and refuses with a readable error if files changed since the restore (a later turn, an edit), so redo never overwrites newer work.

Guest side, for writers (read-only links get the usual `error`), on hosts whose `welcome.features` has `rewind-files` (advertised only while the session can snapshot: setting on, folder inside a git repository):

- `session-cmd` `rewind` with `restoreFiles: true` restores the files first, then moves the conversation. If the files cannot be restored (no snapshot for that prompt, a refusal) nothing moves and the guest gets an `error`; if the conversation then fails to move, the files are put back. On success the requester gets `{ t: "files-restored", kind: "restore", plan, skipped, canRedo }` and the room hears `<guest> rewound the conversation and restored N files (...)`. Without `restoreFiles` a rewind touches no files.
- `session-cmd` `rewind-preview` with the prompt's entry id answers `{ t: "rewind-preview", entryId, files }`: `files` is `{ revert, remove, recreate }` (files that would be reverted, removed, recreated) or `null` when no snapshot was recorded for that prompt. It changes nothing.
- `session-cmd` `redo-files` undoes the last restore and answers `{ t: "files-restored", kind: "redo", plan, skipped, canRedo: false }`.

Both restoring and redoing are refused while the agent, a compaction or a command is running. In the host's TUI, Esc Esc rewind of a prompt asks `Restore files too?` when files would change, and `/redo-files` undoes the last restore. The web client shows *Also restore the files* in *Edit & resend* and an *Undo restore* bar.

A prompt never waits more than 2 seconds for its snapshot (and Esc ends the wait): past that it runs without one (the restore then answers that no snapshot was recorded for it), and the snapshot finishes in the background without being bound to it. While one is still running, later prompts skip snapshotting instead of queueing another pass, and a repository that makes three prompts in a row give up is skipped for five minutes. In the TUI, the Esc Esc rewind waits at most 1.5 seconds to learn which files would change, then rewinds the conversation only. The index is kept per session and a new session starts from the newest other one, so after the first snapshot of a repository (seconds to tens of seconds for tens of thousands of files, on a large repository longer than the budget, so the first prompts may have none) a snapshot takes a fraction of a second.

Limits: git repositories only (other folders advertise nothing and snapshot nothing). A repository with more than 50,000 files (tracked, or untracked and not ignored: an untracked `node_modules` counts) or more than 512 MiB of covered files is not snapshotted, and is not tried again for five minutes. Files over 2 MiB, ignored files, files outside the repository, and non-regular files are not snapshotted and not touched. A path the snapshot does not cover that blocks a restore (for example an oversized file where a directory must come back) is skipped and counted in `skipped`. Shell side effects outside the repository (packages installed, services started, files elsewhere) are not undone, and neither is anything a command did to ignored files. Snapshots are taken at prompt boundaries, so a restore to before a prompt also reverts edits made by hand after that prompt was sent (they cannot be told apart from the agent's), while edits made before it are part of the snapshot and stay.

### Undoing the last turn

`/undo` takes back the last turn in one step: it rewinds the conversation to just before the last user (or guest) prompt, restores the files from that prompt's snapshot when one exists (the same snapshots as [Rewinding files](#rewinding-files); without one only the conversation moves), and puts the prompt text back in the editor to edit and resend. The rewind is the same branch move as `/branch`, so the undone turns stay in the session file as a branch reachable from `/tree`. Repeating `/undo` walks one prompt further back each time. `/redo` returns to the conversation tip and the file state the last `/undo` left; several undos redo in reverse order. Redo stays valid only until something new is sent (a prompt, a compaction, any move off that tip), and its files part is refused, leaving everything as it is, when the files changed since the undo. Both are refused while the agent, a compaction or a command is running.

Guest side, for writers, on hosts whose `welcome.features` has `undo` (always advertised: the conversation half works without file snapshots):

- `session-cmd` `undo` and `redo`, or the slash commands `/undo` and `/redo` (listed in `welcome.commands`, no arguments). A refusal (nothing to undo, nothing to redo, busy, files changed since the undo) answers with an `error` and changes nothing.
- The requester gets `{ t: "turn-undone", kind: "undo" | "redo", text?, images?, staleText?, files?, skipped?, filesUnavailable? }`: for an undo `text` and `images` are the removed prompt to put back in the message box; for a redo `staleText` is that draft, to clear if it is still untouched. `files` is the restore plan `{ revert, remove, recreate }` when files changed, and `filesUnavailable: true` means the host snapshots files but recorded none before that prompt. The room hears the usual `branch` frame and a notice naming the guest (`<guest> undid the last turn and restored N files (...)`, `<guest> redid the turn`).
- `state.redoTurns` is how many undone turns `redo` can bring back (absent or `0`: none), so the web client offers *Redo* only when it is positive.

The web client shows *Undo* and *Redo* in the session sheet and a *Redo* bar after an undo; both appear only when the host advertises `undo`.

### What a turn changed, and receipts

A writer on a host that advertises `turn-diff` in `welcome.features` (the host's session can snapshot files, see [Rewinding files](#rewinding-files)) can ask what one prompt changed or what the whole session changed. The diff compares the file snapshot taken before the prompt with the snapshot before the next prompt that has one, or with the working tree when none follows, so it needs no git history and shows only that turn's edits, including files created and deleted. Covered files are those the snapshots cover (tracked and untracked, not ignored, up to 2 MiB).

- `session-cmd` `turn-diff` (`arg`: a prompt's entry id) and `session-cmd` `session-diff` (no arg: everything since the session's first snapshot, against the working tree) answer a targeted `{ t: "turn-diff", scope: "turn" | "session", entryId, files, spansTurns?, omitted?, reason? }`. `files` is `[{ path, status: "added" | "modified" | "deleted" | "typechange", added, removed, diff, truncated? }]`: `diff` is the unified hunks only (no `diff --git` preamble), `added`/`removed` are `null` for a binary file (`diff: ""`), `truncated` marks a per-file cut. `files: null` carries a `reason` (not a prompt on the active path, no snapshot recorded, snapshots unavailable). `spansTurns` is how many turns the diff covers (more than one when the later prompts had no snapshot), and `omitted` counts changed files beyond the 2000-file / 1 MB budget.
- `session-cmd` `receipts` (advertised as `receipts`, always) answers `{ t: "receipts", receipts }` with `receipts` = `{ turns, files, commands, approvals, subagents, truncated? }`, all derived from the session's entries on the active path: `files` are paths changed through `edit`, `write`, `apply_patch` and `ast_edit` (`{ path, tool, turn, promptId }`), `commands` the agent's `bash` calls and the person's `!` commands (`{ command, exitCode, source: "agent" | "user", turn, promptId }`), `approvals` the recorded tool-approval decisions (`custom` entries of type `tool-approval`: `{ tool, approved, by: "tui" | "guest" | "grant", reason?, turn, promptId }`; calls approved automatically by tier leave no entry) and `subagents` the `task` runs (`{ id, agent, label, exitCode, durationMs, turn, promptId }`). Each list keeps its most recent 500 rows (`truncated: true`). `turn` is 1-based; `promptId` feeds `turn-diff`.
- The requests are writer-only, like the other `session-cmd`s.

The web client shows a *Changes* action on every prompt (and in the long-press block sheet) and in the action row after each finished turn. It opens one sheet with three tabs: *This turn* (with previous/next turn), *Session* and *Receipts*. Files list their status and +/− counts and expand to the diff with the review comments of the working-tree views (tap a line, then send the comments to the message box); a check button marks a file viewed (kept in the browser per session and turn, cleared if the file's diff changes), and on wide screens a *Unified / Split* toggle lays the diff out side by side. Receipt rows link to their turn. The command palette lists *Show the latest turn's changes*, *Show everything changed in this session* and *Show receipts*. The mock host serves all three.

In the TUI, `/diff [turn [<n>] | session]` prints the diff (default: the latest turn; `turn <n>` counts prompts from 1) and `/receipts` lists the receipts. Both are host-only commands.

### What fills the context

A writer on a host that advertises `context-items` in `welcome.features` can see what fills the host's context window and prune items (the same ranking and pruning as the host's `/context` and `/context prune`, see [Compaction](./compaction.md#pruning-chosen-items-context)):

- `session-cmd` `context-items` answers a targeted `{ t: "context-items", items, usedTokens, contextWindow }`: `items` are up to 30 rows `{ id, kind, label, tokens, share, prunable }` ranked by size (`kind` is `toolResult`, `file`, `attachment`, `systemPrompt` or `toolSchema`; `share` is a fraction of `usedTokens`, the host status line's anchored count). System prompt parts and tool schemas are listed with `prunable: false`.
- `session-cmd` `context-prune` with a row's `id` as `arg` prunes it on the host and answers the same frame, refreshed, plus `pruned: { entries, tokensFreed }`; the room hears `<guest> pruned … from the context`. A stale or fixed row, or a response, compaction, or command still running on the host, answers with an `error` and changes nothing. Guests' replicas keep the original transcript text; only the host's model context shrinks.

The web client shows a *Fills context* row in the session sheet that opens the list with a prune button per prunable row.

### Trajectory and request preview

A writer on a host that advertises `inspect` in `welcome.features` can see every model request of the host's active branch and the request the next turn would send (the host's `/inspect` and `/preview-request`, see [Trajectory inspector](./inspector.md)). Read-only peers are refused. Both answers go through the host's secret obfuscator.

- `session-cmd` `inspect` answers a targeted `{ t: "inspect", rows, total }`: `rows` are the newest 200 requests, oldest first, each `{ seq, entryId, at, model, ttftMs?, durationMs?, input, output, cacheRead, cacheWrite, cost, stopReason, error?, injected }`. `at` is the request start (epoch ms), `ttftMs` the time to the first streamed token and `durationMs` the whole response (both absent when the provider reported none), `cost` is US dollars. `injected` lists what entered the context since the request before as `{ kind, label, tokens, text? }` (`kind` is `prompt`, `tool-results`, `system-prompt`, `context-notes`, `todo`, `verify`, `hook`, `memory`, `advisor`, `mode`, `compaction` or `other`; `text` is a redacted excerpt of at most 1,200 characters). `seq` counts every request of the branch and `total` is that count, so `total` above `rows.length` means older requests were cut. The rows are derived from the persisted session entries, so a resumed session reports its earlier requests too.
- `session-cmd` `preview-request` answers a targeted `{ t: "request-preview", preview }`: `preview` is `{ source, model, tokens, messages, tools, text, truncated, note? }`. `source: "request"` means `text` is the provider request body the next turn would send, captured before the host's transport sent it and aborted (nothing is transmitted); `"context"` means that transport cannot show its body without sending, so `text` is the provider-neutral context (system prompt, messages, tools) the next turn would hand it. `tokens` estimates the serialized request, and `text` is JSON cut at 120,000 characters (`truncated`). `note` says what the preview leaves out. A host with no model selected, or a refusal from the preview, answers with an `error`.

The web client opens a *Timeline* from a row in the session sheet and from the command palette (*Open the request timeline*), shown only for a writer on a live host that advertises `inspect`; it asks for `inspect` on open and has a refresh button. Requests are listed newest first with a bar that splits the response time into waiting for the first token and streaming (scaled to the slowest request), the tokens, the cache share and the cost; a failed request is marked, and expanding a request shows the context items it received with their excerpts. A summary gives the request count, cost, tokens, median time to first token and overall cache share. *Preview next request* sends `preview-request` and shows the source (`provider request` or `request context`), the host's note, the model, the message and tool counts, the token estimate and the JSON body, with a copy button.

### Tool approval choices

A host that advertises `approval-grants` in `welcome.features` lets writers answer a tool-approval prompt with "always" choices (see [Always allow and deny always](./approval-mode.md#always-allow-and-deny-always)). The prompt is the ordinary `ui-request` `select`, and its `options` are the choices' labels, so a client that ignores the extra field still shows a usable list and answers with the chosen label in `ui-response`. The request adds `approval: { tool, rule?, guestProject, choices }`: `tool` is the tool name, `rule` describes what an "always" choice saves, `guestProject` says whether the host honors a project-scoped choice from a guest, and `choices` is `{ label, kind }[]` with `kind` one of `once`, `session`, `project`, `deny`, `deny-project` (labels: *Allow once*, *Always allow (this session)*, *Always allow (this project)*, *Deny*, *Deny always (this project)*).

Only writers receive the request. A guest's `session` choice saves a session rule; its `project` and `deny-project` choices are applied to that call only (as `once` / `deny`, with a warning notice) unless the host runs with `collab.guestsCanSaveApprovals: true`. The host never asks a guest to edit the saved pattern; the host user's own answer opens the pattern editor. The web app shows the choices as buttons when the feature is advertised and disables the project-scoped ones while `guestProject` is false. The mock host (`bun run mock-host`) offers the prompt when a writer sends the prompt `approve [command]`; `MOCK_GUESTS_SAVE_APPROVALS=1` makes it honor guest project choices.

### Editing the queue, and mentions

A host that advertises `queue-edit` in `welcome.features` lets writers change the follow-ups they see in `state.followUps`. `state.followUpIds` carries one id per follow-up, same order (ids are stable for the life of the queued message, across edits and moves). Three `session-cmd` commands name a follow-up by `id`:

| `cmd` | fields | effect |
| --- | --- | --- |
| `queue-edit` | `id`, `arg` = the new text, optional `mentions` | replaces the text in place (id, position and attached images kept); mentions are expanded again for the new text |
| `queue-move` | `id`, `index` (0 = runs next) | moves the follow-up; its position among the other follow-ups is all that changes |
| `queue-steer` | `id` | takes it out of the queue and delivers it into the running turn, as a steer |

Only a prompt a guest sent (a `collab-prompt`) can be edited, and never one that starts with `/` (a slash command runs only when it is sent, so it is removed, not edited); move and steer work on any queued follow-up. The host answers with an `error` frame (`a queued prompt cannot be empty`, `that follow-up is no longer queued`, `no position given`, `no queued follow-up given`, or the reason an edit was refused) and announces a successful change as a `notice`. Read-only guests are refused like every other session command. `unqueue` (by text) keeps working on every host.

A host that advertises `mentions` expands references a `prompt` carries in `mentions` (and a `queue-edit` too): `{ "kind": "pr", "number", "title", "url" }` and `{ "kind": "session", "id", "title" }`. The text the guest typed is delivered unchanged (the web app writes `#123` and `@session:<first 8 of the id>`); the host appends a `<referenced-context>…</referenced-context>` block to the message the agent sees, listing each pull request as its number, title and URL, and each session with the path of its transcript (found by id under the sessions directory) and the instruction to read it (`read history://<id>`). A session the host has no log for is described as such. The list is validated and capped: at most 12 mentions, a pull request needs a positive integer number and an `https` URL, session ids match `[\w-]{4,64}`, titles are one line, have no angle brackets and are cut to 160 characters. Queued follow-ups keep the text as typed on their chip.

### Sessions run by another vendor's agent

The collab companion in `packages/collab-web` can also host a room for Claude Code, Codex, Cursor, Grok, OpenCode or a custom ACP command. `scripts/foreign/host-main.ts` is a detached process per session: it speaks the Agent Client Protocol to the vendor's agent over stdio and the collab protocol to the relay, so those rooms look like omp rooms to a guest. Such a host sets `welcome.agent` (`{ id, name }`; omitted on omp hosts) and publishes the same value as `agent` in its registry entry. The transcript is kept by the host in `<config>/agent/collab-foreign/sessions/<id>.jsonl`, and `<config>/agent/collab-foreign.json` lists the sessions the companion can resume.

A host advertising `permission-mode` accepts `session-cmd` `permission` with `arg` `supervised` or `full` and reports the current mode as `state.permission`. *Supervised* asks the guest to approve each tool call (the `approval` choices are *Approve once*, *Approve for this session* and *Deny*; "for this session" is a rule the host keeps itself, never the vendor's own "always" option); *full* approves every request and records each as a `tool-approval` entry. These hosts advertise only what they implement: `follow-up`, `approval-grants`, `permission-mode` and `rewind` always, `commands`, `prompt-model`, `spend-cap` and (in a git repository) `turn-diff` and `rewind-files` when the agent or the folder allows. A rewind cannot make the vendor agent forget turns, so the next prompt starts a fresh agent session whose first message carries a digest of the conversation that is left.

"For this session" uses omp's own grant rules: a shell grant is a program-and-subcommand pattern (`bun test *`) that never covers a compound or shell-controlled line, an edit or write grant names one path inside the working folder, only `read`, `grep` and `glob` inside the folder are granted whole, and fetch, web search and unknown tools are approved one call at a time (a call without a safe rule is offered *Approve once* and *Deny* only). A request to leave the vendor's own sandbox or to reach more than the call needs (Codex `sandbox_permissions` other than `use_default` or `with_escalated_permissions`, `additional_permissions`, a "network access" approval, Claude Code's `dangerouslyDisableSandbox`) is labelled *Leaves the sandbox* in the prompt and is never covered by a rule. Other vendors' agents run unsandboxed for now: the collab sandbox applies to omp sessions only, so a start that asks for an agent and a sandbox is refused, and the vendor's own permission mode is what limits a supervised session. `supervised` is reported only once the vendor has confirmed its ask-first mode: if the switch is refused the session stays in full access (and says so), and an agent that cannot be put in that mode at start-up or after a rewind is not used. The session index (`<config>/agent/collab-foreign.json`) is changed under an owner-aware lock (pid and token; only a dead owner's lock is broken), a damaged file is moved aside, and a host puts its whole row back when an update finds it gone.

## Web client

`packages/collab-web` is a standalone browser client for the same links — no omp install needed on the guest side. The relay serves it at `/`, which is what makes the `/collab` deep link click-to-join: `https://<relay>/#<link>` loads the client and auto-connects from the fragment. It renders the live transcript (streaming text, thinking, tool cards), a subagent panel with on-demand transcripts, and a composer with the same guest powers (prompt, interrupt, hub actions). Run `bun run dev` in the package for a local instance, `bun run mock-host` for an offline scripted host to develop against, and `bun run build` to emit a static `dist/` deployable anywhere (HTTPS required for WebCrypto). The client never talks to anything but the relay, and the key stays in the URL fragment.

The client is also an installable app (home-screen PWA). Because a home-screen launch carries no fragment, it remembers recent rooms and the last open room in browser storage, and offers *Paste link* and *Scan QR* (the `/collab` QR code) to join without typing. Inside a session it offers a chat view (prompts and replies with tool runs folded), find in session, a per-device *keep the latest turns* trim, *after this turn* follow-ups, *edit & resend* (rewind to before a prompt), the agent's task progress, selectable prompt, reply and tool-run blocks with copy, quote-to-composer and share actions, keyboard shortcuts and touch gestures, copy/share of replies and Markdown export, text and file attachments, a list of files the agent changed, session controls and usage, a *new since you left* marker, and an offline prompt queue. The optional companion (`bun run companion` in `packages/collab-web`, installable as a macOS LaunchAgent) pairs the app with a computer once and then lists every session hosting `/collab` there, built on `omp collab list` / `omp collab link`. It also drives the in-session sessions sidebar, needs-input banners, Web Push notifications sent with its own VAPID key, keeping the Mac awake while it runs (with battery warnings and power notifications), per-device pairing and removal, an inbox across sessions, spend alerts, a diagnostics screen, a read-only terminal view, a gallery of the session's screenshots, a live preview of the session's dev server, voice input transcribed on the computer, a working-tree view, an editor (file tree, tabs, and saves refused when the file changed on disk; read-only for view-only links and sandboxed sessions), and code map (folder, file, and symbol dependencies from the codemap index) for the session's repository, starting sessions in tmux (optionally sandboxed on macOS: file tools only, writes confined to the folder by `sandbox-exec`), and sharing idle sessions through `omp collab start`. See the [collab-web README](../packages/collab-web/README.md#installed-app-pwa) for details.

The companion also drives a git flow from the app, so it can change repositories, not only read them. *Start session* can run omp in a new git worktree (`git worktree add -b <branch> ~/.omp/worktrees/<repo>/<branch> HEAD`); the *Branch* tab of *Changes* reviews the session's branch against its base (origin's default branch, else `main`/`master`) from the merge-base; and *Commit*, *Push*, *Create PR*, and *Commit, push & open PR* run `git add -A && git commit`, `git push -u origin HEAD`, and `gh pr create` on the computer after an explicit confirm that lists the exact commands. The companion refuses these while the session's agent is working, on the base branch, and on a detached HEAD, and they use only the computer's own git and `gh` credentials. Anyone holding the companion pairing link can therefore commit and push in any session's repository: treat the link like an SSH key.

When the companion advertises `canGitFlow` in its `hosts` frame, the confirm of *Commit*, *Create PR* and *Commit, push & open PR* opens with text written for you. The app sends `git-message` (`{ instanceId, commit, pr }`); the companion gathers the uncommitted diff (for the commit message) and the whole branch against its base (for the pull request), asks a headless `omp -p --no-session --no-tools --no-extensions --no-skills --no-rules --no-lsp --no-title --thinking off --max-cost 0.25 --model @smol` run for a JSON `{ commit, title, body }`, and answers `git-message` with `text: { commit, prTitle, prBody, source, note? }`. The run is separate from the session being committed (an idle or busy session needs nothing from its agent) and uses the cheap `smol` role by default; the prompt goes in on stdin from a neutral folder, so project context files are not loaded. It carries the session title and the end of its last reply, the repository's 15 most recent commit subjects so the message follows its style (prefixes, casing), the repository's pull request template when it has one, and the diff cut to about 14,000 characters per section with lockfiles, generated bundles and binary files left out and a fair share per file. That diff goes to whichever provider the model uses, as it would in a session. The message, title and description appear editable, with *Regenerate* (it replaces edits) and the *Open as draft* toggle; text you type while the model works is kept; *Run* waits for the text. If the run fails, times out, or answers something unreadable, `source` is `fallback` and `note` says why: the text is then a template from the session title (typed `chore: …` in repositories that use conventional commits), the changed files, the branch's commit subjects and the diffstat, and the dialog says so. Nothing runs until you confirm.

The *worktree settings* (Settings → *Sessions* → *Git worktrees*, shown when `canGitFlow`) are kept by the companion in `<config>/agent/collab-companion-git.json` and read and replaced with `git-settings` (`{ settings?, trust?, sweep? }`, answered with `{ settings, worktreesDir, swept?, projects }`, where `projects` is `[{ root, script, hash, trusted, approved }]` for the repository setup scripts below; `trust` is `{ root, hash }` to approve the script that was shown, or `{ root, hash: null }` to withdraw; a replacement with an invalid field is refused and nothing is stored):

- **Branch name prefix** (`branchPrefix`, default `omp/`): generated worktree branches are `<prefix><YYYYMMDD-HHmm>-<4 hex>`. A prefix ending in a letter or digit gets a `/` added; empty means none. A branch name typed in *Start session* is used as written.
- **Worktree folder** (`worktreesDir`, default `<config>/worktrees`): an absolute path (`~/` allowed) under which worktrees are made as `<folder>/<repo>/<branch, / as ->`. Moving it leaves existing worktrees where they are and still removable from *All sessions* and by cleanup.
- **Setup script** (`setupScript`, default empty): a shell command run once, in the new worktree, right after it is created and before omp starts, with `OMP_WORKTREE_PATH`, `OMP_WORKTREE_BRANCH` and `OMP_REPO_ROOT` set (for example `bun install`). A script that fails or runs over five minutes discards the worktree and its branch and the start fails with the end of the script's output. Scheduled runs and best-of-N runs go through the same start, so they run it too.
- **Repository setup scripts** (`.omp/worktree-setup`, `trustedSetups` in the file): a repository can carry its own setup script, but it is code someone else wrote, so it never runs on its own. A start that finds one the user has not approved runs only the `setupScript` setting (if any), logs that the file was not run, and the script appears under *Setup script* in the worktree settings with its full text, *Approve this script* and, once approved, *Withdraw approval*. An approval is per repository (the repository's root path) and bound to the SHA-256 of the script's exact content, so editing the file (a pull, an agent) stops it running until it is approved again. An approved script runs with `sh -c` in place of the `setupScript` setting, from the very text that was hashed. The companion approves only a repository its start reported or that was approved before, and only when the hash the device sends is still the file's current one; scripts over 20,000 characters are never offered or run. A sandboxed session ignores the repository file entirely, because its agent can write it, and runs only the setting. The approvals are in `collab-companion-git.json` (mode `0600`), outside the repository.
- **Settle script** (`settleScript`, default empty): a shell command run in a session's worktree when the session settles, for cleanup such as `rm -rf node_modules target`, with the same `OMP_WORKTREE_PATH`, `OMP_WORKTREE_BRANCH` and `OMP_REPO_ROOT` as the setup script. It runs only for a folder the companion made as a worktree (`<worktree folder>/<repo>/<name>`, a linked worktree of its repository), never in the main checkout, a scratch folder or any other folder, and once per transition into settled: from any device's *Settle*, the idle auto-settle rule or the pull-request auto-settle rule (the companion keeps the settle time it last handled per session in `collab-companion-sessionorg.json`, so repeated syncs and restarts do not run it again; moving a session back to active and settling it again does; settled sessions that predate the setting are not run). It runs even while a dev server is still running in the folder, never delays or blocks the settle, and stops after five minutes (its process group is killed). Which worktree a session belongs to comes only from what the companion recorded when it started or resumed the session (`sessions` in `collab-companion-settle.json`) or from the list of open sessions, never from a session file, which a sandboxed session can rewrite; a session the companion cannot place is skipped. A sandboxed session's agent has no way to run code but can write everything a cleanup runs (`package.json` scripts, a `Makefile`, an `.npmrc`), so nothing runs in a worktree a sandboxed session was ever started in or above (a mark the companion makes before it starts one and never lifts, `sandboxed` in the same file), or that an open sandboxed session works in or above; the settle then shows *Skipped* (when there would have been something to run). A settle batch (a rule can settle many sessions at once) takes one list of open sessions and runs at most three commands at a time. A repository's own `.omp/worktree-settle` runs instead of the setting, with the same approval as the setup script (*Approve this script* under *When a worktree session settles, run*, per repository root and bound to the SHA-256 of the exact content, kept as `trustedSettles` in the file, and `trust` carries `kind: "settle"`). The latest result per worktree (done, failed with its exit code, timed out or skipped, with the end of the output; at most 50, gone when the worktree is removed) is kept in `<config>/agent/collab-companion-settle.json` and shown under *Latest cleanup per worktree* in the worktree settings. A companion that supports it adds `settleCleanup: { projects, results }` to the `git-settings` answer (`projects` like the setup scripts' for `.omp/worktree-settle`); the app shows the setting only when it is there.
- **Remove worktrees** (`cleanup`, default `off`): `merged` removes a worktree once its branch's pull request is merged (`gh pr list --head <branch> --state all`; an open one wins over a merged one, and an answer `gh` cannot give counts as not merged); `inactive` removes one that has seen no commit, checkout or staging for `days` days (1 to 365, default 14). The companion checks every ten minutes while cleanup is on, and *Clean up now* runs it at once. It runs `git worktree remove` without `--force`, so a worktree with uncommitted changes (untracked files included) is never removed; neither is one a running omp works in (end the session first), or one outside the worktree folders. The branch always stays, so no commit is lost.
- **Commit and pull request text model** (`messageModel`, default `@smol`): the model id or role passed to `omp --model`. The `@` form resolves the built-in `smol` role even when your settings do not configure it.

With the same signed-in `gh`, *GitHub* (in the session sheet) lists the open issues and pull requests of the session's repository, filtered to open, mine, or review requested, and opens one with its description, checks, and latest comments. It only reads (`gh issue list/view`, `gh pr list/view`, `gh repo view`); *Send to agent* puts a prompt about the item into the message box and sends nothing.

*GitHub alerts* (Settings → *Notifications*) use the same `gh` to watch your open pull requests in the repositories of the companion's sessions (`gh pr list --author @me`, every 5 minutes, every 2 while checks are pending) and push to devices with notifications on when checks finish or someone else reviews or comments. Tapping the notification opens the pull request.

*Organising sessions.* The sessions sidebar sorts sessions into **Pinned** (top, in your order), **Working** (running now), **Active**, **Snoozed** and a folded **Settled** section. Every row has a ⋯ menu (also right-click on desktop, press and hold on a phone) with *Pin to top*, *Move up/down*, *Snooze…* (1 hour, 4 hours, tomorrow 9:00, next week, and *Until the limit resets* for the open session when the host advertises `usage-limits` and the session is limited), *Wake now*, *Settle* and *Move back to active*; pinned rows also drag to reorder with a mouse. Pin, snooze and settle exclude one another, a snooze wakes by itself at its time, and each change offers an *Undo* for a few seconds. The auto-settle settings (Settings → *Sessions*, kept on this device without a paired computer): settle sessions idle for 3, 7, 14 or 30 days (default never; pinned and snoozed sessions are left alone), and, when a companion is paired, settle a session when its pull request merges or closes (default off).

The organisation is stored in the browser (`omp.collab.session-org`, so it also works without a companion: recent rooms are keyed `room:<roomId>`) and, with a paired computer, in the companion's `<config>/agent/collab-companion-sessionorg.json` (mode `0600`), so every device shows the same sidebar. A companion that keeps it puts `sessionOrgRev` (a counter) in its `hosts` frame; the app sends `session-org` (`{ doc? }`) and is answered with `session-org` (`{ doc, rev }`), where `doc` is `{ entries: Record<sessionId, { at, status: "active" | "pinned" | "snoozed" | "settled", order?, until?, reason? }>, settings: { at, idleDays, settleOnPr } }`. The companion merges the device's document into its own entry by entry, the larger `at` (the time of the action that wrote the entry) winning and an exact tie going to the larger JSON, so devices converge in any order; a device fetches again whenever `sessionOrgRev` moves, and re-sends its changes after being offline. Idle days count from the last time the companion saw a session working or asking (first sight counts as activity, so a restarted companion never settles a session at once); the pull request rule reads the branch checked out in each session's folder (`gh pr list --head <branch> --state all`, every 5 minutes while the rule is on, skipped for the default branch, working sessions, and pull requests that finished before the session started). Moving a session back by hand is never undone by either rule for that pull request or idle period. The start-screen computer card lists sessions unsorted. `bun run scripts/mock-companion.ts` serves a fixture list and the real organiser from a temp directory for trying two devices in a browser (it never touches `~/.omp`).

*End sessions when they settle.* Settling only moves a row; the omp process keeps running, idle, in its tmux session. A companion advertising `canEndOnSettle` in its `hosts` frame adds *End sessions when they settle* to the auto-settle settings (default off; `settings.endOnSettle` in the document, an optional boolean: a copy that lacks it, from an older app or companion, takes the value of the copy it is merged with instead of switching it off). With it on, a session the companion started (its omp runs in the companion's `omp-<id>` tmux session, other vendors' agents included) is ended with `tmux kill-session` once it is settled and idle, however it settled: *Settle* from any device, a bulk settle, the idle rule or the pull request rule. One that settles while working or asking is ended on the first poll after it goes idle; moving it back first cancels the end. Sessions started by hand in a terminal are never touched. The sessions waiting to end are kept in the `ending` list (`sessionId` → the `at` of the settle) of `collab-companion-sessionorg.json`, so a restart ends nothing twice, and turning the option on does not end sessions that are already settled. The worktree cleanup command (*When a worktree session settles, run*) runs after the end, never beside a live agent; the companion records the session's folder before ending it, so it is still found. An ended session stays under *Settled*, marked *ended* and listed from the session history (the 200 most recently active sessions, as *All sessions*); opening it, or *Move back to active*, resumes it like *Resume* in *All sessions*, and the row keeps its place when that fails. An omp session that never had a model reply has no session file, so ending it leaves nothing to resume.

The same `gh` also powers pull request review from the app: a *Files* tab with per-file diffs and line comments that become an agent prompt or a GitHub review, a confirm-first merge, and *Fix it*, which collects the end of each failing check's log (`gh run view --log-failed`) into a prompt for a session on that repository. A *Checks failed* notification opens *Fix it* directly.

Beyond reading, the companion can act on the computer for you. *Run* lists the repository's package scripts, Makefile targets, `just` recipes, and `cargo test`/`cargo build`, and runs only those (no free-form commands) after a confirm that shows the script body, with live output and Stop. *Download* saves a repository file to the device. *Schedules* starts a prompt once or daily on chosen weekdays in a new or resumed session, skipping runs while the daily spend limit is crossed. *All sessions* → *Messages* searches prompts and replies across every session and opens one at the matching message. Reviewing and merging are refused for sandboxed sessions, and running in any repository a sandboxed session works in. A merge applies only to the head commit the device showed.

Companions advertising `canScheduleCron` extend *Schedules* beyond once and daily. A schedule can repeat every N minutes (5 or more, anchored to its creation so runs do not drift), or follow a 5-field cron expression (`0 9 * * 1-5`, names such as `mon-fri`, and `@daily`-style macros) in an IANA time zone (default: the device's; empty means the computer's local time). The editor shows the cron in words and the next three run times in that zone as you type. Cron and interval schedules refuse anything that could fire more often than every 5 minutes. Across daylight-saving changes a time that falls in the spring-forward gap runs at the first valid moment after it, and a time in the repeated fall-back hour runs once, at its first occurrence (an hour field starting with `*` runs in both). Each schedule also has a catch-up policy for runs missed while the computer was off or the companion stopped: `skip` (default) drops a run that is over an hour late and records it as skipped, `run-once` starts a single catch-up run however late it is and notes when it was due. Schedules the agent made are marked *made by agent* in the list.

An agent can create schedules itself with the `schedule` tool (setting `schedule.enabled`, default off; see [schedule](./tools/schedule.md)). The tool talks to the companion over a local channel: the companion listens on `127.0.0.1` on an ephemeral port and publishes `{port, token, pid}` in `collab-companion-ipc.json` (mode `0600`, next to `collab-companion.json` in the companion's agent directory); the tool sends `POST /schedule` with `Authorization: Bearer <token>`. Requests that carry an `Origin` header are refused, so a web page cannot use it. Through the channel the agent can list schedules, create enabled ones (stored with `createdBy: "agent"`, never replacing another schedule) and delete only the ones agents made. Without a running companion the tool says that scheduling needs it. Creating always asks the user for approval, in every approval mode, showing the cron in words and the next three run times.

*Start session* lists the folders omp has run in, and a companion advertising `canBrowseFolders` (which follows `canStart`) also offers *Choose another folder…* to start in any folder on the computer; an older companion shows only the list. The browser view opens at the computer's home folder. The path field at the top shows the folder on screen and takes a path to jump to (Enter; `~` is the home folder and a path that is not absolute is read from it); the up arrow goes to the parent; each row opens a subfolder, and a git repository (a folder with a `.git` entry) is marked with a repository icon and *Git repository*; *Show hidden folders* adds the ones whose name starts with a dot; *Use this folder* continues as if a recent folder had been picked, with the usual new-session form (the folder's earlier sessions are in the recent list). Arrow keys or Tab walk the rows and Enter opens one. The app asks with `browse-folders {path?, hidden?}` and gets `folder-listing {listing}`: `path` (absolute, as resolved), `parent` (`null` at `/`), `folders` (`{name, path, git}`, sorted without regard to case) and `truncated`. The companion lists directory names only, never files or their contents; a symlink to a folder is listed under its own name and one that does not point to a folder is left out, as is anything it cannot inspect or enter. A listing is cut at 500 folders (`truncated`) and, on a slow disk, after 5 seconds. A path that does not exist, is not a folder or cannot be read is answered with an error naming it. A device that can start a session can already run code in any folder, so listing folders gives it no new power. The `start` request checks its folder before tmux runs, for a new session (a resumed one keeps the folder it recorded, and a session without a project starts in its own new folder): `~` is expanded, a path that is not absolute is read from the home folder, and a folder that does not exist or is not a folder is refused with a plain message. The mock companion answers `browse-folders` with the same code over a throw-away home folder (`<dir>/home`, with projects, git repositories, hidden folders, a symlink and a folder of 520 subfolders).

*Compare models* (best-of-N, companions advertising `canFanout`) runs one prompt on 2 to 4 models at once, each session in its own git worktree of the same repository, and lets you keep the best. Start it from the *Start session* sheet (tick *Compare models* under the prompt and pick the models; the folder must be a git repository) or from the message box of a session on that computer (the compare pill next to the model pills sends the draft). The companion lists the models with `omp models --json`, then for each model creates a branch `omp/fan-<group>-<n>-<model>` and a worktree from the repository's current commit (reusing the same worktree helpers as *New git worktree*, so the worktree folder follows the git settings; uncommitted changes in the folder are not carried over) and starts `omp --model <provider/id> --max-cost <share> -- "<prompt>"` in it, exactly as a scheduled run does. An optional total budget in USD is split evenly in whole cents, rounded down (`$10` over three models is `$3.33` each), and each session stops at a safe point at its share; a budget too small for a cent each is refused. A worktree that cannot be made undoes the others and fails the request; a session that does not start is listed with its error and its worktree discarded, and the rest go on. Sandboxed sessions are supported when the computer can run them.

Sessions of a group carry a model chip in the sessions list, and a *Compare …* button above the list opens the compare sheet. For each session it shows the status (working, needs input, idle, offline, ended, failed to start), the spend against its limit, the changed files against the base branch with `+`/`-` line counts, whether it has uncommitted changes, the newest finished test, verify, check, typecheck or lint run from *Run* (passes or fails), and the branch's pull request once there is one. It refreshes every 6 seconds while a session works. *Keep this one* asks first: the winner's session opens on its branch review (commit, push, pull request), and *Remove the other worktrees* (off by default) ends the other sessions and removes their folders while their branches stay. A worktree with uncommitted changes is removed only when *Discard their uncommitted changes* is ticked as well; otherwise it stays and is reported, and a worktree a session still runs in is never removed. Only sessions the companion started can be ended this way.

Companion frames (all need `canFanout`, which follows `canStart`): `fanout-models` → `fanout-models {models: [{selector, name, provider}]}`; `fanout-start {request: {cwd, prompt, models, budgetUsd?, sandboxed?}}` → `fanout-started {group}`; `fanout-compare {group}` → `fanout-compare {compare}`; `fanout-keep {request: {group, keep, removeOthers, discardDirty}}` → `fanout-kept {result: {removed, skipped}}` (`discardDirty` needs `removeOthers`). The `hosts` frame carries `fanout: {group, model}` on each session of a group. Groups (the newest 20) are stored in `<config>/agent/collab-companion-fanout.json` (mode `0600`). `bun scripts/mock-companion.ts` fakes a computer where starting sessions and comparing models work over a throw-away git repository (real worktrees and refusals, fake sessions); `--session-link <room link>` makes opening any session join a `mock-host` room.

Guests with a full link to a host that advertises the `commands` feature can run some slash commands, listed in `welcome.commands`: skills, prompt templates and markdown commands, `/plan`, `/retry`, `/clear` (the host's own `/clear`: the conversation context is dropped and the session continues; it takes no arguments and is refused, to the guest alone, while the host is answering, compacting or running a command), and the session controls `/model <provider/id>` (the session-only switch, as `/switch`), `/effort <level>`, `/compact [instructions]` and `/rename <title>`, which run the same code as the matching `session-cmd` frames, so they share its checks and refusals and name the guest in one `<guest> ran /x` notice, only when they succeeded. The bare forms that open a selector on the host (`/model`, `/effort`, `/rename`, `/resume`) are refused with a hint to give an argument. A host that runs with `collab.autoStart: control` also lists `/new`, `/resume <session>` and `/fork` (`CollabCommand.switchesSession`): the host replaces its session as the TUI does, the room ends with a `bye` (see above), and a guest follows to the successor room only if it can ask for the new link, as the web app does through a paired companion; so the web app lists them only with a companion, and a host without `control` auto-start refuses them. They are also refused while the host is answering, compacting, switching, or in plan, goal or vibe mode, `/resume` reaches only sessions of the host's folder (`CollabCommand.choices` lists the recent ones for the app's suggestions), and `/fork` is the plain whole-session fork, never the pane or window variants. `/clear`, `/shake`, `/handoff`, `/fresh`, `/branch`, `/tree`, `/delete` and every other command are refused with an error, and text that only starts with a slash stays an ordinary prompt.

Markdown commands and prompt templates a guest runs may contain ``!`cmd` `` snippets, which the host runs under its own `commands.shellExpansion` gate (default `user`: only the host user's own command directories, never a project's or an installed plugin's) and `commands.shellTimeoutMs`; the guest's arguments reach the snippet as environment variables, never as shell source, and the host sees a notice naming what ran. See [Slash command internals](./slash-command-internals.md#shell-output-in-commands).

A host that advertises the `profiles` feature lets writers switch the session's [agent profile](./profiles.md): `welcome.profiles` lists `{ name, description? }` (writers only), `state.profile` names the active one, and `session-cmd` `profile` with the name as `arg` switches it (queued until the turn ends while the host is busy; refused for view-only guests, for unknown names, and while the host is in plan, goal or vibe mode). A guest can only move to a profile at least as strict as the active one: a switch that loosens the approval mode, enables more tools, or widens approval, path or LSP permissions is refused with an `error` explaining why, while the host can still switch to any profile from its own TUI. The web app shows the profile as a pill next to the model pills.

A host that advertises the `usage-limits` feature reports the subscription limits of its providers and what a usage limit does to the session (the same reports `/usage` shows, read with `AgentSession.fetchUsageReports`):

- Writers receive a `usage-limits` frame `{ windows, fetchedAt }` after `welcome`, again whenever a read changes the windows, and as the targeted reply to `session-cmd` `usage-limits`. Each window is `{ provider, account?, windowId?, label, usedFraction?, resetsAt?, status? }` (`usedFraction` 0 to 1, above 1 for overage; `resetsAt` epoch ms; `status` `ok`, `warning`, `exhausted` or `unknown`), one per limit with an amount or a reset time, at most 60. The host reads the providers at most once a minute for a plain `usage-limits` request (`arg` `refresh` skips that cache), when a turn fails on the limit, and every 5 minutes while a writer is connected. View-only guests get no windows because they carry account identities.
- `state.limited` is present only while the session is limited: `{ kind, provider?, until?, resumeAt? }`. `kind` is `blocked` (the last turn failed on the account's usage limit, and no later turn has worked), `wrap-up` or `low-priority` (a Claude subscription serving requests past its limit, see `providers.anthropic.slowMode`). `until` (epoch ms) is the reset: from the provider's error text when it states one, otherwise from the usage windows (for a provider whose every account has an exhausted window, the earliest moment one of them is free again); it is absent when neither says.
- `session-cmd` `resume-at-reset` (writers) arms the host to send `continue` as a prompt, authored "usage limit reset", 30 seconds after `state.limited.until`; `state.limited.resumeAt` shows when. `resume-cancel` disarms it. Arming is refused when the session is not limited, the reset is unknown or already past. The host checks the wall clock every 30 seconds, so a machine that slept still sends it on waking. It skips the prompt when the session is working again by then, drops the plan when a later turn works before the reset (a `blocked` session whose limit was lifted another way), and, when the `continue` itself fails on the limit, re-arms up to three times. The timer lives in the omp process: it needs the session hosted (collab on, as for companion-started sessions) and does not survive the process exiting. A session that is no longer running is resumed by a scheduled run instead (the companion's *Schedules* with mode *resume*).

The web app shows the windows as bars with the reset clock time and a countdown under *Usage* → *Limits*, and a bar above the message box while the session is limited: "Limited on anthropic until 14:30 · in 2h 05m" with *Resume at reset* (or *Cancel resume* once armed), *Snooze until reset* (the session list's snooze) and *Switch model*, which opens the windows and the host's model list. The mock host (`bun run mock-host --limited [seconds]`) fakes the windows and a limited session whose reset is that many seconds away (default 90 minutes); switching it to a non-Claude model lifts the limit.

The companion also reads omp's stats database (`~/.omp/stats.db`, as `omp stats` does) for two screens. *Usage* shows cost, tokens, requests, and cache hit rate across all your sessions for 24 hours to all time, as a bar chart plus the top models and projects by spend. *All sessions* lists every past and live session grouped by project, with *Open*, *Share*, or *Resume* on each. Before answering, the companion ingests new session files into the database, at most once a minute; the first request after a long gap can take a while.

Set `collab.webUrl` when the browser UI is hosted separately from the websocket relay. When empty, `/collab` derives `http(s)://host[:port]` from `collab.relayUrl`; explicit web UI URLs must use `https://` except for localhost/loopback `http://` development origins, and cannot contain a query string or fragment. The generated browser URL still carries the relay-specific collab link in the fragment.

### Hiding messages

A message, or a run of them, can be hidden from the chat. Hiding changes only what this app shows: the agent's context, the session file and what other guests see are untouched, so the agent still remembers everything it was told and did. Nothing is sent to the host and nothing is deleted; showing a hidden message again brings it back exactly as it was.

- **What can be hidden.** A prompt, a reply, a tool run, or in chat view a folded group of tool runs (all of its calls). From a message's actions on desktop, or press and hold on a phone, choose *Hide*. A prompt also offers *Hide this exchange*: the prompt and everything up to the next prompt. In select mode (a click on a block's gutter, ⌘/Ctrl-click to add, Shift-click for a range on desktop; *Select* in a phone's long-press menu) the bar offers *Hide N messages*. A message that is still streaming, a tool that is still running and a pending approval or question cannot be hidden until they are done.
- **What shows.** A run of hidden messages is replaced by one thin marker, "N hidden messages" with *Show*. *Show* reveals the run in place, dimmed, with *Unhide* and *Hide again*; neighbouring hidden messages share one marker. Each hide offers one *Undo* for a few seconds. ⋯ → *Show hidden messages* shows every hidden message in place until you turn it off (it is not remembered). It works the same in chat view and in the full transcript.
- **Copy, export and share.** The session's *Copy*, *Download* and *Share* in the ⋯ sheet, and *Copy reply* and *Share* under a turn, leave out hidden messages, unless ⋯ → *Show hidden messages* is on. Hiding is meant to keep something out of what you hand on, so the default is that it stays out; the temporary *Show* on one marker does not change an export. Copying a selection copies the blocks you picked, including ones you revealed. Read-aloud, *Find in session* and the command palette still see hidden messages.
- **Ids.** A prompt is its session entry id, a reply is `<entry id>:<index of its block>`, a tool run is its tool call id. They are stable across reconnects, resumes, compaction and `/clear` (omp writes them in the session file); they are unique only within a session, so the hidden messages are kept per session id. A fork or a rollover is a new session and starts with nothing hidden. In chat view a folded group of tool runs is hidden only while all of its calls are, so a group that grows with a new call shows again.
- **Storage and sync.** The hidden messages are kept in the browser (`omp.collab.hidden`: `{ v: 1, sessions: { [sessionId]: { entries: { [id]: { at, hidden } } } } }`, at most 5000 entries per session and 200 sessions), so they also work without a companion. A companion that keeps them advertises `canHideMessages` in its `hosts` frame (optional, as is `hiddenRev`, a counter that moves whenever any device changed something) and stores them in `<config>/agent/collab-companion-hidden.json` (mode `0600`), so every device shows the same chat. The app sends `hidden-messages` (`{ reqId, sessionId, doc? }`) and is answered with `hidden-messages` (`{ reqId, sessionId, doc, rev }`); an error reply carries the `error`. The companion merges the device's document into its own message by message, the larger `at` (the time of the action) winning, and the same `at` leaving the message hidden, so two devices that hide and unhide at once converge. An unhide is kept as `hidden: false` so it reaches the other devices, and is dropped after 30 days. The app syncs on opening a session, on reconnect, when `hiddenRev` moves and after each change, and falls back to the browser's copy when the computer cannot be reached.

### Deleting sessions

*Settle* only moves a row and *End sessions when they settle* only stops the omp process; neither removes the conversation. *Delete…* does. It is in a row's ⋯ menu (sidebar), in the session's ⋯ sheet and in *All sessions*; the Settled section has *Delete settled sessions…* with a count. A confirm dialog names what will go and asks nothing else, except for *Also remove its worktree* (below).

- **What goes.** The session's transcript (`<config>/agent/sessions/<project folder>/<timestamp>_<sessionId>.jsonl`) and the folder beside it that holds its subagents' transcripts and artifacts (the same name without `.jsonl`); the sidebar entry on every device (the companion's `collab-companion-sessionorg.json` takes the entry out and bumps `sessionOrgRev`, and a device that still has the entry merges that in, so the row is gone everywhere, along with the session's activity, settle and end-on-settle bookkeeping); its hidden-message marks (`collab-companion-hidden.json`); the companion's settle records for it (`collab-companion-settle.json`: the folder it remembered and the results that name it); its per-session pull request watch files (`<config>/run/pr-watch/watches/<sessionId>.json` and `inbox/<sessionId>/`); and the message-search cache of its transcript. It is gone from *All sessions* and from searching the history on every device.
- **What stays.** The worktree folder, unless *Also remove its worktree* is ticked. *Spend history*: the usage totals and charts still count what the session cost, because that money was spent; omp's own `stats.db` (and `history.db`) are omp's files and are never edited (the database only ever adds rows, so *All sessions* hides a row whose transcript is gone instead, which also covers a session after the trash has been emptied). That means the database still holds per-request numbers for the session, a session title and, in omp's stats tables, text of its prompts: deleting a session here removes the conversation, not every trace omp itself keeps (`omp gc` drops what omp archived). Quiz, spar and bake-off records that mention the session stay and keep working, but their *Show in session* is no longer offered (the session cannot be opened); high-stakes records stay; a schedule that resumes the session stays and will fail when it runs; the GitHub alert state (`collab-companion-prwatch.json`) is keyed by repository and pull request, not by session, and is untouched.
- **Undo and the trash.** Nothing is erased at once: the files move into `<config>/agent/collab-trash/<trashId>/` (mode `0700`, with a `manifest.json` of where they came from and of the companion's records), and the app shows an *Undo* toast for a few seconds, like settle does. *Undo* sends `session-restore`, which puts the files back where they were, and the sidebar entry, hidden marks and settle records with them (a settle that had already been handled is not run again). It refuses, and leaves everything in the trash, if something now occupies the place the transcript or its folder was (omp wrote a new one, or a folder was made there). The trash is emptied of what is older than 7 days when the companion starts and then daily; until then the files can be copied back by hand from the trash folder. A removed worktree is not in the trash and cannot be undone; the dialog says so.
- **The worktree.** *Also remove its worktree* only appears when the companion made the worktree for the session (it recorded it when the session was started or ended, in the folders the companion makes worktrees in; the folder is read from that record, never from the session file). It runs the same removal as the worktree's own *Remove worktree*: `git worktree remove` without force, from the main checkout, refused when a session is running in it or it has uncommitted changes, so a dirty worktree is reported ("The worktree has uncommitted changes") and kept, while the session is deleted all the same. The branch stays. A worktree another session also worked in, or one a settle cleanup command is running in, is kept as well, which lets a batch remove a worktree together with all the sessions that used it.
- **Running sessions.** A session the companion started (its omp runs in the companion's `omp-<id>` tmux session) is ended first, as *End* does, then deleted once it has left the listing and nothing has its transcript open (it waits up to 15 seconds, then refuses). A session started by hand in a terminal is refused: "It is running in a terminal. End it there first.", as is one another omp has open. The Personal agent's session is refused and has no Delete.
- **Only omp sessions.** Sessions run by another vendor's agent (Claude Code, Codex…) keep their transcripts in that agent's own folders, which the companion does not manage: their rows have no Delete in this version. Rooms and sessions on a computer whose companion does not advertise `canDeleteSessions` have none either.
- **Safety.** The device sends session ids (`^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`, at most 200 per request), never a path. The companion finds the files itself, by listing its own sessions folder, resolves real paths and refuses anything that is not a plain file or folder where omp keeps it: a project folder, transcript or artifacts folder that is a link, a session found in more than one folder, a folder that overlaps the Personal agent's sessions. Nothing from a session file (its `cwd`, any id inside it) becomes a path, links inside a session's own artifacts are moved as links and never followed, and the trash is read back through the same checks (the manifest's names must be plain names, so a forged one cannot move a file out of the sessions folder). Deleting, settling and ending the same session run one at a time.
- **Wire.** A companion advertises `canDeleteSessions` (optional) in its `hosts` frame; an older one does not, and the app then offers no Delete. `session-delete-plan` (`{ reqId, sessionIds }` → `{ plans: [{ sessionId, refused?, running?, worktree? }] }`) tells the dialog what a deletion would meet (a refusal reason, that the session is running and will be ended, the worktree that could go with it) without changing anything. `session-delete` (`{ reqId, sessionIds, removeWorktree? }` → `{ results }`) answers one result per session, in order: `deleted` with its `trashId` (and `worktree: "removed"`), `worktreeKept` with the `reason` (the session is deleted, its worktree is not) or `refused` with the `reason`. `session-restore` (`{ reqId, trashId }` → `{ sessionId }`) undoes one deletion; an error reply carries the `error`. All fields besides the request names are optional on the wire, so an app and a companion of different versions keep working.

### The message box

- **Queued follow-ups.** The *After this turn* chips above the box show the host's queued follow-ups. On a host with `queue-edit` each chip has buttons to edit it in place (Enter saves, Shift+Enter adds a line, Esc cancels), run it sooner or later (the chevrons) and send it into the running turn now (⚡). Without the feature, or for a read-only guest, only removing works. In Settings → *Messages* → *Enter key* a device chooses what Enter does while the agent works: *Steers* (the default: Enter sends into the running turn, Alt+Enter queues) or *Queues* (the other way round, and the two buttons swap).
- **Mentions.** `#` in the draft lists the open pull requests of the session's repository (read through the paired computer's `gh`, plus any pull request URL the conversation already linked), `@` lists other sessions of the paired computer (most recent first; this session is left out). Tab or a tap picks one and writes `#123` or `@session:abcd1234`; Enter picks only after ↑/↓ moved the highlight, so a message that merely contains `#` or `@` still sends, and `@src/app.ts` stays plain text. The send carries the picked references as `mentions` (host feature `mentions`, see above); typing a token by hand works once its list has loaded. Without a paired computer only pull requests the conversation linked are offered, and no sessions.
- **Stash.** ⌘S / Ctrl+S sets the draft aside and empties the box; the *Stash* button (archive icon, with a count) next to the attach button opens the list to stash the current draft, restore one (a draft already in the box is stashed in its place) or delete one. Stashed drafts are text only (attachments stay in the box), at most 20, kept on this device across sessions. The shortcut is remappable like the others (*Stash the draft in the message box*) and the palette lists it.
- **Recall.** ↑ in an empty box brings back the previous prompt of this session, ↑ again the one before, ↓ walks forward again and ends on the draft that was there. Prompts the host injected, repeats in a row and prompts over 20,000 characters are skipped, and the context block of a mention is removed. In a recalled multi-line prompt ↑/↓ move the caret until it reaches the first or last line's edge.
- **Large pastes.** Pasting more than 32 KiB (32,768 UTF-8 bytes) of text attaches it as a `pasted-text.txt` chip instead of filling the box; it follows the usual file rules (inline up to 256 KiB, uploaded through a paired computer beyond that). When no chip can take it (eight files already, or too large with no paired computer) the text is pasted as usual.

### The session top bar

The header of a session shows the sessions toggle, the session's name, the connection status and, at the right, a row of action buttons ending in ⋯. The buttons on by default are Settings, Find, Editor, Code map, Quizzes, GitHub, Agents, Sparring, Bake-off and Leave; Changes, Architecture, Map of what changed, Terminal, Preview, Run, Timeline, Usage and All sessions, which otherwise live only in the ⋯ sheet, are off until chosen. A button appears only when the session can do what it opens (for example Editor and Code map need the paired computer, GitHub a signed-in `gh`, Changes a changed file or a working tree). Settings → *Appearance* → *Top bar* chooses which of them show and in what order (a box and move-up / move-down buttons per button, *Reset top bar* for the default), per device, in `localStorage` under `omp.collab.top-bar`; a choice saved before a button was added never turns that button on. ⋯, and the session's name, always open the session sheet, which lists every action, and the command palette reaches them as well, so hiding a button hides only the shortcut. A phone's bar has room for four buttons: the first four of your shown buttons, not counting Settings, Quizzes, GitHub and Leave, which stay in ⋯ on a phone. By default that is Find, Editor, Code map and Agents.

### Moving and resizing the big sheets

On a window 901px wide or more with a mouse or trackpad as the main pointer, the big sheets (Quizzes, Sparring, Bake-off, GitHub, Code map, Changes, Usage, the Inbox, the session sheet that ⋯ opens, the editor, Settings and the other full-size or wide ones) can be moved and resized; the session behind stays dimmed and blocked, and Esc and the backdrop close the sheet as before. Until one has been moved or resized, a wide one opens centred, like Settings. Drag the title bar or the slim bar at the top of the sheet to move it (a press on a button or field in the title bar does nothing special), and drag any edge or corner to resize it. A sheet is never smaller than 420×320 and always stays inside the window, so its top bar is reachable. Double-click the bar to put the sheet back at its default size and place. From the keyboard, Tab to the bar (*Move or resize the window*): the arrow keys move the sheet by 16px, Shift+arrow resizes it from its bottom right corner and Home resets it. All the big sheets share one place and size per device, so switching between Quizzes, Sparring and the others keeps the window where you put it; it is stored in `localStorage` under `omp.collab.sheet-frame` as `{ "x", "y", "w", "h" }` in CSS pixels. Nothing is stored until you move or resize one, a malformed value is ignored, and a window too small for a saved frame shows it clamped while the saved size comes back with the room. Phones, tablets and touch screens keep the sheets as they were.

### Command palette and keybindings

⌘K / Ctrl+K (or ⋯ → *Search* in the session sheet on a phone) opens the command palette, which works from the message box too. It searches four kinds of rows, all in the browser:

- **Actions**: what the app can do (open the session sheet, find, changes, editor, code map, run, GitHub, usage, schedules, switch model or thinking level, theme, export, leave …). Entries need what they need: companion actions appear only with a paired computer, host features only when the host advertises them. Features register their own with `usePaletteEntries` (or `setPaletteEntries`) from `src/lib/palette.ts`; an entry has an `id`, a `title`, an optional `section`, `keywords`, `icon`, `searchOnly` (kept out of the empty list) and `shortcut` (a shortcut id whose live keys are shown), and a `run`.
- **Commands**: the host's slash commands from `welcome.commands` (`/name`, with its description and, when typing, explicit choices). Picking one puts it in the message box; after an existing draft it lands after a blank line, and the host treats the line as plain text, so edit it before sending.
- **Sessions**: live sessions on the paired computer (open), idle ones (shared first), recent rooms, and past sessions from the companion's `sessions` request (opens *All sessions* on them).
- **Messages**: this session's prompts and replies, and, on companions advertising `canSearch`, every session's through `session-search` (the same 250 ms-debounced search as *All sessions* → *Messages*, from two characters). A hit in the open session scrolls to the message.

Matching is fuzzy: every word of the query must match in order inside the title (consecutive letters and word starts score higher; `dkth` finds *Use the dark theme*) or as a whole substring of a keyword or description. Results are grouped, best group first; recently picked rows (kept in `omp.collab.palette.recent`, 12 at most) come first with an empty box and rank higher otherwise. A prefix narrows the search: `>` actions, `/` commands, `@` sessions, `#` messages (or tap a scope chip). ↑ / ↓ or Ctrl+N / Ctrl+P move, PageUp / PageDown jump, Enter runs, Esc closes.

Settings → *Keyboard* (also `?`) is the keybindings editor: click a shortcut's keys and press the new ones (Esc cancels). Overrides are stored per device in `localStorage` under `omp.collab.keybindings` as `{ "<shortcut id>": { "key", "mod"?, "shift"?, "alt"? } }`, read when the app loads and applied at once; a malformed entry or an unknown id is ignored. Two shortcuts with the same keys are flagged (both still fire in the order the app checks them), keys the browser keeps for itself (⌘/Ctrl+L, Q, T, W, N, R, digits, `[`, `]`) and a bare printable key on a shortcut that must work while typing are refused, each override has a reset, and *Reset all* clears the lot. Esc is fixed. The palette itself is the `palette` shortcut (default ⌘K / Ctrl+K); the sessions sidebar toggle moved to ⌘\ / Ctrl+\ (`sidebar`) to free ⌘K.

### Local relay for the web app on the host's computer

Set `collab.localRelayUrl` to `ws://127.0.0.1:<port>` and omp serves each `/collab` room on that relay as well as on `collab.relayUrl`. The web app opened on the same computer then connects over loopback and skips the public relay's round trip; guests anywhere else keep using the public relay, and both see the same live session and can both prompt (a control link works on either). The two connections are independent: the host sends to the local relay only while a guest is on it, and a local relay that is down or killed never ends, delays, or degrades the public session. A local relay that comes up later is picked up automatically.

The local relay is carried by the link that tools on the host's computer receive — the registry entry behind `omp collab` and the companion's session list — as `?local=<host>:<port>` after the relay-explicit link (`my.omp.sh/r/<roomId>.<key>?local=127.0.0.1:7467`). Links printed by `/collab` stay public-only, so a link or QR code you share never names a loopback address. Older apps ignore the parameter; only `localhost`, `127.0.0.1`, and `[::1]` with an explicit port are honored, and anything else is dropped.

The companion starts such a relay for you at `ws://127.0.0.1:7467` (the next free port, then any free port, when that one is taken; `--no-local-relay` turns it off) and sets `collab.localRelayUrl` for the sessions it launches. For a session you start by hand, set the setting to `ws://127.0.0.1:7467` while the companion is running, or run `bun run relay --port 7467` yourself. `packages/collab-web/scripts/mock-host.ts --local-relay` exercises the whole path offline (`local off` / `local on` on its stdin stop and restart the local relay).

The app tries the local relay first only on a computer that can be the host's: touch devices (phones, tablets) always use the public relay. A local attempt that has not opened after 1.2 seconds, or that the room is not on, falls back to the public relay with no backoff, and a failed local relay is not tried again for 60 seconds, so a computer that is not the host's pays one short failed attempt a minute. The companion's relay refuses a guest for a room it does not hold before the WebSocket opens, only accepts a browser from the web app's own origin, and never lets a browser host a room. Payloads stay AES-GCM sealed end to end exactly as on the public relay.

Browser limit: the web app is served over `https://`, so the browser must allow an `https` page to open `ws://127.0.0.1`, and today that is the weak point. Measured: Chrome 150 gates the connection behind its Local Network Access check and, with no permission, fails it at once (`net::ERR_BLOCKED_BY_LOCAL_NETWORK_ACCESS_CHECKS`); headless Chrome cannot show the permission prompt, and granting the permission over the DevTools protocol did not lift the block, so whether a headed Chrome that the user allows connects is untested. Firefox treats loopback as potentially trustworthy for mixed content (from vendor documentation; untested here). Safari blocks a plain `ws://` connection from an `https` page even for loopback (WebKit bug 171934; untested here). In every blocked case the local attempt fails immediately and the app uses the public relay, so nothing is lost but the shortcut. A page served from `http://127.0.0.1` (not `https`) does connect to it in Chrome 150, as tested against the mock host.

### The app served by the companion

The companion also serves the web app itself on its local relay's port: open `http://127.0.0.1:7467` (the port the companion logs at startup; `omp companion --open` finds it for you) in a browser on the same computer. The page, its scripts, the room and the session sockets all stay on loopback, so this copy needs no Pages site, no public relay and no internet once loaded, raises no mixed-content or Local Network Access prompt (the page is `http://127.0.0.1`, a secure context and the same origin as the relay), still opens with the companion stopped (the service worker serves the app shell, which shows it is reconnecting), and installs as a PWA (scope `/`). The companion's own room is hosted on the local relay too; a page served that way tries the local relay first for the companion and for every session, and falls back to the public relay for a room the local one does not hold, so a session whose host was started without `collab.localRelayUrl` still opens. Device pairing and the end-to-end encryption are unchanged; a device is paired per origin, so a browser already paired on Pages pairs again here.

- `omp companion --open` opens `http://127.0.0.1:<port>/#pair:…&invite=…` with a fresh one-time invite in the default browser and prints the same link. It talks to the running companion through `<config>/agent/collab-companion-local.json` (pid and port, mode 0600) and starts a foreground companion when none runs. The installer opens this link at the end of an install, and still prints the Pages link and QR code for a phone.
- `omp companion --print-local-link` prints the link without opening it (exit 1 when no companion runs or it serves no app).
- `omp companion --no-local-app` serves the relay without the app (also implied by `--no-local-relay`). A relay without the app answers every non-room request with 404.
- The compiled `omp` carries the production build inside the binary (gzip-compressed text, read from the binary on demand) and serves it from memory, so the app version always matches the companion. Run from a source checkout, the companion builds the app in the background into `<config>/cache/collab-web/<source-hash>/` (the hash covers the app sources, the shared protocol packages, `bun.lock` and the Bun version): until a build is ready the page says it is building and reloads itself, a changed source tree builds a new copy while the previous one keeps being served, and only the last two builds are kept.
- **A page open across a rebuild.** The app is split into content-hashed chunks that load when a screen is first opened, so a page loaded from one build can ask for a chunk the host no longer has. A checkout's companion keeps the previous build and serves its hashed files (a script, a chunk or a stylesheet, never `index.html` or `sw.js`) when the current build lacks the name, newest first, so that page carries on; the compiled `omp` embeds one build only and Pages replaces its files on each deploy, so there the chunk is simply gone. In every case the page itself (`src/lib/stale-build.ts`) retries a failed chunk load once and then shows "The app was updated. Reload to continue." in the update bar with a *Reload* button. It never reloads on its own, so a draft in the message box is not lost to it. A page two rebuilds old reaches the same notice.

When to use which: the local copy for this computer (fastest, private, offline, no prompts); the Pages site, <https://ctrlc03.github.io/oh-my-pi/> by default or `collab.webUrl`, for a phone, a tablet, another computer, and for links and QR codes you share. Share links and the *Devices* QR code always point at `collab.webUrl`, never at loopback. *Settings → About* shows which copy a page is (*Served by: This computer* or *GitHub Pages*). Web Push needs a secure context, which `http://127.0.0.1` is; delivery still goes through the browser vendor's push service, so it needs the internet, as on Pages.

What the server does and refuses: only `GET`/`HEAD`, a `Host` of `127.0.0.1`, `localhost` or `[::1]` (anything else gets 403, which blocks DNS rebinding), no CORS headers, `Cross-Origin-Resource-Policy: same-origin`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, and a Content-Security-Policy that allows the app's own scripts (and the inline ones in `index.html`, by hash), `ws:` only to loopback, `wss:` anywhere (relays are user-configured) and no framing. Assets are looked up in a table, never joined onto a path, and a path with an encoded `/`, `\`, NUL or `..` gets 400. Unknown paths answer with the app only for a browser navigation; a missing script or image answers 404. Hashed assets are cached `immutable`; `index.html` and the service worker are `no-cache`. The local relay admits a browser only from the web app's own origins (Pages, `collab.webUrl`) and the two loopback origins of this port, and no HTTP route hands out an invite: a new one is issued only through the command line, the *Devices* screen, or a paired device.

The policy also lets fonts (only fonts) come from `https://esm.sh`: Excalidraw lists its CDN after the app's own copy as the second source of every font it registers, and Chrome reports a blocked source even when the first one loads. The app's copies under `excalidraw-assets/` are used; nothing is fetched from the CDN while they are present.

### Watching pull requests

A host that advertises `pr-watch` in `welcome.features` watches pull requests for its session and wakes the agent when CI fails or someone reviews (see [Watching pull requests](./pr-watch.md)). `state.prWatch` lists them: `{ key, repo, number, url, title, state, checks, conflict, review?, wakes, queued, error? }`. A writer sends `session-cmd` `pr-watch` (`arg`: a pull request URL, `owner/repo#N` or `#N`; empty watches the host's current branch's pull request) and `pr-unwatch` (`arg`: a `key`); a pull request that cannot be resolved answers with an `error`. The web client shows a *Pull requests* row in the session sheet with a status chip per pull request (state, checks, conflict, review, queued, wakes), an unwatch button and *Watch this PR*, and a *Watch this branch's pull request* entry in the command palette, all only for a writer on a host that advertises `pr-watch`. `scripts/mock-host.ts` plays a pull request whose test job fails, then passes after a push, gets a comment and merges, so the whole flow, including the wake, can be tried offline.

### Several computers

One device pairs with as many computers as it needs, each running its own companion: a laptop, a desktop, a server such as `moonstone`. The app keeps one connection to each, and a computer that is closed or unreachable only greys out its own group; sessions on the others keep running and stay reachable, and so does a session already open from them. Closing the laptop never touches sessions on the server. A computer whose companion stopped reads *Offline* beside its name (the relay reports its room gone) while the app keeps retrying, and is live again as soon as the companion is back; *Connecting…* means the relay itself is not answering.

- **Pair another computer** with its link: on that computer run `omp companion --pair` (link and QR code), then open the link, scan the QR code or paste it under *Add a computer* (connect screen, the sidebar once there are two, Settings → *Computers*). A computer already paired takes the new link's invite instead of appearing twice. Settings → *Computers* lists them and *Remove* signs this device out of one and forgets what the device kept for it.
- **Identity**: a computer is the room of its pairing link (the companion keeps one room for the life of its state file), so its id is the same on every device. `omp companion --rotate` makes a new room, so the rotated companion is a new computer: remove the old entry, which reads *not running*. The machine name shown is what the companion reports (`os.hostname()`); two with one name read `name` and `name (2)`.
- **Sessions are listed per computer**. The sidebar groups them under each computer (collapsible once there are two; sessions that no paired computer lists are under *Other sessions*), the all-sessions sheet combines them with a computer chip and a filter, and the inbox, schedules, usage and architecture maps cover every computer. An omp process id (`instanceId`) is only unique on its computer, so everything the app remembers for one carries the computer's id too.
- **Starting a session**: *Start session*, a schedule and the model comparison show a *Computer* picker once two are paired. It starts on the computer on screen, else the one used last, else the first that can; one that is offline or whose companion lacks the feature is shown with the reason and cannot be picked.
- **Notifications** subscribe per computer. A browser ties a push subscription to one server key and each companion has its own, so each computer subscribes through its own service worker registration (scope `push/<computer id>/`); turning notifications on for one computer subscribes the others when permission is already granted, and Settings → *Notifications* turns each off separately. A tap opens the session on the computer the push came from: the companion puts its room id in the push payload (`computer`, optional), and a push from a companion that predates it opens on the one computer that lists the session, or says so when two do. The app icon badge is the count of the computer that last pushed.
- **Storage** (`localStorage`): `omp.collab.computers` holds the list; per-computer data (recent rooms, dismissed inbox items, the session organisation `omp.collab.session-org.<computer id>`) is keyed by computer. A device paired before there could be several moves its one pairing into the list on first launch, with its rooms, dismissed items and organisation document.
- **The app served by the companion** adds the computers the same way. Its loopback relay serves only that computer's room; the others are reached through their own relays as before.

### Disk space

A session that sits idle without being settled keeps its worktree, and a Rust `target` or a `node_modules` in it keeps growing back every time the agent builds. The *Settle script* runs only when a session settles, so it never reaches a worktree that is left open for days: one such `target` filled a laptop's disk to 99% (89 GB), and the swapping that followed made omp sessions too slow to answer the companion, which then dropped them from the app. The **disk guard** watches free space instead of waiting for a settle. A companion that has it advertises `canDiskGuard` in its `hosts` frame; the app then shows a *Disk space* group in Settings → *Sessions*.

- **What it watches.** Every three minutes (`DISK_CHECK_INTERVAL_MS`) the companion reads the free space of the volume holding the worktree folder (and any other folder the worktree settings used before) and of the one holding the home folder (the same volume is one reading; each is warned about separately). Reading free space is a single `statfs`, so the interval only has to be shorter than a disk can fill; three minutes catches a build that fills it within the hour and costs nothing. The heavy work (listing and measuring build output) runs only while a volume is below the limit and auto-clean is on, and then at most once every ten minutes.
- **Settings** are kept by the companion in `<config>/agent/collab-companion-disk.json` (mode `0600`), beside the git settings but in their own file, together with the recent cleans and which volumes already warned: the limit (`limitGb`, a whole number from 1 to 10,000, default 40; gigabytes are decimal, as Finder shows them), *Clean build output automatically* (`autoClean`, default **off**) and *Leave worktrees alone that were used in the last* (`idleHours`, 1 to 720, default 6). The app reads and replaces them with `disk-guard` (`{ settings? }`, answered with `{ settings, volumes, limitBytes, marginBytes, cleans, checkedAt }`); a replacement with any invalid field is refused and nothing is stored.
- **Warning.** Dropping below the limit sends one push notification (tag `disk-low`; a tap opens Settings → *Sessions*, route `disk:space`) and shows the warning in the app: on the computer's card, beside the battery note, and in the *Disk space* group, with a bar per volume. It is sent once per drop: the volume is armed again only after it recovers to **limit plus a margin** (the larger of 2 GB and 10% of the limit), so free space hovering around the limit, or an auto-clean that lifts it a little, never repeats the notification. What was warned is saved before the push goes out, so a restart does not warn again. The `hosts` frame carries `disk` (`{ path, freeBytes, limitBytes }`, free space rounded down to 100 MB) only while a volume is low, so it does not re-broadcast on every write. A companion without the guard sends neither field, and the app shows nothing.
- **Auto-clean** (opt-in). With it on, while a volume holding worktrees is below the limit, the companion deletes rebuildable build output in worktrees *it made* (a linked worktree at `<worktree folder>/<repo>/<name>`), the biggest first, reading the real free space after each deletion and stopping once it is back above limit plus margin. A size scan that does not finish in time (30 s per folder, 2 minutes in all) counts as "may be the biggest": a scan that cannot finish is looking at something huge, or at a disk that is struggling.
- **What can be deleted** is rebuildable output only, and the list is short on purpose:
  - `target`, only where `Cargo.toml` sits beside it and cargo's own files are in it (`CACHEDIR.TAG`, `.rustc_info.json`, `debug` or `release`): it is the folder that grew to 89 GB, and `cargo build` recreates it.
  - `node_modules` and `.next`, only beside a `package.json`: reinstalled and rebuilt by the package manager and `next build`.
  - `dist` and `build`, only beside a `package.json` **and** only when git ignores them. Those names are also used for committed assets and hand-written output, so they count only when the repository says they are generated.
  - Never anything in which git tracks a file, never `.git`, never source, never a symlink, and never inside another build folder. The search reads at most 300 folders, two levels below the worktree (a monorepo's packages) and 20 folders per worktree. Caches such as `.cache`, `.turbo`, `__pycache__` or `.venv` are left alone: some are expensive or impossible to rebuild, and none is as large and as certain as the five above.
- **When a worktree is skipped.**
  - *Busy:* a session works in it (its host state is working, or it waits for an answer; an idle session does **not** make a worktree busy, which is the whole point), or a process of yours has it as its folder or as its running program's folder, or a build tool (cargo, rustc, node, bun, npm, pnpm, make, a compiler) holds a file open in it. Language servers (`rust-analyzer`, `gopls`, `tsserver`, `pyright`, `clangd`, anything named `*-language-server`) are ignored, since they sit in a project all day. `lsof` runs once for the folders and once for the build tools' open files, never `lsof +D`, which walks the tree. When the processes cannot be listed in time, every worktree counts as busy and nothing is deleted. A shell or an MCP server left in a worktree makes it busy too: close it, or use *Clean now*, which refuses busy worktrees as well.
  - *Recently used:* its newest sign of use, the later of the session's last activity (`collab-companion-sessionorg.json`), the worktree's last commit, checkout or staging, and the newest file in the build folders themselves (a build in progress), is within `idleHours`. Auto-clean skips it; *Clean now* may clean it, because you chose it.
  - *Sandboxed:* **not** skipped. The settle script skips a worktree a sandboxed session worked in, because a sandboxed agent can write files that a command would run (`package.json` scripts, a `Makefile`). The disk guard runs no repository code: it deletes folders it found itself with `rm -rf`, which never follows a symlink, and a sandboxed session that is working is busy anyway. Skipping those worktrees would exempt the sessions most likely to sit idle.
  - Everything is looked at again just before each deletion, so a worktree that became busy since the scan is left alone.
- **Safety.** A path is deleted only when, after resolving symlinks, it is one of the five names, a real folder (not a symlink), inside a linked worktree under the worktree folder (a main checkout, a clone, a submodule or a worktree made elsewhere is refused), not through `.git` or another build folder, and on the same volume as its parent. `..` and relative paths are refused outright, and a symlink inside the worktree that points out of it is neither followed when measuring nor when deleting. The app never sends a folder to delete: it names worktrees, which the companion matches against its own list and searches again. Scans and sizes are bounded (timeouts, `du -sk -x`, at most two folders measured at a time) and run in child processes, never on the companion's own loop.
- **Recent cleans.** Every clean is recorded (worktree, what was deleted, bytes freed, automatic or *Clean now*, the free space before, the time and any error; the newest 100), kept in the settings file and listed in the *Disk space* group.
- **Clean now** (`disk-scan`, then `disk-clean` with the picked worktrees) works with auto-clean off and with free space fine. The sheet lists each worktree that holds build output with its folders and sizes, how long it sat idle and, for the skipped ones, why; busy ones cannot be ticked, recent ones can. A scan answers `{ candidates, volumes, scannedAt }` and a clean `{ cleans, refused, volumes }`, where `refused` names every worktree that was not cleaned and why.
- **Suggested settle command.** The disk guard is the backstop; cleaning when a session settles is still the cheapest place to do it. In Settings → *Sessions* → *Git worktrees*, *When a worktree session settles, run*, set `rm -rf target node_modules`. It runs in the worktree, only for worktrees the companion made, and only for sessions that settle: a session that stays open and idle never triggers it, which is why the guard exists.
- **Mock.** `scripts/mock-companion.ts --disk on|off` (default on) serves a computer with 6.3 GB free, five canned worktrees (two cleanable, one a cargo build runs in, one used an hour ago, one whose size could not be measured) and two earlier cleans, from memory; settings are kept in a real file by the real parser.

## Personal agent

An opt-in, always-on agent that remembers and acts for its owner, run by the companion on one home computer under its own `personal` profile. It is off until you set it up from Settings → *Personal agent* ([Turning it on](./personal-agent.md#turning-it-on)); with Personal never set up, the companion writes nothing for it and starts no timer.

- **Capability.** The `hosts` frame carries `canPersonal` (tmux is available, so the app can offer *Set up*) and, while Personal is on, `personalRev` (the status revision); the Personal session's host row carries `personal: true`. The companion keeps that session alive on its host poll, which then runs without a device connected: it starts it when missing (resuming the profile's session), rolls it over to a fresh session daily with a handoff note, and never lists it for settling, auto-settle or end-on-settle.
- **Requests** (`personal-*`, answered by `reqId`; writes need a paired device): `personal-status`, `-setup`, `-enable`, `-disable`, `-control` (`start`/`stop`/`restart`), `-events` (the event log, newest first, `before`/`limit`), and the settings, memory, About-you, proposal, digest, inbox and answer requests listed in [Contracts](./personal-agent.md#contracts). A write before setup answers `Set up the Personal agent first`. Every change broadcasts `personal-changed` `{ what, rev }`.
- **Schedules.** A schedule with `deliverTo: "personal"` starts no process: when due, its prompt reaches the live session as an event (owner trust when made in the app, external when the agent made it). The companion refuses one while Personal is off.
- **`POST /event`.** On the companion's loopback server, with the token in the profile's `collab-companion-personal-ipc.json` (a separate token from the schedule channel, 404 until Personal is on, no `Origin`, 64 KB, 30 events a minute per source): local scripts hand the agent news as an external event. `POST /personal` is the session's own channel for `notify_owner`, its hello and delivery receipts.
- **Origin.** The host of a Personal session (`personal.enabled`) stamps `origin: "owner"` in the `details` of the `collab-prompt` messages it injects (`CollabPromptDetails.origin`, also for the resume-at-reset `continue`): only the owner's paired devices hold a write link, so every writer is the owner. A host that does not stamp it (every session without Personal) leaves `origin` out, and readers treat a missing one as `owner`. A Personal session also publishes no read-only link through the registry and `/collab` refuses to start, view or print a link (`personal.allowShareLinks` lifts this); `/collab status` omits the link, and `list` and `stop` still work.
- **Files.** Everything is under `<config root>/profiles/personal/` (config, About you, sessions, memory, backups) and `<config root>/run/personal/` (the event file channel and the session's heartbeat). Turning it off keeps all of it.

### Personal agent in the app

The app offers Personal only to a computer whose `hosts` frame says `canPersonal`, and renders nothing for it (no request, no sidebar row, no Settings section) until a computer can host it or one already does. The home computer is the first one whose `personal-status` says it is set up, preferring one that is on; a second set-up computer is listed as a warning, and *Set up* is refused on another computer while a home exists. The pick is remembered on the device (`omp.collab.personal-home`) so a home that is offline shows *Home computer is offline* instead of vanishing.

- **Sidebar.** On the home computer's group, above the sessions, a pinned *Personal* entry shows its run state, a badge for what waits for the owner (questions, pending proposals, unread digests), *Start* while no session is up, and a button for Settings. It opens the live Personal session's thread (the host row carrying `personal: true`), and a row with that mark is left out of the session lists, the fan-out groups and the start screen's lists, so it is never listed twice and has no settle, end, archive or drag. Other computers' groups, once there are two, say where Personal lives. Turned off, the entry is hidden.
- **Settings → *Personal agent*.** A lazily loaded section (its code stays out of the app's first load): a setup screen (pick the home computer, an optional first About-you draft), then *Agent* (login checklist with `omp --profile personal login`, run state, start/stop/restart, spend meters, backups, nightly review, turn off/on), *Memory* (search, origin filters, retract, pin, earlier versions, export), *About you* (edit, history with diffs), *Activity* (proposals, digests, events) and *Settings* (limits, review, rollover, backups folder, sources).
- **Inbox.** The sheet merges Personal items with the sessions that wait: open questions and pending proposals first, then newest first. A question is answered with its option chips or free text, a proposal is accepted, edited or rejected in place, a digest is read, an alert or note is dismissed. The Personal session's own "needs input" is not listed as a session; the same question arrives as a Personal item. The Inbox button's badge adds the Personal count.
- **Routes.** Personal's push routes (`personal`, `personal/inbox`, `personal/memory`, `personal/about`, `personal/settings`) have no `:`; the service worker and the app's route parser accept them besides the usual `kind:id` form.
- **Mock.** `scripts/mock-companion.ts --personal fresh|enabled --personal-login ready|missing` serves every `personal-*` request from memory (`scripts/mock-personal.ts`).

## Diagrams

The web client draws diagrams client-side; nothing about them crosses the wire.

- **In replies.** A closed ` ```mermaid ` fence is drawn as a diagram, and so is an ` ```excalidraw ` fence or a ` ```json ` block holding an Excalidraw scene (read-only). Each figure has a *Source* toggle and *Open*. Streaming replies stay plain code until the fence closes, a diagram that does not parse falls back to its code block with a one-line error, and the drawing follows the light/dark theme (it re-renders when the theme switches). Mermaid runs with `securityLevel: "strict"` (no HTML labels or click handlers from agent text), and every rendered SVG is checked for active content before it enters the page. Scenes from untrusted JSON go through an allow-list validator (`src/lib/excalidraw-scene.ts`): unknown or embed elements are dropped, malformed numbers, colors and ids reject the scene, and only raster images are kept.
- **Viewer.** *Open* shows the diagram full screen with pan/zoom (wheel, drag, pinch) and *Copy source*, *Download SVG* and *Download PNG*. *Edit* opens it in the canvas.
- **Canvas.** An Excalidraw canvas (loaded on demand). A Mermaid diagram is converted to editable shapes with `@excalidraw/mermaid-to-excalidraw`; if the converter cannot handle it, the rendered SVG is placed as an image with the source text beside it. *Send to agent* (*Done* for a sketch) attaches a PNG and the scene as a `.excalidraw` text attachment (compacted: deleted elements, rendering noise and image data dropped, numbers rounded, strokes thinned) and adds a short note explaining both to the message box, through the composer's normal image and file attachment paths.
- **Sketch.** The pen button next to the attach button (and *Sketch a drawing* in ⌘K) opens a blank canvas; it is full screen with safe-area padding on a phone. Read-only links do not offer it.
- **Repository files.** `.excalidraw` files open in the canvas, and `.mmd` / `.mermaid` files in a source editor with a live preview, wherever the app opens a file path (tool cards, working tree, code map, IDE *Canvas* button) on a paired computer. *Save* writes through the companion's file write (`file-write`, with the version check) and is offered only to writers on a companion that can edit; otherwise the sheet says so and offers downloads only.
- **Code map.** *Open in canvas* on the Focus card and the Flow bar exports the graph (nodes and edges, language colors from the tokens) as an editable scene.
- **Offline and assets.** Mermaid and Excalidraw are separate lazy chunks; the entry bundle does not import them (`test/diagram-lazy.test.ts` checks this against a real bundle). Excalidraw's stylesheet and fonts are copied to `dist/excalidraw-assets/` by `scripts/build-assets.ts` and loaded from there, never from a CDN, in a built app (the `bun ./index.html` dev server does not carry them, so Excalidraw falls back to its CDN there). The service worker does not precache these several megabytes; it caches each one the first time it is fetched, so diagrams work offline after first use. Only the build's own files are cached this way: query-less `.js` / `.css` / `.woff2` files at the site root and everything under `excalidraw-assets/`, whole `200` answers only; any other request passes through untouched.
- **Agent guidance.** The host adds no prompt text for this; an agent only needs to write a fenced ` ```mermaid ` or ` ```excalidraw ` block.

## Architecture maps

An architecture map is a set of layered diagrams of a repository at one commit: the whole system, then one diagram per major component, then packages, folders, files and symbols, each diagram opening into the next. Every arrow cites the code behind it as `path@line@token`, and the viewer shows the cited lines. A diff map marks nodes, edges and symbols *added*, *modified* or *removed*; it is made for a branch or pull request against its base, or for `@worktree` against `@default`, which is "what the agent just changed". The format and requests are `@oh-my-pi/pi-wire/blueprint`; the companion advertises `canBlueprint` and answers `blueprint-list`, `-create`, `-get`, `-excerpt`, `-delete` and `-refs`, and pushes `blueprint-changed` to every paired device.

- **How a map is made** (`scripts/companion-blueprint*.ts`). The target is resolved to commits (a branch, tag or commit; `pr/<n>`, fetched into a private ref; `@worktree`, a snapshot commit built with a temporary copy of the index, so the real index, files and branches are untouched). The commits are checked out as detached worktrees under `<config>/cache/blueprints/work` and indexed with omp's code index (the dependency graph, symbols and `flow` calls), with no model: that gives the lowest levels and the overview of every package. An omp session the companion starts then reads the code and writes the top diagrams (system, one per component) as JSON to one result file. Last, every citation is checked against the commit: a correct one is kept, one on the wrong line moves to the line where its token is, and one that cites nothing real is dropped, together with any arrow left without a citation. Checkouts and the session are removed afterwards.
- **Where it lives.** `<config>/agent/blueprints/` (`index.json` and one `<id>.json` per map; the folder is 0700 and the files 0600), never in the repository. A map keeps its commits reachable under private refs `refs/omp-blueprint/maps/<id>/…` (which git tools do not list) so excerpts keep working; *Delete* removes the map and its refs. Nothing is committed, pushed or written to the repository.
- **Privacy and permissions.** The agent session is an ordinary omp session started through the companion, so it is listed, can be watched and stopped from the app, and obeys its spending limit (`maxCostUsd`, default 3 USD; `--max-cost`). It runs with a read-only tool set (`read`, `grep`, `glob`, `ast_grep`, `trace`, `flow` and `write`), no shell, an overlay that lets `write` touch only its result file, and, on macOS, the same `sandbox-exec` profile as sandboxed sessions. On other platforms the tool allowlist and the overlay's path rules are the only barrier. Its code is sent to the model provider like any session's; the code-index levels never leave the computer except to the paired devices.
- **Cost and time.** The index levels take seconds to a minute (about 25 s for a 9,700-file repository); the agent step is the model's: expect minutes and a few USD at most, capped by the limit. Two maps are generated at a time; the rest wait.
- **Limits.** A map holds at most 600 index diagrams (80 of them file diagrams, only for files with at least two symbols), and a diagram at most 80 nodes; the entries a folder's diagram has no room for open in a "N more" diagram. Large maps are big (a 9,700-file repository gives about 6 MB of JSON, 0.5 MB compressed). When the agent step fails (no tmux, spending limit, no usable output) the map is stored with the index levels only and a warning says why. `stale` marks a branch or tag that moved on since the map was made; *refresh* makes a new map at the new tip, asking the agent to keep what is still right. A companion that stops mid-run marks the map failed ("interrupted") and ends its session when it next starts.
- **In the app** (`src/components/architecture/`, fetched on first open and gated on `canBlueprint`). *Architecture* on the computer card and in ⋯, *Architecture map* and *Map this session's changes* in the command palette, *Map this PR* in the GitHub sheet, and *Map what changed* in ⋯ (a diff map of `@worktree` against `@default`) open the sheet: the list of maps with progress for a running one (updated by the `blueprint-changed` push), a *Stale* badge with *Update*, cost and *Delete*, and a form (repository folder, branch, tag, commit or PR, optional base, cost limit). A map opens in a viewer: a deterministic layered layout drawn as SVG (columns by dependency order, own code, about 4 KB; no layout library), where a node with a child diagram opens into it with a zoom transition, breadcrumbs go back up, and pan and zoom, search (over every diagram, built once, debounced) and keyboard use (Tab, Enter, `/`, arrows, Esc) work throughout. Only the diagram on screen is laid out. An edge or node opens a panel with the cited code (`blueprint-excerpt`, at most 200 refs a request) and the cited line highlighted; with a matching checkout it also opens the file in the editor. A diff map colours nodes and edges added, modified or removed (never by colour alone), with a legend, a *Show only changes* filter and the changed diagrams marked in the breadcrumbs. The cited code opens up like a quiz's (*More of the code*, under *Quiz me*).
- **Export as one HTML file.** *Export* in the viewer downloads a single page that works offline from `file://` (the viewer script and styles are inlined; the page is generated in the browser, nothing leaves the device). It carries the code of the agent's diagrams by default; the folder, file and symbol diagrams keep their structure and show `path:line` with "code not included in this export". *All the code* adds every citation: the file's lines are deduplicated, overlapping ranges merged, the size is estimated before the download, and the reads go in batches of 200 with progress. Syntax colours are added only up to 20,000 lines. The viewer script is built by `bun run build` (`scripts/build-architecture-standalone.ts`) into `dist/architecture-assets/`, so *Export* needs a built app, not the dev server. The mock companion (`bun scripts/mock-companion.ts`) serves a fixture repository, and `--blueprint-sample map.json --blueprint-source <checkout>` serves a real map.

## Quiz me

*Quiz me* tests whether you understood a set of code changes, in the style of a tutor walking you through a pull request stack: one question at a time with the cited code beside it, you answer in your own words, and you get a verdict and an explanation with real code. At the end there is a score and the topics to revisit. The wire contract is `@oh-my-pi/pi-wire/quiz` (`quiz-list`, `-create`, `-get`, `-answer`, `-retry`, `-excerpt`, `-delete`, `-stack`; the `quiz-changed` push; the `canQuiz` capability, which needs tmux like the other sessions the companion starts).

- **What it quizzes.** A session's changes (*New quiz* in the session's quiz list, which the graduation-cap button at the top right of the session opens, or ⋯ → *Quizzes* on a phone; also *Quiz me* in the Changes sheet and the command palette): the session's worktree or branch against the default branch (`@worktree` against `@default`), with the session's conversation attached. Or any pull request in the GitHub sheet (*Quiz me*): when the PR is part of a stack (found from the PR branches, else from a stack list in the PR description, read-only through `gh`), the whole stack is offered, one part per PR, bottom first, each shown against the PR below it.
- **Choosing what to quiz.** The new-quiz form asks *What to quiz*: *This session's changes* (only where there is a session to take them from; it alone has the *Ask about why things were done* option), *A branch* (the branch against the default branch, `ref` = the branch, `base` = `@default`) or *A pull request* (the same stack offer as from the GitHub sheet). Branches and open pull requests come from the `blueprint-refs` request, which the new-map form uses too, with a filter box; when a computer cannot list them, a branch name or a pull request number is typed instead.
- **Quizzing on a session's topic, design and implementation** (the `canQuizTopic` capability, which follows `canQuiz`; an older companion does not send it and the app then shows only the quiz of changes: no *This session's topic* choice, no *Focus* control, no ⋯ entry). A quiz need not be about a diff. *This session's topic* (`QuizCreate.subject: "session"`, with `sessionId` and `cwd`, no `ref`, `base`, `pr` or `stack`) tests whether you understand what the session was about: the **concepts** (a session on statistics over fully homomorphic encryption can ask CKKS against BFV, the noise budget, why the arithmetic is approximate), the **design choices and trade-offs** made in it, and **how the implementation does it**. It also works for a *No project* session, which has no git repository. It starts from *Quiz me on this session* in the session's ⋯ menu (also on a phone, and for a No project session), or from the new-quiz form's *What to quiz*; a non-git folder offers only the topic there, since it has no changes to show. Sources, all three at once:
  - *The conversation* of the session, as for a quiz of changes but with each message marked by its entry id, so a question can cite it (below).
  - *The files in the folder*: design documents, notes, code. A git folder is read as its working tree, snapshotted into a commit held under a private ref (`@worktree`, no base) like a change quiz's states, so what is cited does not change afterwards. A folder that is not a repository is read when the quiz is made: its text files (not dotfiles, `node_modules`-like folders, binaries or symlinks that leave it; at most 3,000) are copied into the checkout the question writer reads, and the **whole file of every cited path** is stored in the quiz (`files` in the quiz document, up to about 1.5 MB in all), so the quiz keeps showing the text it was made from when the folder changes or goes away, and *Show 20 more lines* still works.
  - *General background knowledge of the topic*, including what the session never covered. Such a question (`background: true`) cites nothing, and the writer is told to write only well-established material, never to invent a fact, name, number or version-specific detail, and to leave out a question whose answer it is not sure of. It **must carry an `explanation`** (the facts the answer rests on) or it is skipped, and a multiple-choice one must have one definitively right choice. The app marks it with a small *Background* chip. Background questions are allowed only in a topic quiz and not in an *Implementation* one.
- **Focus.** Every quiz is created with a focus, chosen each time in the form's *Focus* control (`QuizCreate.focus`, default `mixed`): *Mixed* (understanding, design and implementation in about equal shares), *Understanding* (concepts; about half of the questions may be background), *Design* (choices and trade-offs, with the alternatives the conversation weighed), or *Implementation* (how the code does it: control flow, data flow, ordering). *Implementation* needs code: for a topic quiz on a folder with none (`quiz-folder` says `code: false`: no file with a source-code extension) it is disabled with "This folder has no code to ask about.", and the companion refuses it ("Implementation questions need code, and this folder has none."). Focus applies to a quiz of changes too, where it changes the weight of the questions, and *Understanding* and *Design* then also let a question cite the conversation. It is stored on the quiz (`focus`, with `about: "changes" | "session"`; both optional, so an older quiz has neither and reads as a quiz of changes) and shown as a small tag in the list. `quiz-folder` `{ cwd }` → `{ folder: { git, code, files, name } }` tells the form whether the folder is a repository, has code and how many files it offers.
- **Citations in a topic quiz, and how each is checked.** A question has `refs` (code or folder lines, `path@line@token`, may now be empty), `session` (messages of the conversation) or `background`. It is kept only when at least one citation holds or it is a valid background question; anything else is dropped, with a warning, as before. A file citation must match the snapshotted commit or the stored copy (kept, moved to the line the token is on, or dropped). A conversation citation `{ entry, quote }` must name a real message of the session file (the id in the `[#id]` marker of the brief, which is the transcript entry id), and the quote, at least 12 characters and cut at 300, must be found in the **whole** text of that message, whitespace aside; the stored citation carries the role (`user` or `assistant`) read from the entry, never the agent's claim. A question shows the quoted message with a *Show in session* link that jumps to it in the transcript when that session is open. Grading is unchanged (one small model call against the rubric); for a background question or one citing the conversation, the grader is also given the explanation and the cited passages, and is told that an answer that is vague, only restates the question or hedges across every possibility earns no credit. The answer key (rubric, explanation) stays with the companion until the question is answered.
- **How the questions are written** (`scripts/companion-quiz*.ts`). It reuses the architecture-map machinery: refs resolve to commits and are held under private refs (`companion-blueprint-git.ts`), a restricted read-only omp session in a throw-away checkout writes JSON to one result file (`companion-agent.ts`: the same tool allowlist, the overlay that allows `write` to that one file, the macOS sandbox where available, `--max-cost`), and every citation `path@line@token` is verified against the commit of its part (`companion-citations.ts`): kept, moved to the line the token is on, or dropped, and a question left without a citation is dropped with it. The session is given each part's numbered diff (changed lines carry the line number a citation uses), each PR's title and description, and, when a session is attached, a digest of its conversation (your prompts and the agent's replies, without tool output or thinking) so it can ask *why* things were done. It writes 3–5 conceptual questions per part (why, what happens, which, when, what would break), each with a short reminder of the idea, a topic, and a hidden rubric (key points and likely misconceptions), plus 1–2 multiple-choice questions with plausible distractors. The prompts are `scripts/companion-quiz-prompt.md` (questions) and `companion-quiz-grade-*.md` (grading).
- **Grading.** A multiple-choice answer is graded on the spot with no model. A free-text answer is graded by one small headless `omp -p` call (`--no-tools --no-session`, the cheap `smol` model role, `--mode json` so its cost is read) given the question, the hidden rubric, the cited code and your answer: *right* (1 point), *partly* (½) or *wrong* (0), a 2–6 sentence explanation with code and `file:line`, and optional verified citations. The rubric and the right choice never reach a device before you answer; the verdict then shows the key points.
- **Cost.** One spending limit per quiz covers writing and grading, default $1 (`maxCostUsd`): the writing session gets three quarters of it, grading the rest and whatever the writing left unspent, each grading call is capped at $0.25 and at what is left. When the limit is reached, open answers say so and are not recorded, and multiple-choice questions keep working. The list shows what each quiz has spent. A quiz is bounded by its limit, not by its size. When the writing session's file is not valid JSON or does not fit the format, a second session is told what was wrong and writes it again, on what the first left of the writing share (not when less than $0.05 is left); only a second rejected file fails the quiz.
- **Privacy.** The code of the changes, the pull request descriptions and, when attached, a digest of the session conversation go to the model you configure, as with any session. Quizzes, answers and attempts are stored privately under `<config>/agent/quizzes/` (0700/0600), never in the repository; deleting a quiz removes them and releases the commits it held.
- **Retry.** Every quiz keeps its attempts. *Retry* starts a new attempt over all questions or only the ones you did not answer right; earlier attempts and their scores stay.
- **More of the code.** Each snippet shows 12 lines either side of the cited line in a box of limited height that opens scrolled to it, with *Show 20 more lines* above and below (repeatable, up to the whole file); the lines are read from git at the same commit and side as the snippet, a *before* snippet included, and `@design` citations of a spar from the stored document, through the optional `from`/`to` of a `quiz-excerpt` ref (`spar-excerpt`, `bakeoff-excerpt` and `blueprint-excerpt` take the same), which the companion cuts to the file and to at most 2,000 lines, at most 20 ranged refs a request. The buttons appear only when the reply carries `total` (the file's line count), so an older companion shows none; the widened snippet is kept while the quiz stays open.
- **In the app** (`src/components/quiz/`, fetched on first open and gated on `canQuiz`): the list of quizzes with progress (a session lists its repository's quizzes; the start screen's *Quizzes* lists every repository's), one-question-at-a-time screens, the summary (score, per-part scores, topics to revisit) and a form for a new quiz, whose model is picked from the models the computer can run (the `fanout-models` list; a text field when the computer cannot list them).
- **Topic quizzes in the app**: *This session's topic* and the *Focus* control in the new-quiz form (the choice is hidden when the computer lacks `canQuizTopic` or there is no session id), the Topic tag in the list, session quotes and the *Background* chip in the question view, and *Quiz me on this session* in ⋯. The mock companion (`scripts/mock-quiz.ts`, `fixture-topic.ts`; `mock-host.ts --topic` serves the matching FHE conversation) answers `quiz-folder` (a path with a `scratch` segment is a non-git folder with no code) and lists a topic quiz on statistics over encrypted data for the *No project* session.

## High-stakes sessions

A *high-stakes* session is a session mode in which **pushing and pull requests are blocked until you pass a quiz on the session's changes**. It is for work where a diff you did not understand must not leave the computer: the agent writes, you prove you read it, then the push goes. The quiz is the one from [Quiz me](#quiz-me); the wire contract is `@oh-my-pi/pi-wire/stakes` (`stakes-get`, `-set`, `-quiz`, `-settings`; the `canHighStakes` capability; `highStakes` on a host row; `stakes` on a `git-review` answer and on a quiz). A companion that predates it sends no `canHighStakes`, and the app then shows no toggle, no chip and no disabled buttons.

**The quiz is mostly about the changes, with some design and understanding.** The quiz that unlocks a push (`createForStakes`) stays a quiz of exactly the session's diff, and its brief now asks the question writer for about a quarter (25 %, `QUIZ_STAKES_TOPIC_SHARE`; at least one and never more than a third) **design and understanding** questions instead of mechanics: why this approach, what trade-off it makes, what idea it rests on. They stay grounded: each cites the changed code or a message of the session. A *delta* quiz (only what is new since the last pass) asks its mixed-in questions about the new changes only. The share is a request to the writer, not enforced after the fact. The pass rule, the pass mark, the scoring and the delta logic are unchanged: a pass is still one finished attempt at or above the mark over every question of that quiz.

**What is gated.** `git push` in any form (and `git send-pack`, `git http-push`, `git subtree push`, `git svn dcommit`), creating, merging or closing a pull request (`gh pr create|merge|close`, `hub pull-request`, `glab mr create|merge|close`), `gh api` calls that write pull requests, merges, refs, commits or file contents, and the app's own *Push*, *Create PR* and *Merge* buttons. Commits, tags, branch switches and everything else local stay free.

**The layers**, outermost first. Each is there because the one before it can be walked around:

1. **The agent's command gate** (`packages/coding-agent/src/high-stakes/`). The existing approval machinery decides every `bash`, `eval` and `github` call before it runs (the same `ToolApprovalDecision` the sandbox escalation and the eval-kernel gate use): a gated command in a session whose checkout is high stakes and not covered gets a `deny` decision, which no approval mode (not even `yolo`), saved grant or `allow` rule overrides. The refusal tells the agent to ask you to take the quiz; there is no tool, setting or message through which the agent could answer a quiz (answers come only from your device over the companion's room, which the agent has no part in). The classifier reads the shell command (not the raw string): `git -C x push`, `git -c k=v push`, `env X=1 git push`, `command git push`, `git push` after `&&`, `;`, `|` or in `$(…)`, `bash -c '…'`, `eval`, heredocs fed to a shell, `xargs`, aliases from the command line, `git config` or your git config (`git p`), `--no-verify` and `core.hooksPath` tricks, `gh`, `hub`, `glab`, `gh api` writes, and `curl` posts to the GitHub API. `eval` code and `github` tool operations (`pr_create`, `pr_push`) go through the same classifier.
2. **The sandbox** (existing, `sandbox.mode`). With the shell sandbox on, a command has no network until it is escalated (and an escalation is asked about, and refused for a gated command), `.git/hooks` and `.git/config` are read-only, and the companion's state files (`collab-companion-*` in the agent directory) cannot be read. This layer catches every git client; it only exists while the sandbox is on, so a high-stakes session is best run sandboxed.
3. **The pre-push hook** (`pre-push` in the repository's hooks folder, installed and kept in place by the companion while a session in that repository is high stakes). It runs in whatever process pushes (git, `gh`, an IDE, a script), reads the commits being pushed, and asks the companion whether the tree of each is covered. It fails closed: when the companion cannot be reached it falls back to the state file the companion keeps, and a tree that is not in it is refused. `--no-verify` skips a pre-push hook, which is why the command gate refuses `--no-verify` pushes and the sandbox (when on) keeps the hook read-only. A user's own `pre-push` hook is moved aside and still runs after ours. A repository that sets `core.hooksPath` is not touched (the status says the hook layer is unavailable).
4. **The companion's own endpoints.** `git-push`, `pr-create` and `pr-merge` (the app's buttons) refuse on the companion when the session is high stakes and the tree is not covered, whatever the app showed. The companion is the source of truth for pass state.
5. **The app.** *Push*, *Create PR* and *Merge* are disabled with "Pass the quiz to push" and a *Take the quiz* action that opens (or creates) the quiz for exactly the diff that is needed.

**Pass state** is kept by the companion in `<config>/agent/high-stakes.json` (0600, atomic writes): per session its mode and its *passes*, and the companion-wide pass mark. A pass is `{ tree, commit, diffId, quizId, attempt, points, total, at }`: the exact tree (the `git write-tree` of the quizzed state, the same for the working tree snapshot and the commit made from it) and a *diff id* (`git patch-id --verbatim` of the changes against the merge base with the default branch). The commit is held under a private ref so the next quiz can start from it. Passes survive restarts, turning the mode off and on again, and deleting the quiz.

**What a pass covers (staleness).** The subject checked on a push is the tree of the commit being pushed. It is *covered* when any of these holds, so commits that only re-record quizzed content never need a new quiz:

- its tree equals a passed tree (the same files, however many commits, amends or squashes made them);
- its diff id equals a passed diff id (a rebase onto a moved default branch re-applies the same changes);
- it has no changes against the default branch.

Otherwise the next quiz covers **only what is new**: the changes from the most recent passed tree to the current one (`needs: "delta"`), not the whole diff again; with no earlier pass it is the whole diff against the merge base with the default branch (`needs: "full"`). Passing a delta quiz adds the new tree to the covered set, so coverage only grows: pass $T_1$, change to $T_2$ and pass the delta $T_1 \to T_2$, and $T_1$, $T_2$ and anything with the same diff are all covered. A quiz that is failed (below the mark) changes nothing. Anything the agent edits after a pass makes the tree differ, and the push is refused again.

**The pass mark** is a companion-wide setting (Settings → *Sessions* → *High-stakes quizzes*), default 90 %, between 50 and 100: below 50 % a quiz mostly measures guessing, and the grading of open answers by a small model has noise that makes 100 % a gamble, so it is allowed but not the default. It is companion-wide, not per device, because the companion and the hook enforce it and cannot read a device's browser storage (the worktree settings are kept the same way); it is read when a quiz is graded, so a raised mark does not unpass an earlier pass. The score is compared exactly (`points × 100 ≥ mark × total`, a half point counts), never from the rounded percent shown, so 89.6 % does not pass a 90 % mark. A pass needs one finished attempt that asks all the quiz's questions (a retry of only the missed ones does not count).

**The mode** is chosen when the session is created (*Start session* → *High stakes*) and toggled on a session in the session menu. Turning it on needs nothing. Turning it **off** asks for an explicit confirmation in the app (the request must carry `confirmOff`), and is never silent: the session logs a visible marker ("High-stakes mode was turned off by <device>") in its transcript, and the companion logs it. The mode of a session that is not running is kept and applies when it resumes (the marker appears then).

**How the session learns its mode.** The companion publishes one small text file per checkout (`<agent dir>/collab-companion-stakes/<hash of the checkout path>`: mode, revision, pass mark and the covered trees) that the gate and the hook read, so neither needs the companion to be running; the session also watches it to write the marker. The hook asks the companion's loopback server (`POST /stakes/pre-push`, its own bearer token in `<agent dir>/collab-companion-stakes-ipc`) for the full decision, which includes the diff-id check.

**Residual risks.** This is a guard against an agent that works through the normal tools and against slips, not a lock against one that is set on getting around it:

- Command strings cannot be classified completely: an agent can build a command at run time (`$(printf …)`, a downloaded script, a binary that pushes by itself) or call the git protocol directly. The gate refuses what it can read and the hook and the sandbox are what catch the rest.
- The hook is a file in `.git/hooks`: with the sandbox off, an agent that can write the repository can delete or edit it, `git -c core.hooksPath=…` or `GIT_CONFIG_*` bypass it (the gate refuses those words in a push, but not a script that builds them). The companion puts the hook back every few seconds while the mode is on; a shell with the sandbox on cannot touch it.
- With the sandbox off the agent can read the state files and the hook's token. The token only answers "is this tree covered", and the state files are re-published by the companion, but deleting a file stops the gate (not the hook, which asks the companion first).
- The hook cannot catch `gh pr merge` or a PR created through the API (nothing is pushed); only the gate, the companion's endpoints and the sandbox's network block do.
- A session that is not under the default agent directory (another profile) is not gated; two sessions in one checkout share one decision (the stricter of the two).
- Pushing from a terminal outside the session is still checked by the hook (a human can pass the quiz, or turn the mode off).
- The mode, the passes and the mark live in the companion's file; anyone who can write your config directory can change them.
- Only the tree at the tip of a push (and of the app's HEAD) is checked, not the history under it: a branch whose tip tree was quizzed passes even if an intermediate commit introduced something that a later commit removed again. The quiz is about what ships, so this is deliberate.
- `git send-pack`, `git http-push` and `git svn dcommit` do not run the pre-push hook, so only the command gate (and the sandbox's network block) cover them.
- A push the hook runs for is only as good as the hook: a repository whose `core.hooksPath` points to another tool's hooks gets no hook, and the status says so; the gate and the companion's endpoints still apply there.
- The companion's decision for a checkout with several high-stakes sessions is the stricter of them (a tree must be covered for each).
- The gate refuses words that disable the hook in a push (`--no-verify`, `-c core.hooksPath=…`, `--config-env`, `GIT_CONFIG_*`, `HOME=`/`XDG_CONFIG_HOME=` on the command, `git config core.hooksPath`) even when the tree is covered; a script that builds them at run time is not seen.

## Design bake-off

A *bake-off* asks several models to each do better than a design or a change, then has a reviewer model that does not know who wrote what pick the best one. You give it the original (this session's changes, a branch, a pull request or a design document), the things that matter to you, two to four challenger models and a reviewer. The result is a ranked list with reasons, code the reasons cite, and, when you ask for it, a second opinion from the cheap `judge` role. Nothing is committed, pushed or opened as a pull request. The design is in [design-review.md](./design-review.md); the wire contract is `@oh-my-pi/pi-wire/bakeoff` (`bakeoff-list`, `-judge`, `-create`, `-get`, `-excerpt`, `-stop`, `-take`, `-review`, `-delete`; the `bakeoff-changed` push; the `canBakeoff` capability, which needs tmux like the other sessions the companion starts; implementation mode also needs fan-out).

- **Starting one.** *Bake off this change* in the Changes sheet, *Bake off this session's changes* or *Bake-offs of this repository* in the command palette, *Bake-off* in ⋯ → the session sheet, or the Bake-off button at the top right (on by default; Settings → *Appearance* → *Top bar* hides it). From a sparring session, *Bake off this* carries its subject over. The form asks:
  - *What to start from*: this session's changes, a branch, a pull request (a stack is offered as in the quiz form) or a design document (pasted, or a file of the repository).
  - *Design only* (each model writes a better design as a document) or *Implementation* (each model changes the code in its own worktree). An implementation can start from the original's code (the default) or from its base, solving the same problem fresh; starting from the base asks what the change should solve when nothing states it.
  - *What matters*: Simplicity, Performance, Fewer moving parts, Migration risk and Lines changed (implementation only), and your own words in a text box. Star the one that matters most. Measured facts (lines changed, a benchmark) count for what they are; the rest is the reviewer's judgement.
  - *Challengers* (2 to 4, from the same model list as *Compare models*), the *Reviewer*, *Second opinion* (use the judge model) and the *Spending limit*.
  - *Implementation only*: a test command and an optional benchmark, picked from the repository's runnable targets, so they are offered when you open the form from a session.
- **What you see.** Each entry (the original included) is a card labelled A to E, working, writing up, done or failed, in an order that has nothing to do with who is who. Models stay hidden behind the labels until you choose *Show models*. When all entries are in, the reviewer runs and then the second opinion. The result is a ranked list with, per entry, the reasons, strengths and weaknesses with the code they cite (a finding whose citations could not be checked against the code is dimmed and says so), the measured facts (files, lines added and removed, tests, benchmark), the per-metric scores and the cited write-up. It also says whether the reviewer and the second opinion agree; when they do not (*Split verdict*) both rankings are shown with the reason. The cited code opens up like a quiz's (*More of the code*, under *Quiz me*).
- **Taking one.** In implementation mode *Take this one* keeps that entry's worktree and branch through the same keep confirmation as *Compare models*, and you choose whether the other worktrees are removed; one whose tests fail while the original's pass needs an extra tap and says why. In design mode it marks the winner and offers *Copy design* (Markdown) and *Start a session from this design*. On any entry, *Spar with this entry* starts a sparring session on it, and for an implementation entry *Map this entry* makes an architecture map of its worktree against the base (a map costs up to a few USD, so only on request). *Review again* repeats the review and the second opinion when they failed, with the same entries (it costs again).
- **Taking it out.** A finished bake-off leaves the app two ways. The report needs nothing new from the companion; patches need `canBakeoffPatch`, and an older companion shows no patch buttons.
  - *The report*: *Copy report*, *Share* (where the browser can share) and *Download .md* put the whole result in one Markdown file: the title, subject and start point, the mode, what matters and the instructions you gave, each entry with its model (revealed, as with *Show models*, since judging is over), cost and measured facts, the ranking with the reviewer's reasons, what the reviewer found, the second opinion and how far to trust it, tests and benchmarks, what the reviewer could not tell, the cost, the notes of the run, up to 40 of the cited code excerpts as fenced blocks headed `path:line` (a block longer than any backtick run inside it, so code that contains a fence stays inside it), and, in design mode, every design's text. The app builds it from what it already shows (`bakeoff-get` and `bakeoff-excerpt`), so nothing private leaves the computer for it. It leaves out what the result view never shows: the reviewer's and the judge's models, the writer's, branch names, worktree paths, session ids and the repository's path. The Markdown is shared as text on a computer and as a file on a phone; where the browser refuses a file share, as Chrome on macOS does, it downloads instead.
  - *Patches* (implementation mode, needs `canBakeoffPatch`): each entry has *Download patch* and *Copy patch*, and the report row has *Download all patches*. A patch is `git diff --binary --full-index` of the bake-off's base against the entry's code, with `a/` and `b/` prefixes whatever your git config says, so `git apply` (or `git apply --check` first) takes it onto a checkout of the base, binary files included. *Download all patches* is one `.patch` file, the winner first, with a banner and one `# ===== Entry B … =====` line per entry; the entries are alternatives to one another, so you split the file and apply one. One file because the app has no zip helper, several downloads at once are blocked or asked about by browsers, and a phone's share sheet would open once per file. The request names the entry by its label (`bakeoff-patch {id, entry}`); the companion looks the commit up in the stored bake-off and never takes a path or a ref from the device.
  - *Where the code comes from.* When the entries were measured the companion snapshotted each entry's worktree into a commit it holds under a private ref (`refs/omp-blueprint/maps/<id>/…`, the same refs that keep the base). The patch is made from that commit, so it is the entry as it was judged, not what its worktree holds now, and it stays available after you take another entry, after the other worktrees are removed and after a worktree is deleted by hand. The refs are released when you delete the bake-off or it is pruned (the newest 20 are kept); after that, or when the commit no longer exists, the entry's patch buttons are disabled and say the code is no longer kept. An entry that made no code says so. The original's commit is the branch you started from. A patch over 5 MB (`BAKEOFF_MAX_PATCH_BYTES`) is refused with a message that says to take the entry and read its worktree; so is one that changes a file that is neither valid UTF-8 text nor binary to git, or that changes nothing.
- **A folder that is not a git repository** (needs `canBakeoffFolder`). A session without a project works in a scratch folder, and any folder may be a plain folder of notes. *Bake-off* opens there: the list answers for the folder (keyed by its real path, as quizzes are) and is empty when there are none. Only a *design* bake-off can start, from a design document, pasted or a text file of the folder; *Implementation*, a change, a branch and a pull request are hidden with a one-line note, since there are no commits or worktrees to work from, and the companion refuses them too. The challengers and the reviewer read a copy of the folder's text files (the same files a topic quiz reads, at most the same number), made once when the run starts; the files the result's citations name are stored with the bake-off (up to 1.5 million characters), so cited excerpts still open after the folder changes. *Take this one* there is *Copy design* and *Start a session from this design*; *Map this entry* and *Spar with this entry* need the repository and are hidden, and *Review again* is refused, since the folder is only read while the bake-off runs. An older computer shows a plain sentence instead of an error.
- **How the judging stays fair.** The reviewer and the judge see labels, never origins. The companion exports each entry's code with `git archive` into a folder with no `.git` (so no branch name such as `omp/bake-…` can be read), scrubs the write-ups of model names, provider names, branch names and the words "original" and "challenger", shuffles labels and presentation order with the bake-off's id as the seed, and quotes every entry as data the reviewer is told to distrust. One neutral writer model puts every implementation, and the original design, into the same template so format does not show who wrote it. Two reviewer passes (reverse order, new labels) are available. Style can still leak authorship, so when the reviewer's own model wrote an entry the result says the reviewer may favour it.
- **The second opinion.** The `judge` role (see [Judge role](./design-review.md#judge-role)) scores each entry per metric and compares entries in pairs, each pair in both orders; an answer that changes with the order counts as a tie, and a judge that contradicts itself on most pairs is ignored. A measured fact (lines changed, a benchmark) beats any opinion on its own metric, and a gap in the combined total larger than a fixed margin cannot be overturned by the judge. The form shows which judge would be used and whether it answered a test question: a usable judge is on by default; a judge that is unreachable, or one picked only because nothing was assigned (it may be an expensive default model), is off until you choose *Use it anyway (advisory)*; with none, the reviewer decides alone. When the judge fails during a run the bake-off still finishes and says "No second opinion: <model> was unreachable (<reason>)" in the result and the list. The companion never uses the reviewer or a challenger as the judge.
- **Measured facts** (implementation mode). Every entry's lines changed come from git against the base, and the chosen test command is run in each worktree (an entry that changes the test script itself is flagged, and a failed or timed-out run is recorded as such and never counted as a pass). A benchmark runs three times per entry on the same computer, one at a time, and the median is compared. Only the repository's own runnable targets are offered, never free text.
- **Cost.** One limit per bake-off, default $12, split by stage: challengers 55% (45% in implementation mode), the neutral writer 10% (20%), the reviewer 25%, the judge 2%, the rest in reserve. A stage that would start with too little left does not start and says why; a challenger that reaches its share keeps what it did and is flagged. The list shows what each bake-off has spent.
- **Privacy and storage.** The code, descriptions and write-ups go to the models you picked, as with any session. Bake-offs are stored privately under `<config>/agent/bakeoffs/` (0700/0600), never in the repository, with the commits they hold under private refs. The stored bake-off keeps the model names (only the screen hides them); the reviewer's session and the review pack hold labels only. Deleting a bake-off never removes a worktree: implementation worktrees stay until you remove them through the keep flow. One bake-off runs at a time per computer, and the newest 20 are kept (a bake-off whose worktree you took is kept until you delete it).
- **When something fails.** A challenger that cannot start fails its own entry; the bake-off goes on with the rest. A designer or writer whose file is invalid is retried once in a fresh session; then the entry shows its summary and diff stat only, flagged *no write-up*. If the reviewer fails, the bake-off is *failed* with entries and facts kept and *Review again* offered. Stopping a bake-off stops its sessions; the companion stopping marks it failed (*interrupted*).
- **In the app** (`src/components/bakeoff/`, fetched on first open and gated on `canBakeoff`): the list (a session lists its repository's bake-offs, with progress, cost, who ranked first and the second-opinion note), the form, the entry cards and the result. `bun scripts/mock-companion.ts` serves canned bake-offs (a finished design bake-off with a split verdict, one whose judge was unreachable, an implementation one with a failing-tests entry and patches, one whose code is no longer kept, a running one that ticks and a failed one); with `--topic`, the *No project* session `fhe-statistics` lists a finished design bake-off of its scratch folder.

## Sparring partner

*Sparring partner* is *Quiz me* turned around. Instead of testing whether you understood a change, an agent challenges the decisions in it, one point at a time, and you defend them in your own words. It is for the moment before you merge, or before you build from a design: it argues the other side with the code open next to it, and you find out which of your decisions hold up. At the end you get the points you held, the risks still open and the changes it suggests. The wire contract is `@oh-my-pi/pi-wire/spar` (`spar-list`, `-create`, `-get`, `-reply`, `-close`, `-again`, `-excerpt`, `-delete`; the `spar-changed` push; the `canSpar` capability, which follows `canQuiz` and needs tmux). Nothing in the repository changes: the partner is read-only.

- **Starting one.** Open the quiz sheet (graduation-cap button at the top right of a session, or ⋯ → *Quizzes* on a phone) and pick the **Sparring** tab, then *New spar*. Shortcuts: *Spar with this change* in the Changes sheet and in the GitHub sheet (a pull request, or a whole stack), the command palette (*Spar with this change*, *Sparring sessions of this repository*), the **Sparring** button at the top (on by default; Settings → *Appearance* → *Top bar* hides it; ⋯ also lists it on a phone), and *Spar with this design* in the editor header when a Markdown or text file (`md`, `mdx`, `markdown`, `txt`, `rst`, `adoc`) is open.
- **What it challenges.** The new-spar form asks *What to challenge*: *This session's changes* (the worktree or branch against the default branch, as for a quiz), *A branch*, *A pull request* (a stack is offered as for a quiz, one part per pull request, bottom first), or *A design document* (pasted text, or a file of the repository). *Attach a design* adds a document to any change: the document is the claim and the change is what was built, so the partner also checks the one against the other. *Include why it was done* adds a digest of the session's conversation to a change or a design written in that session. The design's own lines are cited as `design:<line>`.
- **The exchange.** One point at a time, with the code it is about beside it (a phone shows it under the point). Each point is a decision, an assumption, a failure case or a migration risk, marked *Would block a merge*, *Worth fixing* or *Nice to have*. You write a defence and the partner replies: it *pushes back* with what your defence does not cover, *concedes*, or says *partly*. A reply is given the code around the point and any `path:line` you cite, and quotes real lines. Confidence, repetition and "the team agreed" are not evidence to it; a fact about the code is. You have three rounds per point; a third push closes the point as open. You can also *Concede* at any time, or *Accept the risk* (with an optional note that goes into the summary) when you have decided to live with it. Defences are limited to 4,000 characters. Its code opens up like a quiz's (*More of the code*), `@design` citations included.
- **What you learn.** When a point closes, it reveals what a strong defence says and, unless you held it, what the partner would change, with the code. Until then the partner's own case file (its strongest defence, the counters, the suggestion) stays on the computer and never reaches a device, so you cannot read your way to the answer. A point you *held* stays held; one you *conceded* becomes a suggested change; *partly held* and *open* ones (the rounds ran out, or you accepted the risk) are the open risks.
- **The summary.** *Held*, *Open risks* and *Suggested changes*, each item with its objection, how it ended and `path:line` citations that open the code; a score band; *Copy as Markdown* (and *Share as Markdown* where the browser can). *Spar again* replays only the points you lost or left open, in a new run; the earlier runs and their results stay. A spar can be left and continued later.
- **Cost.** One spending limit per spar covers writing the points and the partner's replies, default $6 (`maxCostUsd`; the field is in the form): writing gets 40% of it, every reply is capped at $0.50 and at what is left. When it is used up the partner stops answering with a plain message, and *Concede*, *Accept the risk* and the summary still work. Writing the points uses the model you pick (the computer's default otherwise); the replies use the *Model for the replies* field (`@default`, the default model role, otherwise). The list shows what each spar has spent. Limits: 12 points per spar, 8 parts, 60,000 characters per design, 2 spars written at once.
- **Privacy.** The code of the changes, the pull request descriptions, the design and, when attached, a digest of the session conversation go to the model you configure, as with any session. Spars and your defences are stored privately under `<config>/agent/spars/` (0700/0600), never in the repository; deleting a spar removes them and releases the commits it held.
- **How it is built** (`scripts/companion-spar*.ts`). It reuses *Quiz me*'s machinery (`companion-review-base.ts`, `companion-seed.ts`): refs resolve to commits held under private refs, a restricted read-only omp session in a throw-away checkout writes its points to one result file, and every citation is verified against the commit of its part (or the design's lines): kept, moved to the line the token is on, or dropped, and a point left without a citation is dropped. Each reply is one headless call whose answer is parsed into a move (`push`, `concede` or `partly`) and verified citations.
- **In the app** (`src/components/spar/`, fetched on first open and gated on `canSpar`): the Sparring list beside the quiz list (progress, outcome, cost), the new-spar form (the same subject picker as a quiz's), the point screen, and the summary. The mock companion (`scripts/mock-spar.ts`, through `scripts/mock-companion.ts`) serves a finished spar showing every outcome, one on a design, a failed one and one still being written, and a fixed partner (a defence with the word `because` is conceded to, one with `partly` is partly held, anything else is pushed back), so the screens can be tried offline.

## Installing the companion on colleagues' computers

A fork that deploys collab-web to GitHub Pages can also ship the companion as one binary and a one-line installer: `curl -fsSL https://<owner>.github.io/<repo>/install.sh | sh` installs the fork's `omp` (collab companion included, run as `omp companion`), sets `collab.webUrl` to the Pages site, runs `omp login` when no provider is usable, installs the companion as a launchd (macOS) or systemd user (Linux) service, and opens the app the companion serves on this computer, paired (see [The app served by the companion](#the-app-served-by-the-companion)). The release workflow (`.github/workflows/collab-release.yml`, tags `collab-v<version>-<n>`), the installer's checks, what it installs where, uninstalling, and the trust model (a paired device controls the computer; sessions use the colleague's own provider logins) are in [Install for colleagues](../packages/collab-web/README.md#install-for-colleagues). A colleague who has never used omp should start with [Getting started with omp collab](./collab-getting-started.md).

## Desktop app

`packages/collab-desktop` wraps the same web app in an Electron window for macOS (Linux and Windows builds are not ruled out, and the code keeps them possible). It runs this computer's companion for you, shows a menu-bar icon with the number of sessions waiting for you, sends a native notification when a session needs input or finishes a turn, saves files through the system save dialog, and has a global shortcut (default `⌥⌘O`) that shows or hides the window.

- **Companion.** On start it looks for a companion that already runs (the endpoint file `<config>/agent/collab-companion-local.json`, the process alive, the port answering) and attaches to it; otherwise it starts one and restarts it with a growing delay if it crashes. Quitting stops a companion the app started, unless *Keep the Companion Running After Quit* is on; it never stops one it attached to. The companion uses the `omp` the installer put on this computer (`omp companion`), which the app finds through `OMP_BIN`, its settings, the installer's state file and the usual directories. If there is none, the app shows the install command.
- **Other computers.** The window is the same app: *Add a computer* pairs laptops, servers and phones exactly as in a browser.
- **Open at login** is a menu item; the app then starts hidden in the menu bar.
- **Moving off the launchd/systemd service.** The app attaches to the service, so nothing has to change. To run the companion inside the app instead, use *Companion → Run the Companion Inside This App…* (shown only when a service is installed): it runs `omp companion --uninstall`, then starts and supervises its own. Nothing does this automatically. A companion the app started by hand counts as unmanaged, so the web app's own *Restart companion* is declined for it; use the app's *Companion → Restart Companion.
- **Install and updates.** The one-line installer offers it on a Mac with a desktop session (`--desktop` / `--no-desktop` decide without asking) and installs it as `~/Applications/omp collab.app` after checking its checksum (and its build attestation when `gh` is signed in). The app is signed ad hoc, not notarized: macOS runs what curl downloaded, while a copy fetched with a browser (the `.dmg` or `.zip` attached to each release) is blocked at first launch: open *System Settings → Privacy & Security* and choose *Open Anyway* for omp collab. The app checks the fork's GitHub releases once a day, verifies the download against `SHA256SUMS.txt`, and swaps the bundle when it quits (*Restart to Update* does it at once).

Details, the security model, binary sourcing and how to test it: `packages/collab-desktop/README.md`.

## Self-hosting the relay

The production relay is not currently distributed for self-hosting: its Go source and standalone binaries are not published. The endpoint list below documents the hosted service's network contract, not an installable release.

For local protocol development, this repository includes a source-available, WebSocket-only stand-in at [`packages/collab-web/scripts/local-relay.ts`](../packages/collab-web/scripts/local-relay.ts). Run `bun run relay` from `packages/collab-web` to listen on `ws://127.0.0.1:7466`. It implements `/r/<roomId>` but does not serve the browser client, `/share` blobs, or `/healthz`, so it is not a replacement for the production service. It binds loopback only and answers only requests addressed to a loopback host name.

The relay is a small content-blind Go service. It keeps no state beyond live connections and exposes:

- `GET /` — the static collab-web guest client (target of the `/collab` deep link),
- `GET /r/<roomId>?role=host|guest` — WebSocket upgrade,
- `POST /s` / `GET /s/<id>` / `GET /s/<id>/raw` — `/share` blob upload, viewer page, and blob fetch,
- `GET /healthz` — liveness.

## Architecture notes

Hub topology — the host is authoritative, guests never peer:

1. `welcome` + `snapshot-chunk` frames — initial state and transcript: the session's active branch (root to leaf), not entries on abandoned branches. The transcript is byte-bounded into chunks so each arrival resets the guest's progress timeout; oversized replicated entries are shrunk before transmission.
2. `entry` frames — durable session entries, broadcast pre-blob-externalization so images stay inline (guests cannot resolve host blob refs). Guests append them with ids preserved to a replica session file under `~/.omp/collab/<roomId>.jsonl` and into the agent's message array, which is why `/dump` and context estimates work. A `/clear` on the host appends a payload-less `reset_boundary` entry, which travels like any other entry (live, in the snapshot, in a delta resume and in `branch` frames); the context starts again after it. A guest that predates the type skips it. The web app draws it as a *Context cleared* divider and folds everything before the latest one behind a one-line *N earlier messages, before /clear* expander (*Show* unfolds them; find and copy work on them then). Rewinding to a prompt before the boundary branches the session as any rewind does, so the divider goes with the abandoned branch.
3. `event` frames — live agent events, fed straight into the guest's normal event controller; rendering is events-only to prevent double-render.
4. `state` frames — debounced footer snapshots: streaming flag, the host's full model object and thinking level (applied to the guest's replica agent state, so model display and context-window math are native), host context numbers, and participants.
   While a session spend cap is set (`session.maxCostUsd` / `session.maxTokens`, `--max-cost`, `/budget`), the host advertises `welcome.features` `spend-cap` and `state.spend` carries `{costUsd, tokens, maxCostUsd?, maxTokens?, capped}`; the web client shows a banner while `capped` and refuses nothing itself (the host refuses prompts). Scheduled companion runs pass `--max-cost` when the schedule has a per-run spend limit.
   With `routing.mode: auto` (or `/route on` on the host) each prompt the room sends runs on a routed model for that turn: `state.model` follows it like any model change, and a `notice` session event with `source: "routing"` names the tier, model and thinking level. A prompt whose frame carries its own model (`prompt-model`) is never routed. No frame or feature string was added; `/route` is host-only, so it is absent from `welcome.commands`. See [Model routing](./settings.md#model-routing).
   A host that advertises `cache-stats` adds `state.cache`: `{ last?, requests, hitPct?, misses, recentMisses }`, where `last` is the newest request that carried a prompt (`{ at, model, input, output, cacheRead, cacheWrite, hitPct?, tokensPerSecond?, ttftMs?, costUsd }`) and each of the five newest `recentMisses` is `{ at, reasons, reprocessedTokens, model }`. `reasons` lists the causes of a prompt-cache miss, most likely first: `model`, `system-prompt`, `tools`, `compaction`, `thinking`, `ttl`, or `unknown`. It rides the ordinary debounced state frame, so it costs nothing extra per turn. The web client shows it as a strip above the message box (see [Prompt-cache hit rate and misses](./settings.md#prompt-cache-hit-rate-and-misses)).
5. `bus` frames — mirrored task-subagent lifecycle/progress EventBus traffic, republished on the guest's local bus so the subagent HUD and status-line count work natively.
6. `agents` frames — agent-registry snapshots feeding a guest-local registry, so the Agent Hub table renders host subagents.
7. `ui-request` / `ui-request-end` frames — host select/editor prompts presented to full-control guests and dismissed everywhere once settled. Guests answer with `ui-response`. A `select` request for a tool approval may carry `approval` (see [Tool approval choices](#tool-approval-choices)).
8. `branch` frames — the active branch changed other than by appending (a guest's `rewind`, or the host's own rewind or `/tree` navigation): guests keep their entries up to `keep`, drop the rest, and append `entries`, the remainder of the new branch.
9. `rewind-preview`, `files-restored` and `turn-undone` frames — targeted replies to the `rewind-files` commands (see [Rewinding files](#rewinding-files)) and to `undo`/`redo` (see [Undoing the last turn](#undoing-the-last-turn)).

Guest→host: `hello`, `prompt`, `abort`, `agent-cmd` (hub chat/kill/revive), `fetch-transcript` (incremental subagent-transcript reads answered by targeted `transcript` frames), `ui-response`, and `session-cmd` (model, thinking level, compaction, rename, rewind, rewind-preview, redo-files, undo, redo, unqueue, queue-edit, queue-move, queue-steer). The replica loads through the regular `/resume` machinery, so theming, ctrl+o, and transcript behavior are native by construction; the guest process never chdirs to host paths.

Transcript fetches are capped at 4 MiB per reply and end on complete JSONL lines. Guests continue from `newSize`; a single entry exceeding the cap produces a terminal transcript error instead of an endless empty-read retry.
