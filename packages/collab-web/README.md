# @oh-my-pi/collab-web

Web client for [omp collab sessions](../../docs/collab.md). Paste a `/collab` link into the browser and you get the same live session guests see in the TUI: streaming transcript, tool-call cards, subagent panel with live transcripts, and a composer that prompts (or interrupts) the host agent.

## Quick start

```sh
# dev server (Bun HTML dev server with HMR) — http://localhost:3000
bun run dev

# offline demo: local relay + scripted mock host; prints a ws://localhost link
bun run mock-host
```

Host a session from any omp instance (`/collab`, or `/collab ws://localhost:7466` to use the mock relay), then paste the printed link into the connect screen. Deep links work too: `http://localhost:3000/#<roomId>.<key>` auto-connects on load.

`bun run mock-host --local-relay [PORT]` also serves the room on a second, loopback-only relay (`ws://127.0.0.1:<main port + 1>` by default) and puts it in the printed link as `?local=`; type `local off` / `local on` in its terminal to stop and restart that relay and watch the app fall back to the main one.

`bun run mock-host --limited [SECONDS]` fakes subscription limit windows and a session stopped at its Claude usage limit until SECONDS from now (default 5400): the app shows the limit bar with its countdown, *Resume at reset* continues the session just after the reset, and switching to a non-Claude model lifts the limit.

The mock host supports the message box features: it advertises `queue-edit` and `mentions` (queue follow-ups with *After turn* while its scripted turn runs, then edit, reorder or steer them; a prompt that carries mentions gets the `<referenced-context>` block in its transcript entry). To try `#` and `@` pickers, pair with `bun scripts/mock-companion.ts --session-link <join link>`, whose canned pull requests and sessions they list; without a paired computer `#` offers only pull request links the conversation contains. See [Collab → The message box](../../docs/collab.md#the-message-box) for stash, recall and large paste.

To try several computers offline, start two mock companions on different ports and pair with both: `bun scripts/mock-companion.ts --port 7471 --machine laptop --dir /tmp/laptop` and `bun scripts/mock-companion.ts --port 7472 --machine moonstone --hosts 1,2,3 --dir /tmp/moonstone` (each with `--session-link` of its own `mock-host`). `--machine` names the computer and gives its sessions ids of their own (their processes still share instance ids, as two real computers can), `--hosts` lists only those fixture sessions, and the room is kept in `<dir>/room.json` so a restarted mock is the same computer. Stop one to see its group go offline while the other keeps working. See [Collab → Several computers](../../docs/collab.md#several-computers).

To try the Personal agent offline, add `--personal fresh` (advertised, not set up: Settings → Personal agent → *Set up*) or `--personal enabled` (set up, with sample memories, About you, proposals, digests, an inbox and events, and a Personal session in the sidebar) to `bun scripts/mock-companion.ts`; without it the mock advertises and answers nothing of the Personal agent. `--personal-login missing` (default `ready`) leaves the profile without a login: the agent stays stopped and Settings shows the sign-in command until you `touch <dir>/personal-login-ready`, which stands for running `omp --profile personal login`. The agent is canned (`scripts/mock-personal.ts`, in memory): answering a question makes it "work" for three seconds and reply with an inbox item two seconds in, and every change is pushed to every paired device.

## Build & deploy

```sh
bun run build   # static site in dist/ (scripts/build-app.ts: bundle, assets, architecture export viewer, service worker)
bun scripts/build-app.ts --outdir /tmp/app --local   # the same build without the Pages analytics beacon: what the companion serves
```

`dist/` is a fully static SPA — host it anywhere, at the site root or under a path prefix (every URL the build emits is relative). JS/CSS bundles and chunks are content-hashed; favicons, `manifest.webmanifest`, `robots.txt`, `sitemap.xml`, and `og-image.png` come from `public/` and are emitted under stable names (canonical URL: `https://my.omp.sh/`). `scripts/build-sw.ts` then writes `sw.js`, an app-shell service worker that precaches the build. Its cache name is derived from the emitted files, so every deploy that changes the client ships a new worker. Two runtime requirements:

- **Secure context**: room keys are unwrapped with WebCrypto (`crypto.subtle`). WebCrypto and service workers are available only on `https://` or `localhost`.
- **Relay reachability**: the client connects straight to the relay over WebSocket (`wss://` for anything that isn't localhost). The default relay is `wss://my.omp.sh`; bare `<roomId>.<key>` links resolve against it (legacy `<roomId>#<key>` and `%23`-mangled links still parse).

The room key never leaves the URL fragment — it is not sent to the relay or any server.

## Install for colleagues

New to omp? [Getting started with omp collab](../../docs/collab-getting-started.md) walks a colleague through install, pairing, a first session, updating, uninstalling and troubleshooting. This section is the reference.

On macOS or Linux (x64 or arm64), paste one line into a terminal:

```sh
curl -fsSL https://ctrlc03.github.io/oh-my-pi/install.sh | sh
```

Then open the web app; there is nothing else to run. The installer asks before anything that needs a decision (an existing `omp`, installing tmux, logging in) and reads the answers from the terminal, so the pipe works. To skip the questions: `curl -fsSL … | sh -s -- --yes --no-login`.

**What it does**, in order:

1. Downloads the fork's `omp` binary for this OS and CPU (`omp-darwin-arm64`, `omp-darwin-x64`, `omp-linux-x64` or `omp-linux-arm64`) and `SHA256SUMS.txt` from the latest GitHub Release of the fork, over https only, and **refuses to install if the checksum is missing or differs**. When the GitHub CLI (`gh`) is installed and signed in it also runs `gh attestation verify` on the binary and refuses it unless the release workflow of this fork built it; without `gh` it says so and relies on the checksum alone. Linux needs glibc 2.35 or newer (Ubuntu 22.04, Debian 12, Fedora 36 and newer); Alpine (musl) is refused.
2. Installs it as `~/.local/bin/omp` (`--prefix DIR` or `PI_INSTALL_DIR` changes the directory). An `omp` that the installer did not put there is never replaced without a *yes*, and another `omp` elsewhere on `PATH` is named and left alone. If `~/.local/bin` is not on `PATH` it prints the line to add.
3. Checks tmux, git and a browser opener. tmux (needed for *Start session* and other vendors' agents) is installed with `brew`, `apt`, `dnf`, `pacman`, `zypper` or `apk` after you agree; git on Linux the same way, `xcode-select --install` on macOS.
4. Runs `omp config set collab.webUrl https://ctrlc03.github.io/oh-my-pi/`, so pairing links open this site and not upstream's app.
5. If no model is usable (no API key in the environment, no login), runs `omp login` on the terminal so the provider's browser sign-in works.
6. Runs `omp companion --install`: a LaunchAgent on macOS, a systemd user unit on Linux, started now and at login, restarted if it dies.
7. Prints the pairing link with a QR code for a phone (the Pages address) and opens the app on this computer in the browser: the copy the companion serves at `http://127.0.0.1:<port>`, paired with a fresh one-time link from `omp companion --print-local-link` (the Pages link when the companion serves no app). With `--no-open` nothing is opened and the closing message says so. On a re-run the installer updates in place and does not open the browser again (`--pair` shows the link anyway; `omp companion --pair` prints a fresh one any time, `omp companion --open` opens this computer's app).

Options: `--yes`, `--no-login`, `--no-service` (install the binary only; start the companion with `omp companion`), `--no-open`, `--pair`, `--prefix DIR`, `--tag TAG` (a specific release instead of the latest), `--service-dry-run` (print the service definition without installing it), `--uninstall`, `--help`. `--base-url URL` (or `OMP_COLLAB_BASE_URL`) fetches `SHA256SUMS.txt` and the binary from another https directory (a mirror; the attestation check is skipped for it, the checksum is not). Plain `http://` is refused unless `--insecure-base-url` is also given, which exists for the installer's tests and prints a warning. `--web-url` sets another `collab.webUrl`.

**What ends up where**

| What | Where |
| --- | --- |
| The `omp` binary (one file, companion included: `omp companion`) | `~/.local/bin/omp` |
| What the installer installed, so a re-run updates it and `--uninstall` removes it | `~/.local/share/omp-collab/install` |
| omp settings (`collab.webUrl`) and provider logins | under `~/.omp` (`PI_CONFIG_DIR`) |
| The native library the binary unpacks on first run | `~/.omp/natives/<version>/` (`$XDG_DATA_HOME/omp/natives` when that is set) |
| Pairing state: room key, paired devices | `~/.omp/agent/collab-companion.json` (mode 0600) |
| macOS service | `~/Library/LaunchAgents/sh.omp.collab-companion.plist`; log `~/Library/Logs/omp-collab-companion.log` |
| Linux service | `~/.config/systemd/user/omp-collab-companion.service`; log `journalctl --user -u omp-collab-companion -f` |

On Linux a user service stops when the last login session ends unless lingering is on; the install prints `loginctl enable-linger $USER` when it is off.

**Updating**: run the same command again (it replaces the binary, restarts the service and keeps your pairing), or `omp update`, which follows this fork's releases for these binaries and not upstream's. Settings → *About & maintenance* shows the companion's build tag.

**Uninstalling**: `curl -fsSL https://ctrlc03.github.io/oh-my-pi/install.sh | sh -s -- --uninstall` stops and removes the service and, if you agree (or pass `--yes`), deletes the binary. It keeps `~/.omp`, so logins, settings and the pairing survive a reinstall; delete that folder to forget them. In the app, Settings → *Devices* removes a paired device.

**Whose logins sessions use.** Everything runs on the colleague's own computer, with the provider logins and API keys of the user who ran the installer. Nothing is shared with the person who published the installer; sessions started from the app bill the colleague's own account, and the colleague's files, git and `gh` credentials are what the agent works with. The relay in between is content-blind (the default is `wss://my.omp.sh`; set `collab.relayUrl` to change it), and the room key lives in the pairing link's fragment.

**Trust model**: read this before pairing a device.

- *A paired device controls the computer.* It can start sessions in any folder, and an omp session runs shell commands, edits files and uses git, `gh` and the provider logins as that user; the app can also read and edit repository files and run scripts. Pair only devices you own, treat the pairing link and QR code like a password (one-time, valid for 10 minutes, but anyone who opens it first is paired), and remove devices you no longer use in the app's Settings → *Devices*. `omp companion --rotate` unpairs every device at once.
- *Where the trust comes from.* The installer, the binary and `SHA256SUMS.txt` all come from this fork: the installer from its GitHub Pages site, the other two from its GitHub Release, and the checksum only catches a corrupt or mismatched download, not a malicious release. Colleagues trust whoever controls the fork, its Pages site and its release workflow, as with any `curl | sh`. With `gh` signed in, the attestation check adds proof that a binary was built by the fork's `collab-release.yml` workflow and not uploaded by hand. Read the script first if in doubt: `curl -fsSL https://ctrlc03.github.io/oh-my-pi/install.sh | less`.
- Darwin binaries are signed ad hoc unless the fork has Apple Developer ID secrets, and `curl` downloads are not quarantined, so macOS does not prompt.

**For the maintainer: publishing a release.** Bump the version as usual (`packages/coding-agent/package.json`, natives package), then push a tag `collab-v<version>-<n>` (for example `collab-v18.8.9-1`; `<version>` must equal the package version, `<n>` counts releases of it). `.github/workflows/collab-release.yml` builds the fork's Rust addons and the binaries on GitHub-hosted runners (macOS 14 arm64, macOS 15 Intel, Ubuntu 22.04 x64 and arm64), signs the macOS ones, smoke-runs each on its own OS, attests their build provenance, and publishes the GitHub Release with the four binaries and `SHA256SUMS.txt`. Only the highest `collab-v*` tag (by version, then `<n>`) becomes the release the installer's default URL serves, so rebuilding an old tag never rolls colleagues back. A tag that already has a release is refused; the Actions tab run takes an existing tag and a `replace` option that overwrites that release's assets. Enable *immutable releases* in the repository settings so published assets cannot be swapped afterwards. `scripts/install-collab.sh` is published as `install.sh` at the root of the Pages site by the `collab-web pages` workflow, so the installer on the site only changes when that workflow runs. The first colleague install works once a release exists; until then the installer fails closed with a download error. Test the installer without GitHub: `bun test scripts/install-collab.test.ts`; point `--base-url` at an https directory that holds `SHA256SUMS.txt` and `omp-<os>-<arch>` (add `--insecure-base-url` for a local http server).

**Release duration and the native-addon cache.** Compiling the Rust addons is most of a release (about 40 minutes on a cold macOS Intel runner, 30 on Linux x64, 10-15 on the arm64 runners; the rest takes a few minutes). They only change with the inputs hashed by `scripts/ci-natives-key.sh` (the crates, the Cargo manifests and lockfile, the pinned toolchain, `packages/natives`, the natives build scripts, the target, the runner image), so the release looks for an artifact `collab-natives-<target>-<key>` from an earlier run and, when it finds one, skips the toolchain install and the compile: a release then takes about 5-10 minutes. The `collab natives` workflow (`.github/workflows/collab-natives.yml`) builds that artifact for all four targets on every push to `collab-pwa` that touches those inputs, so it is normally ready before the tag is pushed; a release started while it still runs, or after the 90-day artifact retention, compiles the addons itself and uploads them for the next one. Bumping the version in `packages/natives/package.json` (it is stamped into every addon) changes the key, so the first release of a new version waits for the build once, and later `<n>` of the same version reuse it. To rehearse a release without publishing, run the workflow from the Actions tab with an existing tag and `publish` unchecked: it builds, signs and smoke-tests, and skips the attestation and the GitHub Release (and the check that a release for the tag already exists).

## Installed app (PWA)

The client installs to a phone's home screen: Safari → Share → *Add to Home Screen*, or Chrome → *Install app*. A home-screen launch opens `start_url`, which has no fragment, so the client keeps its own state in `localStorage`:

- **Recent sessions**: every room that welcomed the guest, with its title, cwd, and full join link. Tapping one rejoins it. A room the relay reports as gone (`no such room`) is dropped.
- **Resume**: the room on screen when the OS last killed the app. It reconnects on launch, and an explicit *Leave* clears it.
- **Join without typing**: *Paste link* reads the clipboard (works with macOS → iPhone Universal Clipboard and accepts `omp join "<link>"` verbatim). *Scan QR* reads the `/collab` QR code with the camera (native `BarcodeDetector` where available, otherwise a lazily loaded `jsqr` chunk). Android's share sheet can also send a link to the installed app through the manifest's `share_target`.

**Updates**: launching the app while online always loads the current deploy (the service worker fetches the page network-first, bypassing the HTTP cache, and falls back to the cached copy after 3 s or offline). An app resumed from the background never reloads on its own, so whenever it comes to the foreground (at most once a minute) it asks for a service worker update and compares its own bundle with the deployed `index.html`; either finding shows *A new version of the app is ready · Reload*. Reloading keeps drafts, queued prompts, and the open room. Settings → *About & maintenance* shows the running *App build*.

Stored join links grant whatever their access says until the host closes the room; *forget* removes one. Each session's transcript is also saved on the device (IndexedDB, `src/lib/replica-cache.ts`; the 8 most recently saved sessions), so reopening the app shows it at once and the host sends only the entries after the saved tail (a delta resume) instead of the whole session; a host without delta resume (omp before this branch) or rewritten history gets the full snapshot, with the saved copy on screen until it completes. *Forget* drops the room's saved transcript; a room the host replaced carries it over. Foregrounding the app or regaining the network reconnects right away instead of waiting out the socket backoff, and a connection that was open when the app went to the background is replaced on phones and tablets if it stayed hidden for 10 s or more (on any device when the network returns; desktop browsers keep a hidden tab's sockets alive, so there foregrounding only skips the backoff), since iOS can suspend the page and leave its sockets dead without a close event; this covers the session and the companion connection alike. A host that does not welcome a connection, or stops sending its snapshot, within 30 s gets a fresh connection rather than ending the session. With a paired computer, a session whose room the host replaced (session switch, access upgrade, relaunch after a relay drop) reopens through the companion's current link, keeping the draft and queued prompts. A reconnect to the same session resumes from the last entry the app already holds (`hello.resume`): the host sends only newer entries, falling back to the full snapshot when it no longer has that entry. Hosts and the companion compress larger frames (deflate inside the AES-GCM seal) toward devices that advertise support; frame sizes on the relay therefore depend on content compressibility. Both need the omp hosting the session to include them; older hosts send the full snapshot uncompressed.

The composer keeps unsent text per room (it survives the OS killing the app), attaches images from the photo library, camera, or clipboard (anything over 1568px or 750 KB is downscaled to JPEG before it is sealed), and shows a row of one-tap quick replies while the input is empty. Settings → *Messages* edits the quick replies (saved prompts, also offered as chips when starting a session); they are stored per device. Prompts sent while the connection is down are queued (stored per room, so they survive an app kill), shown as pending bubbles you can cancel, and sent in order once the session is live again. Each queued prompt is sent at most once: a drop right after hand-off loses it rather than risking a duplicate. Read-only links never queue.

While the agent works, *Send* (Enter) steers the running turn as before, and *After turn* (Alt+Enter) queues the prompt on the host to run as its own turn once the current one ends. Queued follow-ups show above the input as *After this turn* chips; ✕ takes one back (the host's `unqueue`). Shown only for hosts that advertise `follow-up` in `welcome.features`.

The model pill beside the model and thinking pills picks a model, and a thinking level it accepts, for the next message only: the message runs on it while the session keeps its own model, and the pill clears once the message is sent (also for *After turn* and quick replies). A message queued while offline keeps its choice and is refused, not run on the session's model, if the host no longer offers it. Replies from a model other than the session's carry an *answered by* note. Shown only for control links on hosts that advertise `prompt-model` in `welcome.features`.

The attach button also takes files other than images (up to 8 per prompt). Text files (by type or extension, valid UTF-8) up to 256 KB are pasted into the prompt as a fenced block under their name. Anything else, such as PDFs or larger files, up to 10 MB, is uploaded through the companion to `$TMPDIR/omp-collab-uploads/<random>/<name>` (mode 0600, removed after 7 days), and the prompt names that path so the agent can read it. Without the companion such files are refused. A prompt may consist of attached files alone.

Inside a session:

- **Chat view** (⋯ → *View* for the session on screen, or `v`): prompts and replies only. Thinking and model/thinking-level markers are hidden, each run of tool calls folds into one line that expands to the usual cards, and a single status line tracks the running tool. Settings → *Messages* → *View for new sessions* sets the view every session opens with and is stored per device; without one, phones (≤640px) start in chat view and larger screens in the full transcript. The ⋯ choice and `v` change the open session only.
- **Keep latest turns** (⋯ → *Keep*): show only the last 1, 3, or 10 turns of a long session on this device; a note at the top counts the hidden turns and *Show all* brings them back. Only the display is trimmed: the session, the agent, and the saved transcript are untouched. Find searches the kept turns. Stored per device and session (50 sessions).
- **Context cleared** (`/clear`): the host's `reset_boundary` entry shows as a *Context cleared · the agent starts fresh from here* divider, and everything before the latest one folds behind one line, *N earlier messages, before /clear*, with *Show* to unfold it (find, copy and export work on it then; a newer `/clear` folds again). It folds together with *Keep latest turns*: the later cut wins. Rewinding to a prompt before the divider (*Edit & resend*, *Undo*) branches the session as it does anywhere else, so the divider goes with the abandoned branch. The context gauge follows the host's own numbers. A foreign agent's room lists only that agent's own commands.
- **Edit & resend** (pencil on a prompt): rewinds the conversation to just before that prompt and puts it back into the message box to change and send again. The turns after it leave the conversation; the session file keeps them as a branch, as the host's own rewind (Esc Esc) does. Refused while the agent works. Shown only for hosts that advertise `rewind`; every guest then sees the new active branch (the host's `branch` frame), and joining guests get the active branch only.
- **Also restore the files** (in *Edit & resend*): when the host advertises `rewind-files` (omp hosting a session inside a git repository, with `rewind.snapshotFiles` on), the confirmation previews how many files the dropped turns changed and, by default, puts them back as they were before the prompt, with the conversation. An *Undo restore* bar then brings the later state back until the agent next changes files; it refuses if files changed since. Restoring covers tracked and untracked, non-ignored files in the repository only (see [docs/collab.md](../../docs/collab.md#rewinding-files)); hosts without the feature show neither control.
- **Undo / Redo** (session sheet → *Last turn*): `/undo` in one tap: rewinds the conversation to before your last prompt, restores the files that turn changed when the host can (see *Also restore the files*), and puts the prompt back in the message box. A *Redo* bar (or the sheet) returns to exactly where it was, files included, until something new is sent; several undos redo one at a time. Shown only for hosts that advertise `undo`; refused while the agent works. See [docs/collab.md](../../docs/collab.md#undoing-the-last-turn).
- **Tasks**: while the agent's todo list has open tasks or its subagents are working, a bar above the composer shows *Tasks N/M* and the current task (or, with the plan done, the running subagent and what it is doing) plus how many subagents are working. Tapping it opens the plan and the subagents of the current `task` run, each marked to do (○), working (→), done (✓), or failed/aborted (✕) with what it was asked, what it is doing now, and how long it has run; tapping a subagent opens its transcript. The plan is read from the last `todo` result in the transcript, the subagents from the host's mirrored progress.
- **Slash commands**: typing `/` at the start of the message box lists the host's commands (with their argument hint and description) and your saved prompts; ↑/↓ and Enter or Tab pick one, Esc closes the list. Sending `/name args` runs it on the host the way its own editor would, with you named as the author: skills (`/skill:<name>`), prompt templates and markdown commands, `/plan`, `/retry`, `/clear` (drops the conversation context in place and keeps the session, as `/clear` does in the terminal; refused while the host is answering or compacting), and the session controls `/model <provider/id>`, `/effort <level>`, `/compact [instructions]` and `/rename <title>` (the session sheet's controls with a slash spelling: for this session only, refused while the host is answering or compacting, and the bare forms, which would open a selector on the host, are refused with a hint). After a command's name and a space the list offers its arguments: the host's models, the model's thinking levels, or, for `/resume`, the recent sessions of the host's folder. On a host started with `collab.autoStart: control` (a computer started from the app is) `/new`, `/resume <session>` and `/fork` also run; they replace the host's session, which ends the room, and the app follows to the new one through the paired computer, so without a paired computer they are not listed. They are refused while the host is answering, compacting or in plan, goal or vibe mode, and `/resume` reaches only sessions of the host's own folder. Every other host command (exit, login, settings, `/clear`, `/handoff`, extension and custom commands) is refused with an error; text that only starts with a slash, like a path, stays an ordinary prompt. Shown on full links to hosts that advertise `commands`.
- **Split view** (screens 1200px and wider, or a landscape tablet): *Open beside* on a session in the sessions sidebar or on the computer card shows it in a second pane with its own header, transcript, and message box, both live; the editor can dock beside the transcript instead of covering it (toggle in its header, remembered per device). Drag the divider between a pane and the transcript to resize the sessions sidebar, the agents rail, the second session and the docked editor (arrow keys move it by 16 px, Shift 64 px, Home/End go to the ends, Enter or a double-click resets it; sizes are saved per device and *Reset pane sizes* in Settings → *Appearance* clears them). Shortcuts act on the pane you last used. The second pane has no agents rail, task bar, find, or voice; narrowing the window closes it.
- **Copy & share**: under each finished agent turn, *Copy reply* copies the reply text and *Share* shares the prompt and reply as Markdown (the system share sheet, or the clipboard where there is none). ⋯ → *Export* shares, downloads (`<title>.md`), or copies the whole session as Markdown: prompts with their author, replies, one line per tool call, thinking left out.
- **Find** (magnifier): searches prompt and reply text, newest match first; ↑/↓ or Enter/Shift+Enter step through matches, which are highlighted with the CSS Custom Highlight API.
- **Changes** (⋯ → *Changes*): every file changed through `edit`, `apply_patch`, `write`, or an applied `ast_edit`, newest first, with line counts and each change's diff. Built from the transcript, so shell commands and edits made outside the session do not appear here; the companion's *Working tree* tab covers those.
- **New since you left**: rejoining a room shows a divider before the first entry you have not seen and an *N new* pill that jumps to it. The last seen entry is stored per room (50 rooms).
- **Session controls**: switch the host's model (session only, not saved as the default) or set the thinking level from the pills in the composer toolbar, or from the session sheet (⋯), which also compacts with optional instructions and renames the session (pencil next to its name, like the host's `/rename`). Shown only on full links to hosts whose omp supports guest session commands; older hosts hide them, and hosts that predate rename answer it with an error.
- **Inactive subagents**: parked and aborted subagents fold under *Inactive* in the agents rail. *Clear* hides them on this device only (stored per session); the host and other guests still list them, and one that comes back to life shows again. *N cleared · Show* brings them back.
- **Usage** (⋯): session cost and input/output/cache tokens summed from the assistant replies, plus the last turn.
- **Blocks**: every prompt, agent reply and tool run is its own block in the transcript, and in chat view a folded run of tool calls is one block. A tool block's header sticks to the top while its output scrolls and shows the command (`$ …` for `bash`) or the tool name and its main argument, a ✓ / ✕ (with the exit code) / spinner mark, and the wall time; its chevron expands or collapses it. Hover or focus a block for its actions: *Copy command*, *Copy output*, *Copy both* (Markdown: the command in a `sh` fence, the output in another), *Send to agent* (quotes the block into the message box, long output cut to its last lines), and *Share* on tools; *Copy* (and the edit pencil) on prompts; *Copy* on replies. Copied text has terminal colours stripped, and says so when the output was truncated, elided for the collab session, still running, or held images that are not copied. On touch devices a 450 ms press on a block opens the same actions in a sheet.
- **Selecting blocks**: click (or tap) a block's left gutter or header to select it, Shift+click to extend, ⌘/Ctrl+click to add or remove one. ⌘↑ / ⌘↓ (Ctrl on Windows and Linux) move the selection a block at a time, with Shift they extend it, ⌘C copies the selected blocks as Markdown when no text is selected, and Esc clears the selection before anything else. On phones the sheet's *Select* turns on checkboxes and a bottom bar with *Copy*, *Send to agent* and *Cancel*.
- **Keyboard** (desktop): one table in `src/lib/shortcuts.ts` drives the handlers and Settings → *Keyboard*. ⌘K / Ctrl+K opens the command palette, ⌘\ / Ctrl+\ toggles the sessions sidebar, `/` opens find, `i` focuses the message box, `G` (Shift+g) jumps to the latest message, `y` copies the last reply, `e` edits and resends the last prompt, `[` / `]` switch to the previous / next recent session, `s` opens the session sheet, `v` toggles chat view, `+` / `-` / `0` zoom the interface in, out and back to 100% (the browser's own ⌘+ / ⌘− / ⌘0 keep zooming the whole page), ⌘, / Ctrl+, opens Settings, `?` opens Settings → *Keyboard*, which lists all of them (gestures included, on touch devices too) and remaps them, and Esc clears the block selection, closes the top sheet or find, otherwise stops a running turn. Everything but Esc and the palette is ignored while typing in a field, and the keys avoid what browsers keep for themselves (⌘L / T / W / N / R, ⌘1–9, ⌘[ / ⌘]). Click a shortcut's keys in Settings → *Keyboard* and press the ones you want to remap it: overrides are kept per device (`omp.collab.keybindings` in `localStorage`), shortcuts that now share keys are flagged, keys the browser keeps for itself are refused, each override has a reset, and *Reset all* restores the defaults. Esc is fixed.
- **Command palette** (⌘K / Ctrl+K, or ⋯ → *Search* on a phone): one box that finds app actions (open a panel, switch model or thinking level, theme, export, anything a feature registers), slash commands (`/name`; picking one puts it in the message box), sessions (live ones on the paired computer, idle ones to share, recent rooms, and past ones from *All sessions*) and messages (this session's, plus every session's when the companion can search). Matching is fuzzy (`dkth` finds *Use the dark theme*, several words match in any order); recent picks come first and rank higher, and an empty box lists recents then the main actions. Start with `>` for actions only, `/` for commands, `@` for sessions or `#` for messages, or tap a scope chip. ↑ / ↓ (or Ctrl+N / Ctrl+P), PageUp / PageDown, Enter and Esc drive it. Features add entries with `usePaletteEntries` from `src/lib/palette.ts`; the entry's `shortcut` shows its live keys. `scripts/mock-companion.ts` serves canned sessions and messages to try the remote search.
- **Settings** (the gear in the header and on the connect screen, ⌘, / Ctrl+,, *Settings* in the palette or ⋯ → *Settings* on a phone): every setting in one two-column sheet (a list that drills in on a phone). *Appearance* (a live preview, theme, accent colour, text size, UI and code fonts, line spacing, zoom from 75% to 150%, pane sizes, the pet; fonts come from the device, nothing is downloaded, and *Reset appearance* restores the defaults) and *Messages* (Enter key, the view new sessions open with, speaking speed, display name, quick replies) are saved on this device; *Sessions* (auto-settle, saved on this device without a computer and shared through one when paired; worktrees need one) is always listed; *Notifications* (push on this device, GitHub and spend alerts), *Devices* and the computer half of *About & maintenance* (diagnostics, restart, update) act on the paired computer and appear only while one is paired; *Keyboard* remaps the shortcuts. Each section says where it is saved, the open section is remembered per device, and `openSettings("sessions")` in `src/lib/settings-ui.ts` deep-links to one.
- **Top bar** (Settings → *Appearance* → *Top bar*): the session header's optional buttons. On by default: Settings, Find, Editor, Code map, Quizzes, GitHub, Agents and Leave. Off until chosen: Changes, Architecture, Map of what changed, Terminal, Preview, Run, Timeline, Usage and All sessions, the actions that otherwise live only in ⋯. A button shows only where it applies (Editor and Code map need a paired computer, Quizzes a computer that writes them, GitHub a signed-in `gh`, Terminal, Preview, Run, Architecture and the two session lists their own computer features, Timeline a host that offers it, Changes a changed file or a working tree). Each has a box to show or hide it and move-up / move-down buttons; the bar changes at once, the choice is saved on this device (`omp.collab.top-bar`; a choice saved before a button existed never turns it on) and *Reset top bar* brings back the default. The ⋯ button at the right end of the bar, on every screen size, opens the session sheet (as the session name does), which has a row for every action, and the command palette finds them too, so a hidden button is never out of reach. A phone's bar has room for four buttons: the first four of yours, not counting Settings, Quizzes, GitHub and Leave, which stay in ⋯ there (the default phone bar is Find, Editor, Code map and Agents). The pure model is `src/lib/top-bar.ts`.
- **Touch gestures** (phones and tablets): swipe a block right to quote it into the message box and left to copy it (it follows the finger, shows the action and snaps back; it commits at about 30% of its width or on a quick flick, and only once the drag is clearly horizontal), double-tap a block to copy it, press and hold for its actions (including *Select text*, which shows the block's text in a sheet where the system's own selection handles pick part of it), swipe in from the left edge to open the sessions sidebar and from the right edge to open the agents rail (the first 20 px), swipe an open drawer toward its edge to close it, and swipe down on the message box to hide the keyboard. Edge swipes are ignored while a sheet is open; Safari's own back-swipe on the left edge is the browser's and cannot be overridden.
- A **Latest** button appears once you scroll away from the tail, and every code block has a **Copy** button.

### Companion: every session on your computer

`bun run companion` (in this package) opens one long-lived encrypted room on the relay and pairs the app with the computer it runs on. Scan the QR code it prints, or open the printed `https://…/#pair:<link>&invite=<code>` URL, once per device. Each pairing code works once and expires after 10 minutes; the device then holds its own credentials. From then on the connect screen lists every omp session on that computer that is hosting `/collab` (name, cwd, working / idle / needs input, guests), refreshed every few seconds, and a tap joins one with full control. No per-session link is needed. Inside a session, the sessions sidebar (header button at the left; docked on wide screens, a drawer on phones) lists the same sessions plus recent rooms (the button shows a dot while another session needs input), and a banner offers a one-tap jump when another session starts waiting on input.

```sh
bun scripts/companion.ts                       # print the pairing QR, then serve
bun scripts/companion.ts --install             # run it as a service, started at login and restarted on exit: LaunchAgent (macOS) or systemd user unit (Linux)
bun scripts/companion.ts --install --dry-run   # print the plist or unit without writing or loading it
bun scripts/companion.ts --uninstall           # stop and remove the service
bun scripts/companion.ts --pair                # print a fresh one-time pairing QR and exit (works while the companion runs)
bun scripts/companion.ts --rotate              # new room key: unpairs every device
bun scripts/companion.ts --no-local-relay      # serve without the loopback relay (and so without the app)
bun scripts/companion.ts --no-local-app        # serve the loopback relay without the web app
bun scripts/companion.ts --open                # open this computer's app, paired with a fresh one-time invite (starts a foreground companion when none runs)
bun scripts/companion.ts --print-local-link    # print that link without opening it (exit 1 when no companion runs)
```

- Sessions are listed in-process from omp's collab registry (`scripts/companion-list.ts`, a few IPC round trips per poll), falling back to `omp collab list --json` when that module cannot load. Opening a session (`omp collab link`) and sharing an idle one (`omp collab start`) go through the same module, so they spawn no process; a refusal such as `stale_generation` (the host started a new room since it was listed) is reported as is, and only an unexpected failure falls back to the installed omp CLI. Set `OMP_BIN` when `omp` is not on `PATH`.
- The relay and web URLs come from `collab.relayUrl` and `collab.webUrl`. The room id and key persist in `~/.omp/agent/collab-companion.json` (mode 0600), so restarts keep devices paired; `--rotate` issues a new key and unpairs every device.
- **Local relay**: next to the room, the companion runs a loopback relay (`scripts/companion-local-relay.ts`) at `ws://127.0.0.1:7467`, or the next free port when that one is taken (`--no-local-relay` turns it off), and writes it into the launch overlay as `collab.localRelayUrl` so the sessions it starts also serve their room there. A session started by hand does the same once `collab.localRelayUrl` is `ws://127.0.0.1:7467`. The app on this computer then connects over loopback and falls back to the public relay on its own when the relay is unreachable or its browser blocks `ws://` from an `https` page (Safari does; Chrome 147+ gates loopback behind a Local Network Access permission and fails it until granted, as headless Chrome 150 does; see docs/collab.md). Phones and tablets always use the public relay. Sessions need an omp that has `collab.localRelayUrl`; older ones are reached through the public relay only. The relay is content-blind: payloads stay sealed end to end.
- **The app on this computer**: the same loopback port also serves the web app (`scripts/local-app.ts`, plugged into `local-relay.ts` as its `app` handler), so `http://127.0.0.1:<port>` in a browser on this computer loads the app, the companion's room and every session over loopback, with no Pages site, public relay, mixed-content or Local Network Access prompt, and it works offline once loaded and installs as a PWA (scope `/`). The companion's own room is hosted on both relays (`scripts/companion-room.ts`; local peers are numbered above `0x40000000`, a device is logged as connecting through the `local` or `public` relay), and the app, when served from a loopback origin, tries the local relay first for the companion and every session and falls back to the public one (`src/lib/relay-route.ts`). Device pairing is unchanged (per origin, so a browser paired on Pages pairs again). Where the files come from: a compiled `omp` embeds the production build (`scripts/local-app-embed.ts` overrides `scripts/local-app-embedded.ts` at compile time; text files gzip-compressed, served from memory, `scripts/build-collab-binary.ts`); from a checkout the companion builds into `<config>/cache/collab-web/<source-hash>/` in the background (`scripts/local-app-source.ts`: the page says *building* and reloads itself until the first build is ready, a changed source tree builds beside the served copy and swaps in when done, two builds are kept). Rules: GET/HEAD only, the loopback `Host` check first (403 otherwise), no CORS headers, `nosniff`, `Referrer-Policy: no-referrer`, a Content-Security-Policy with the inline scripts allowed by hash, `index.html` and the service worker `no-cache`, hashed files `immutable`, a navigation to an unknown path gets the app and a missing file gets 404, and any path with an encoded separator, NUL or `..` gets 400. The pairing link comes only from the command line (`--open`, `--print-local-link`, which find the running companion through `<config>/agent/collab-companion-local.json`); no HTTP route issues invites. Share links and the *Devices* QR code keep using `collab.webUrl`. Settings → *About* shows *Served by*.
- **LaunchAgent**: `--install` writes `~/Library/LaunchAgents/sh.omp.collab-companion.plist` (absolute bun and script paths, `OMP_BIN`, `PATH`, and `PI_CONFIG_DIR` captured at install time) and logs to `~/Library/Logs/omp-collab-companion.log`. Stop a manually started companion first: two companions fight over the same room. Re-run `--install` after moving the repository. Use `--pair` to pair another device while the LaunchAgent runs. macOS privacy protection keeps a LaunchAgent out of `~/Documents`, `~/Desktop`, iCloud Drive and external volumes: to start sessions in folders there, macOS asks once whether bun may access the folder; allow it, or later turn bun on under System Settings → Privacy & Security → Files and Folders (only that folder class, unlike Full Disk Access), then restart the companion. The grant is per binary path: it covers bun whenever macOS holds bun itself responsible (launchd jobs), not bun run from a terminal, which uses the terminal's grants. Without it, starting there fails with "macOS blocked the companion from this folder".
- **systemd user unit (Linux)**: `--install` writes `~/.config/systemd/user/omp-collab-companion.service` (`$XDG_CONFIG_HOME` is respected), runs `systemctl --user daemon-reload`, `enable` and `restart` (so a re-run picks up changes) and prints the log command, `journalctl --user -u omp-collab-companion.service -f`, which holds no pairing link: a service prints none, because the journal is readable by other administrators of the machine. Run `omp companion --pair` (or `bun scripts/companion.ts --pair`) in a terminal for a fresh one-time link and QR; `--install` itself prints one to your terminal. The unit runs the absolute `bun` and `scripts/companion.ts` from a checkout, or `omp companion` for the standalone binary, with `Restart=always` and `RestartSec=5`, `WorkingDirectory=%h`, and `OMP_BIN`, `PATH` and `PI_CONFIG_DIR` captured at install time as `Environment=` lines (paths with spaces, quotes or `%` are escaped as systemd reads them; an executable path with a quote or backslash is refused, as systemd does). It has no `User=` (it is a user unit) and sets `KillMode=process`, so stopping or restarting the companion leaves the tmux sessions it started running; they stay in the unit's control group, and systemd logs a warning about them when the unit stops. `--install` needs `systemctl --user` and a running user manager; without one (WSL without systemd, a container, `su` or `sudo -u` without a login session) it writes nothing and prints how to run the companion by hand, for example `tmux new-session -d -s omp-companion omp companion`. The user manager stops with the last login session, so the install prints `loginctl enable-linger $USER` (once, as the user) to keep the companion running after you log out and across reboots. `--uninstall` runs `disable --now`, deletes the file and reloads systemd. Sandboxed sessions need macOS `sandbox-exec`, so on Linux the companion refuses them. Chrome for *Preview* is looked up in `CHROME_PATH`, the usual `/opt/google/chrome`, `/usr/bin` and `/snap/bin` locations, then `PATH` (`google-chrome`, `chromium`, `brave-browser`, `microsoft-edge`); tmux on `PATH` (or `/usr/bin`, Homebrew).
- **A paired device holds a standing capability for the whole computer**: joining every session with full control, reading files inside each session's repository, git status and diffs, and starting omp in any folder. The app keeps its credentials in this origin's `localStorage` only, and *unpair* removes them.
- **Devices** (Settings → *Devices*), implemented in `scripts/companion-devices.ts`: every paired device, with when it was paired and last seen. Rename or remove one, or *Add a device* to show a one-time pairing QR and link. The companion serves only authenticated devices (tokens stored as SHA-256 hashes in the state file; pending invites in `~/.omp/agent/collab-companion-invites/`), and each device's push subscription lives on its record. A removed device is signed out at once and stops getting notifications. It still knows the room key, so a dishonest relay could misroute frames to it; `--rotate` evicts every device for certain. Devices paired before this change must pair again.
- **Notifications**: Settings → *Notifications* → *Push notifications* subscribes the device to Web Push. The companion then pushes when a session needs input (the body is the pending `ask` question, read from the tail of the session file) or finishes a turn (the start of the last reply), straight to the browser's push service with its own VAPID key (stored in the same state file; `--rotate` replaces it and drops every subscription). A device showing the app gets the in-app banner instead. Tapping a notification opens that session. iOS offers push only to the installed app (16.4+); notifications stop while the companion is not running. The app icon shows how many sessions wait for input (installed app; iOS 16.4+), set by each notification even while the app is closed. On Android and desktop Chrome, needs-input and finished-turn notifications have *Reply*: the text is sent to that session once it is open, without opening the app first where the browser allows it.
- **GitHub alerts** (Settings → *Notifications* → *GitHub alerts*), implemented in `scripts/companion-prwatch.ts`: while a device has notifications on and `gh` is signed in, the companion checks your open pull requests (`gh pr list --author @me`) in the repositories of its sessions every 5 minutes, or every 2 while some checks are pending. It pushes when a pull request's checks finish (passed, or failed with the first failing check) and when someone else reviews or comments on it; tapping the notification opens the pull request. The first sighting of a pull request only records it. *Checks finished* and *Reviews & comments* turn each kind off. The last seen state lives in `~/.omp/agent/collab-companion-prwatch.json` (mode 0600).
- **Pull request watching** (feature `pr-watch`), implemented in `scripts/companion-prwake.ts` and `src/components/shell/PrWatch.tsx`: sessions that watch pull requests (`watch_pr`, `/watch-pr` or the session sheet's *Pull requests* row) publish them under `<config>/run/pr-watch/`; while `gh` is signed in the companion polls each one with conditional `gh api` requests (ETags; every minute while checks are pending, every 2 minutes otherwise) and leaves its latest reading in the session's inbox directory, so the session, which decides whether to wake the agent, does not poll GitHub itself. It writes a heartbeat (`companion.json`) while it does, and pushes only when a watched pull request merges or closes (checks and reviews already reach the phone through *GitHub alerts*). Without the companion, or when it stops reporting a pull request, the session polls it itself. See [docs/pr-watch.md](../../docs/pr-watch.md).
- **Session organisation** (the sessions sidebar), implemented in `src/lib/session-org.ts` (pure model: transitions, last-writer-wins merge, sections, auto-settle rules) and `scripts/companion-sessionorg.ts` (the companion's copy, the idle and pull request rules, `<config>/agent/collab-companion-sessionorg.json`, mode 0600): pin (drag to reorder on desktop), snooze, and settle sessions from a row's ⋯ menu, right-click, or a long press on a phone, with undo; auto-settle after N idle days or when the pull request merges or closes (both off by default). It lives in `localStorage` and, with a paired computer advertising `sessionOrgRev` in `hosts`, syncs through the companion by `session-org` frames. `scripts/mock-companion.ts` is an offline fake computer for trying it.
- **End sessions when they settle** (an option in the auto-settle settings, off by default; `canEndOnSettle` in `hosts`), implemented in `resolveEnding` in `scripts/companion-sessionorg.ts` and `endSession` in `scripts/companion.ts`: a settled session the companion started is ended (`tmux kill-session` of its `omp-<id>`) once it is idle; sessions started by hand are left alone. Settled sessions that were ended show an *ended* chip under *Settled* (`src/lib/use-ended-settled.ts` lists them from the 200 most recent sessions) and opening one, or *Move back to active*, resumes it. The pending ends live in the `ending` list of the organisation file; `settings.endOnSettle` is optional so older apps and companions keep the other copy's value on merge.
- **Staying reachable**, implemented in `scripts/companion-power.ts`: while it runs, the companion holds a sleep assertion, so the computer does not idle-sleep and every session stays online; the assertion ends with the companion. On macOS it is `caffeinate -i -s -w <pid>`; closing the lid still sleeps a Mac without an external display, so leave it open (the screen may turn off) or use `sudo pmset -a disablesleep 1` while away. On Linux it is `systemd-inhibit --what=sleep:idle` wrapped around `tail --pid=<pid> -f /dev/null`; polkit refuses a sleep inhibitor to a process outside a login session (the usual case for a systemd user service), so the companion then falls back to `--what=idle`, which only holds off the idle action, and a lid close or a desktop's own suspend timer may still sleep the computer: turn automatic suspend off in the desktop's power settings or with `sudo systemctl mask sleep.target suspend.target` on a server. The computer card and the sessions sidebar warn while the computer runs on battery (red at 20% or less) or the assertion could not be taken, and devices with notifications on are pushed when it goes on battery, when the battery drops to 20%, and when it is plugged in again. The power state comes from `pmset -g batt` on macOS and from `/sys/class/power_supply` on Linux (system batteries only, averaged; a computer without one reports no battery and no power state).
- **Inbox** (*Inbox* on the computer card or in the sessions sidebar; the badge counts sessions waiting on input), implemented in `scripts/companion-inbox.ts`: sessions that need input, with the pending question and its options, and sessions that recently finished a turn, with the start of the reply, newest first. An option or a reply opens the session and delivers it once joined; an option is dropped if the question changed meanwhile.
- **Diagnostics** (Settings → *About & maintenance*), implemented in `scripts/companion-diag.ts`: companion and omp versions (the build tag in the standalone binary), uptime, whether it runs under launchd, under systemd or was started by hand, keep-awake and power, how sessions are listed and how long that took, the measured round trip, and recent connection events from the computer and the app, merged by time. *Restart companion* (only when launchd or systemd runs it: `launchctl kickstart -k` on macOS, `systemctl --user restart --no-block omp-collab-companion.service` on Linux) and *Update omp* (`omp update`, refused while a session works) run after a confirm.
- **Terminal** (⋯ → *Watch the screen*), implemented in `scripts/companion-pane.ts`: a read-only view of the tmux pane the session runs in (found from the omp process ancestry, so sessions started by hand in tmux work too), with colours, refreshed every 2 s while it is open and the app is visible.
- **Screens** (⋯ → *Screens*): every image the session's tools produced (browser and `eval` screenshots, `read` of image files, generated images), newest first, in a grid with a full-screen viewer (swipe or arrow keys, *Open original*, *Jump to message*). User attachments are left out. New screens appear while it is open.
- **Preview** (⋯ → *Preview*), implemented in `scripts/companion-preview.ts`: a screenshot of a page on the computer (a dev server the session runs), taken with the Chrome (or Chromium, Brave, Edge) installed there through puppeteer-core with device emulation: phone 390×844 and tablet 820×1180 as touch devices with an iPhone user agent, desktop 1280×800, all at 2×, optionally the whole page (up to 6000 CSS px). Dev servers listening on the computer from the session's repository are offered as chips (`lsof`). It re-captures when the agent finishes editing files (2 s after the last edit, while the sheet is open and the app visible; *Auto* turns that off), and remembers the page, size, and options per session. Only `localhost`, `*.localhost`, `127.0.0.0/8`, and `[::1]` pages are captured, and the page may not navigate elsewhere. One browser stays warm between captures (about 0.6 s each) and closes after 2 minutes idle.
- **Voice input**: the mic button in the composer records on the device; the companion transcribes the recording on the computer with omp's local speech model (the `dictation` role when it names a local model, else Parakeet TDT v3; no API key, the audio stays on your machines) and the text lands in the draft to review before sending. The first use offers the model's one-time download on the computer (~680 MB for Parakeet). Recordings stop at 3 minutes. Decoding uses `afconvert` (macOS), with `ffmpeg` for webm/ogg and as a fallback; implemented in `scripts/companion-voice.ts`.
- **Hands-free** (headphones button next to the mic): each finished reply is read aloud with the device's speech voice (prose only: code blocks, tables, and link targets are skipped; long replies stop after about 1,500 characters), then the mic opens again. Recording stops after 1.5 s of silence (at most 60 s); what you said is sent after a 1.5 s countdown, and *Cancel* puts it in the message box instead. With no speech for 8 s, or two empty recordings in a row, it pauses on *Tap to listen*. Questions from the agent are read out with their options. Speaking speed (Settings → *Messages*: 1×, 1.25×, 1.5×) is stored per device. On iOS, the silent switch may mute the voice, nothing is spoken while the app is in the background, and if the audio meter cannot start, stopping falls back to a tap.
- **Working tree** (⋯ → *Changes* → *Working tree*): branch, upstream ahead/behind, changed files with line counts, per-file diffs against HEAD, and the last 15 commits, read with `git --no-optional-locks` in the session's repository. Includes changes made by shell commands and outside omp. Tap a diff line (a second tap or Shift+click extends the range within the hunk) to comment on it; comments also work on the *Branch* tab's diffs, survive switching files and tabs, and are kept per session on the device until sent. *Send to agent* puts one review prompt into the message box: each comment with its `path:line` range and the quoted diff lines. Not available on view-only links or for the *Agent edits* tab.
- **GitHub** (⋯ → *GitHub*), implemented in `scripts/companion-github.ts`: the open issues and pull requests of the session's repository (the one `gh` resolves for it, including `gh repo set-default`), newest activity first, up to 50, read with the computer's signed-in `gh` (offered only while `gh auth status` passes). Filters: *Open*, *Assigned to me* / *Mine* (`--assignee @me`, `--author @me`), and for pull requests *Review requested* (`review-requested:@me`). Pull requests show combined checks and the review decision. Opening an item shows its description and latest 30 comments as Markdown (raw HTML escaped, HTML comments dropped), a pull request's branch, size and every check, failing first. *Send to agent* adds a prompt with the title, link, branch, failing checks and description to the message box, for you to edit and send. Nothing is written to GitHub. Pull requests also have a *Files* tab (`scripts/companion-prreview.ts`): changed files with line counts and each file's diff, where a tap on a line (a second tap extends the range) adds a comment. The comments go to the agent as one prompt (*Send to agent*) or to GitHub as a review (*Submit review*: Comment, Approve, or Request changes, showing exactly what will be posted, pinned to the head commit you reviewed). *Merge…* offers squash, merge commit, or rebase and deleting the branch, and asks for an extra tick when the pull request is a draft or its checks fail or are still running. The companion checks again just before merging and merges only the head commit you saw (`gh pr merge --match-head-commit`); if commits were pushed since, it asks you to reload. Reviewing and merging are refused for sandboxed sessions.
- **Fix it** (`scripts/companion-cilog.ts`): a pull request with failing checks has *Fix it* in the GitHub sheet, and the *Checks failed* notification opens the same sheet. It shows each failing check with the end of its log (`gh run view --log-failed`, the last 200 lines or 16 KB per check, 8 checks at most) and offers the sessions open in that repository, the one on the pull request's branch first, or a recent folder of the repository to start one in. The chosen session gets a prompt with the failures and logs in its message box; nothing is sent until you press Send.
- **Run** (⋯ → *Run*), implemented in `scripts/companion-run.ts`: the scripts in the session's repository (`package.json` scripts through the package manager its lockfile names, Makefile targets, `just` recipes when `just` is installed, `cargo test` and `cargo build`), run on the computer after a confirm that shows the exact command and the script, recipe, or target body it runs; the run is refused if that body changed since the confirm. Only listed targets run, as an argument list without a shell, with credential-named variables removed from the environment. Output streams in with colours; *Stop* ends the whole process group (SIGTERM, then SIGKILL after 3 s); *Send output to agent* puts the last 200 lines into the message box. At most 3 runs at once per computer; the last 10 runs per session (30 in all) and their output (1 MB each) stay while the session is listed, until the companion restarts. Refused in a repository a sandboxed session works in, since that session could have written the scripts.
- **Download** (download button in the editor, file viewer, working tree, and screens viewer), implemented in `scripts/companion-download.ts`: saves a file from the session's repository to the device, in 4 MB pieces up to 100 MB, with progress and cancel. Phones offer the share sheet (*Save to Files*, *Save Image*); elsewhere it downloads. The same repository rule as the file viewer applies.
- **Schedules** (*Schedules* on the computer card or in the sessions sidebar), implemented in `scripts/companion-schedule.ts`: run a prompt once at a date and time, or daily at a time on chosen weekdays (the computer's time zone), in a new session in a folder (optionally a new worktree or sandboxed) or by resuming a session. A run starts omp in tmux like *Start session* and hands it the prompt (`omp ... -- <prompt>`), then notifies the devices; tapping opens the session. A run is skipped while the daily spend limit is crossed or the previous run's session is still working, and a run missed while the computer slept goes once on wake if less than an hour late. *Run now*, edit, pause, and delete from the list. Schedules are stored in `~/.omp/agent/collab-companion-schedules.json` (0600).
- **File viewer**: file paths in read, write, edit, `ast_edit`, LSP, and glob cards open the file read-only (first 512 KB, binary files detected), syntax-highlighted up to 256 KB (highlight.js, fetched on first open). Paths must resolve, after symlinks, inside the session's repository (or its cwd outside a repository).
- **Editor** (header button, or ⋯ → *Editor*), implemented in `scripts/companion-files.ts`, replaces the file viewer once the companion advertises `canEdit`: file paths in tool cards, the working tree and the code map open there. The session repository's files (git's tracked and unignored untracked files, or a walk of the cwd outside a repository skipping `node_modules`; at most 20 000) in a tree, *Go to file* (⌘P / Ctrl+P), tabs, and a CodeMirror editor (fetched on first open) with search (⌘F), undo per tab, and highlighting by file type. ⌘S / Ctrl+S or *Save* writes the file in place: each read carries a version (hash and size), and a save whose base version is no longer on disk is refused, offering *Reload* / *Discard mine* or *Keep mine*. Writes never create files, are refused inside any `.git` folder, for binary files, files over 512 KB, and sandboxed sessions; view-only links open files read-only. Open tabs are checked every 2.5 s and after each agent edit: a clean tab reloads with the changed lines marked, a tab with unsaved edits shows the conflict bar. With the code map available, F12, ⌘/Ctrl+click or the target button jumps to a symbol's definition (a list when several match). The message button puts the selected lines, with `path:lines` and a fenced block, in the message box. Tabs and unsaved edits survive closing the sheet until the page reloads.
- **Start session**: pick a recent folder (from the local session store) and start a new session or resume a recent one, optionally with a first prompt (sent once the session is joined) or a saved prompt. The companion runs `omp --config <overlay> [-r <id>]` in a detached tmux session (`tmux attach -t omp-<id>` on the computer), with an overlay at `~/.omp/agent/collab-companion-overlay.yml` that sets `collab.autoStart: control`, and opens it once it is listed. Resuming a session that already hosts opens that host instead. Resuming one that another omp on the computer has open (a Terminal omp, which an older omp does not list) is refused with a warning naming its pid, app and terminal, and *Resume anyway* sends `force`; the check combines `lsof` on the session file (writers hold it open), omps the registry lists, and `-r`/`--resume` in process arguments (`scripts/companion-open.ts`). Requires tmux.
- **Sandboxed sessions** (macOS): the *Sandboxed* toggle in *Start session* starts omp under `sandbox-exec` so it can read and edit code but not run it. Two layers enforce this:
  - omp gets only `read`, `grep`, `glob`, `edit`, `write`, `ast_edit`, `todo`, and `ask` (`--tools`). Extensions, LSP, and project MCP config are off. A second overlay, `~/.omp/agent/collab-companion-sandbox.yml`, denies shell, eval, browser, and subagent tools. They are denied rather than prompted, because anyone holding a control link could approve a prompt.
  - The OS profile allows writes only in the chosen folder and in the omp state omp must write (sessions, logs, databases, caches). Inside the folder, `.git`, `.omp`, `.claude`, `.vscode`, `.envrc`, and `.mcp.json` stay read-only at any depth, because they run code later. `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.kube`, `~/.docker`, `gh`/`gcloud` config, `.netrc`, `.npmrc`, and the companion's pairing file are unreadable.

  Limits: reads are not confined to the folder, since omp must read its install, config, and credential database. The network stays open for the model API and relay. A folder that contains your home or omp config folder is refused. Sessions the companion started sandboxed are badged in every list, the header, and the session sheet.
- **Start and new, and sessions without a project** (*Start session*): ⌘Enter (Ctrl+Enter off macOS) or the *Start and new* button starts the session without leaving the sheet and opens a fresh draft in the same folder with the same sandbox and worktree choice; what started is listed above the form with an *Open* button. The `start` request then carries the first prompt (`prompt`), which the companion hands to omp at launch (`omp … -- <prompt>`) so the session works without being opened, and starts sessions that share a folder one at a time (`createKeyedLock` in `scripts/companion-start.ts`) so each start claims its own host; worktree starts each make their own branch and checkout. *No project* in the folder picker (`scratch` in `start`) makes a folder `<omp config dir>/scratch/<YYYY-MM-DD>-<first words of the prompt, slugged>-<6 hex>` (`scripts/companion-scratch.ts`; `session` without a prompt, names in `src/lib/scratch.ts`) and starts omp there. The companion never deletes it (only a folder whose start failed and is still empty goes), sandboxed mode works (the folder is the sandbox's project folder, the one place under the config folder it may write), the worktree and *Compare models* choices are hidden, and it is refused when the config folder lies inside a git checkout (even a home folder kept as a dotfiles repository). Lists show these folders as "Scratch · convert pngs". Companions advertise `canBackgroundStart` and `canScratch`; with an older one the app offers neither.
- **Share idle sessions**: sessions that are running but not hosting `/collab` appear under *Not sharing* with a *Share* button, which starts hosting with control access through `omp collab start`. Needs an omp with `omp collab start`; with older versions the section stays empty.
- **Git flow** (⋯ → *Changes* → *Branch*), implemented in `scripts/companion-gitflow.ts`:
  - *New git worktree* (in *Start session*, new sessions only): runs `git worktree add -b <branch> ~/.omp/worktrees/<repo>/<branch with / as ->  HEAD` and starts omp there; the branch defaults to `omp/<YYYYMMDD-HHmm>-<4 hex>`. If omp fails to start, the worktree and branch are removed again.
  - *Branch* tab: the session's branch against its base branch (origin's default branch, else `main`/`master`): commits since the merge-base, every changed file (committed, uncommitted, and untracked) with a lazy diff from the merge-base, whether the branch is pushed, and the open pull request, if any.
  - *Commit* (`git add -A && git commit -m`), *Push* (`git push -u origin HEAD`), *Create PR* (`gh pr create --base <base> --head <branch> --title --body [--draft]`), and *Commit, push & open PR* each show the exact commands and run only after you confirm. The chain stops at the first failure and names the step. The app hands over a message, title, and description; nothing is amended, forced, or merged.
  - The companion refuses these writes while the session's agent is working, on the base branch, and on a detached HEAD. Pull requests need `gh` on `PATH` (or `GH_BIN`) and signed in (`gh auth status`, re-checked every five minutes), and a pushed branch. Git runs with `GIT_TERMINAL_PROMPT=0` and `gh` with `GH_PROMPT_DISABLED=1`, so missing credentials fail instead of waiting for input; repository hooks run as usual. Origin's URL is shown without credentials.
  - *Remove worktree* (`git worktree remove`, branch kept) is offered for worktrees under `~/.omp/worktrees/` once the session is no longer a collab host and the tree is clean.
- **Usage** (*Usage* on the computer card, or ⋯ → *Usage* in a session), implemented in `scripts/companion-stats.ts`: spend and tokens for every omp session on the computer, from omp's stats database (`~/.omp/stats.db`, the one `omp stats` reads): cost, tokens including cache, requests, and cache hit rate for the last 24 hours, 7, 30, or 90 days, or all time (7 days by default, remembered per device), a bar chart per hour (24h) or day with a cost or tokens toggle (tap or hover a bar for its value), and the top models and projects by spend. Before answering, the companion ingests new session files into the database, at most once a minute, so the first request after a long gap can take a while. *Spend alerts* (Settings → *Notifications*, `scripts/companion-spend.ts`) set a daily limit across all sessions and a per-session limit; subscribed devices are pushed once when one is crossed (the daily one once per local day). Spend is checked about every five minutes while a device has notifications on.
- **All sessions** (*All sessions* on the computer card, or ⋯ → *Sessions*): every session in the local session store, past and live, grouped by project with each project's spend, searchable by title or folder. Each row shows its last activity, cost, tokens, and models. A session hosting collab has *Open*, a running one that is not hosting has *Share*, and an ended one has *Resume* (needs tmux, like *Start session*). *Messages* searches what was said instead (`scripts/companion-search.ts`): prompts and replies across every session (not tool output or thinking), newest first, every word in the same message, 50 results or 1.5 s at most. A hit opens its session at that message; an idle or ended session is shared or resumed first, after a confirm.
- **Code map** (header button, or ⋯ → *Code map*), implemented in `scripts/companion-codemap.ts` over omp's codemap index (`packages/coding-agent/src/codemap`): a navigable map of the session's repository. Every view centres on a folder, file, or symbol, with what uses it on one side and what it uses on the other, and its contents below (subfolders and files, a file's symbols, a type's members); tap any of them to move there, with back, breadcrumbs, and search by path or symbol name. File links come from names a file imports (or reaches by a qualified path) that exactly one file of the same language defines, so a link is evidence rather than a guess; folder views roll outside paths up to the folder that branches off. Symbol views list callers, callees, emitters, handlers, publishers, and the cross-language links (Solidity event → Rust decoder → internal type, Rust → Solidity calls, Rust → Noir circuits), dashed in the accent colour, and *Flow* walks them several steps downstream or upstream. *View source* opens the file viewer at the symbol's line. On wider screens a folder also gets a force-directed *Map* of its contents (size by symbols, colour by language, line width by references; drag to pan, wheel or buttons to zoom). Test and fixture files are left out. The first request for a repository builds its index, which can take a minute on a large one; later requests re-parse only changed files. The companion loads the codemap module from this checkout, so the native extractor must be built; without it the entry points stay hidden. Path links in tool cards have a *map* button that opens the code map on that file, and a file's view lists the recent sessions that changed it (edit, write, and patch tool calls in the session files). The code map's code loads on first open.
- **Architecture maps** (*Architecture* on the computer card and in ⋯, *Map this PR* in the GitHub sheet, *Map what changed* in a session, and the command palette), lazy-loaded and gated on `canBlueprint`: layered diagrams of a repository (or a diff map of a PR, branch or what the agent just changed) that open into each other from the whole system down to files and symbols, every arrow citing the code behind it; pan, zoom, search, a code panel with the cited line highlighted, and *Export* to one standalone HTML file that works offline from `file://`. See `docs/collab.md`, *Architecture maps*.
- **Quiz me** (the graduation-cap button at the top right of a session opens its repository's quizzes, ⋯ → *Quizzes* on a phone; *New quiz* there, *Quiz me* in the Changes sheet and on a pull request or a whole stack in the GitHub sheet), lazy-loaded and gated on `canQuiz`: a read-only agent, given the diff (and the session's conversation, to ask why things were done), writes conceptual questions that each cite the code behind them (verified against the commit like an architecture map's arrows); you answer one at a time, multiple-choice questions are graded at once, free-text answers by a small cheap model against a hidden rubric, and the end shows your score and the topics to revisit. Quizzes are saved and can be retried; one spending limit (default $1) covers writing and grading. See `docs/collab.md`, *Quiz me*.
- The working tree, file viewer, editor, and path links appear only when the companion lists the current session. Only sessions publishing control access are listed. The companion must be running for the list to load.

To make `/collab` links and QR codes open your own deployment, set `collab.webUrl` to its URL. The repository's `collab-web pages` workflow deploys this package to a fork's GitHub Pages site (`https://<owner>.github.io/<repo>/`). It runs on pushes to the `collab-pwa` branch or on demand.

## Pet

A small animated companion floats over the app and shows what the agent is doing. It is on by default with a mouse, off on phones and tablets (turn it on in Settings → *Appearance*), and its settings stay on the device.

| The pet | When |
| --- | --- |
| failed (about 2.5 s) | a tool or the turn just failed |
| jumping (about 2 s) | the plan finished: every task is done |
| waving (about 2 s) | a turn ended cleanly |
| waiting | a question or approval waits for you |
| running | a tool is executing, or the turn is in flight |
| review | the model is thinking, or only reading tools (read, grep, find, search…) run |
| idle | nothing is happening |

The first three play only when seen live, never when a session is opened or reconnected. On the connect screen the pet follows the paired computer's sessions: waiting if any needs you, else running if any works.

- **Moving it**: drag the pet (the spot is kept as a fraction of the window, so it survives resizes), or focus it and press the arrow keys. By default it sits at the bottom right above the message box and the bars over it (and above the jump-to-latest button on a phone). It stays below sheets and hides while a phone's keyboard is up. A click shows its status for 2 s; Alt + scroll over it resizes it.
- **Roam** (off by default): while idle, the pet walks along its band above the message box, pauses and sometimes hops. Any other state stops it and sends it back to its spot. It uses one `requestAnimationFrame` loop only while a step moves it.
- **Reduced motion and hidden pages**: with `prefers-reduced-motion` the pet shows still poses and does not roam; a hidden page freezes it and stops its timers.
- **Pop out** (desktop Chrome and Edge, Document Picture-in-Picture): Shift-click the pet, or *Pet…* → *Pop out*. A small always-on-top window shows the pet with a status bubble ("working…", "thinking…", "your turn", "done", "failed") in the app's theme; clicking it focuses the app tab where the browser allows it, and *Back to the app* closes the window. The in-page pet is hidden meanwhile. The choice is remembered, but the window never reopens on its own (the browser needs a click): the pet then shows a small *Pop the pet out again* chip.
- **The petdex gallery**: *Pet…* → *Change* lists [petdex](https://petdex.dev) pets (search by name, kind or creator). Nothing is fetched until you open that list. Opening it contacts `petdex.dev` (the list, about 1.8 MB, kept on the device for a day) and `assets.petdex.dev` (each pet's animated preview, about 55 KB, and the chosen pet's sprite sheet, about 2 MB, kept on the device so the pet works offline). Pets are user-submitted fan art; the list shows who made each one. If a download fails, the current pet stays and the picker says why.
- **Settings** (Settings → *Appearance*, or *Pet…* in the command palette): show the pet, which pet, size (about 64 px with a mouse, 44 px on touch), Roam, Pop out, and *Reset position*. The palette also offers *Show pet* and *Hide pet*.

The pure rules live in `src/lib/pet-activity.ts` (state precedence and transients), `pet-roam.ts`, `pet-layout.ts` and `petdex.ts` (manifest validation and sprite-sheet geometry); the mascot art is `src/components/pet/Mascot.tsx`. The mock host plays a failing tool when a writer sends `fail`, and an approval when one sends `approve`.

## Architecture

- `src/lib/` — vendored wire codec (`codec.ts` AES-256-GCM, `link.ts` envelope + link grammar), `socket.ts` reconnecting relay socket, `client.ts` guest session store (`GuestClient` + immutable snapshots for `useSyncExternalStore`). Shared protocol shapes come from `@oh-my-pi/pi-wire`.
- `src/components/` — `transcript/` (entries, markdown, tool cards), `agents/` (panel + transcript drawer), `shell/` (connect screen, header, composer, banners, toasts).
- `src/tool-render/` — per-tool React renderers shared with coding-agent HTML session exports: one view per built-in tool, common `ToolView` chrome, theme-adaptive `tv-` design tokens, and an `<omp-tool-view>` web-component wrapper. The `ToolRenderHost` seam lets hosts wire agent-id chips to a sub-session view (drawer here, overlay in exports) and, through the optional `openFile`, turn file paths into links (the companion file viewer here).
- `scripts/` — `local-relay.ts` (content-blind relay on `Bun.serve`), `mock-host.ts` + `fixture.ts` (scripted host for offline dev), `companion.ts` + `web-push.ts` (companion room and its WebCrypto-only Web Push sender: RFC 8291 encryption, RFC 8292 VAPID), `companion-git.ts` (read-only git and contained file reads), `companion-files.ts` (editor file tree, version-checked writes and version polling), `companion-stats.ts` (usage report and all-sessions list from omp's stats database; `omp-stats.d.ts` types its three subpath imports so tsc does not walk into pi-ai), `companion-codemap.ts` (code map views over the codemap index), `companion-sessions.ts` (session-file parsing for notifications and recent folders), `companion-start.ts` (tmux launch), `companion-sandbox.ts` (sandboxed-session profile, overlay, and detection), `companion-launchd.ts` (LaunchAgent), `build-sw.ts` (service worker: app-shell cache, push display, notification taps), `build-tool-views.ts` (bundles `src/tool-render/` + React into `packages/coding-agent/src/export/html/tool-views.generated.js` for self-contained exports).
- Architecture maps (companion side, `scripts/companion-blueprint*.ts`): `-git.ts` (target resolution: branch, pull request, `@worktree` snapshot without touching the real index; private refs; detached checkouts), `-index.ts` and `-source.ts` (the index levels from the code index, no model, with import-line and call-line citations and diff marks), `-agent.ts` with its three `.md` briefs (the read-only omp session that writes the top diagrams, and the wait for its result file), `-verify.ts` (parses the agent's JSON and checks every `path@line@token` against the commit: kept, moved or dropped), `-store.ts` (`<config>/agent/blueprints`, 0700/0600) and `companion-blueprint.ts` (the run, excerpts, refresh, delete). See [Collab → Architecture maps](../../docs/collab.md#architecture-maps).
- Local relay: `scripts/companion-local-relay.ts` starts `local-relay.ts` (loopback only, loopback `Host` only, browsers only from the app's origin, never as host, guests refused with 404 before the upgrade when the room is missing) at `ws://127.0.0.1:7467` or the next free port; `src/lib/relay-route.ts` decides which relay the app tries first (`?local=` link parameter, touch devices excluded, 1.2 s attempt limit, 60 s cooldown) and `socket.ts` falls back to the public relay.

The browser bundle is standalone — no dependency on `@oh-my-pi/pi-coding-agent` at runtime or type level. The companion script reads omp's stats database through `@oh-my-pi/omp-stats` subpath imports and the codemap index through `@oh-my-pi/pi-coding-agent/codemap/index` (loaded on first use; `omp-codemap.d.ts` types it so tsc does not walk into the coding agent). Wire-shape drift is prevented by consuming the same `@oh-my-pi/pi-wire` contracts as the host, with sealed-frame interop still covered by `test/codec.test.ts`.
